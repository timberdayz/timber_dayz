# ADR-2026-11-13：模板漂移判定口径收敛为唯一入口(SSOT)

- 状态：**已接受**
- 日期：2026-11-13
- 影响域：数据采集与治理(模板治理 / 漂移判定 / 入库前置校验)

## 背景

「什么算模板漂移、什么算阻断」这件事，系统里曾经有**三份**定义：

| # | 位置 | 它在算什么 |
|---|---|---|
| 1 | `backend/services/template_matcher.py::_classify_header_changes` | 自己把列差异分成 blocking / non_blocking，并对 `shopee/orders/monthly` 单开一个口子 |
| 2 | `backend/services/semantic_field_contract_service.py::evaluate` | 又算一套 `should_block` / `missing_required_keys` |
| 3 | `backend/services/data_sync_status_semantics.py` | 只定义「状态叫什么」，不管「什么算漂移」 |

后果（2026-11-13 实测）：

- 业务口径只能靠 `if` 打补丁。`shopee/orders/monthly` 的豁免是 2026-06-17 的救火补丁（提交 `e1c7cfca`），TikTok 订单接进来时没有人想到要一起打；
- 各域行为不一致：同一个「文件多一列」，Shopee 订单月报放行，TikTok 订单月报阻断；
- 治理面板上出现过「匹配率 100.0% 却报阻断漂移」的自相矛盾状态（纯列顺序变化被误判）；
- 用户在界面上改完模板保存，仍然看到「模板已保存，但该样本文件仍未通过治理复核」—— 因为保存不触发重检，面板读的是上一次检查留下的漂移快照。

## 决策

### 1. 判定口径收敛为唯一入口

新增 **L3 唯一判定入口** `data_sync_status_semantics.classify_drift`，并把漂移判定拆成三层：

| 层 | 模块 | 职责 |
|---|---|---|
| L1 事实 | `template_matcher.detect_header_changes` | 只产出事实：列差异 / 顺序 / 值形态。**不下结论** |
| L2 语义 | `semantic_field_contract_service.evaluate` | 只产出语义事实：必填键是否可解析 / 可选键缺失 / 多余列 / 少列的三种归宿 |
| **L3 结论** | `data_sync_status_semantics.classify_drift` | **唯一**判定入口：事实 + 语义 → 阻断与否 / 状态 / 原因 |
| 编排 | `data_sync_template_status_service` | 选基准 → 跑 L1/L2 → 取 L3 结论 → 产信号。**不写规则** |

`template_matcher._classify_header_changes` 与其中的平台特判一并删除。

### 2. 业务口径（唯一一条规则，对所有域一致）

> **多一列 ⇒ 阻断，直到模板把它纳入；少了必填字段 ⇒ 阻断；可选列与列顺序变化 ⇒ 不阻断。**

「多一列要阻断」的**理由**（此前没有人写下来过）：

模板没声明的列**不会写进事实表**。若放行 ⇒ 新列的数据被**静默丢弃**，且没有任何提示（治理面板不提示，因为不是阻断漂移；已入库的行不重算）。所以「多一列」必须先拦一道，把「模板落后于源文件」变成一个**待办**；等运营更新模板（新版本纳入该列）⇒ 契约晋升 ⇒ 文件按新模板解释 ⇒ **新列的数据这才真正落库**。

唯一的例外：用户在「已确认的新列」清单里确认过的列 ⇒ 不阻断（用户明说不要）。

「少一列」按**能否证明它可缺**分三种归宿：已证明可选 ⇒ 不阻断；绑定必填语义键且被别名救回 ⇒ 不阻断（缺的是列名，不是数据）；其余 ⇒ 阻断。**该域没有语义契约时，保守阻断**。

`shopee/orders/monthly` 的旧豁免被取消 —— 它原本会造成**新列数据被静默丢弃**（与其他所有域不一致且丢数据）。

### 3. 模板发布是一次带影响面复核的闭环动作

新增 `backend/services/template_recheck_service.py`，作为「重检与放行」的 SSOT：

- 模板保存成功后**立刻**重检同维度的待更新文件，能过的当场放行（并完成契约晋升与漂移快照搬移）；
- 定时巡检**复用同一份**逻辑（`scheduled_tasks._recover_template_update_required_files` 改为调用它），两处不再各写一套；
- 判定复用 `DataSyncService.get_file_sync_readiness`（与入库前置校验同一条链路），避免「面板说过了、入库说没过」。

### 4. 治理面板同时给出组合级与文件级结论

漂移快照回答「这个组合还有多少文件卡着」（待办不会凭空消失），**实时判定**回答「这个样本文件此刻行不行」。前端提示因此分成三态：已放行 / 仍待重检 / 仍有字段对不上。

## 后果

**正面**

- 「什么算漂移」只有一处定义，平台特判消失；
- 各域行为一致；「100% 匹配却阻断」的荒谬状态消失；
- 用户改完模板立刻看到效果，不必等 15 分钟巡检。

**代价与约束**

- 「多一列」仍然是阻断项 —— 这是**刻意**的（见上），不是遗漏；
- 判定口径变更属行为变更，必须用失败集 diff 证明无回归（见 `docs/guides/VERIFICATION_MATRIX.md`）；
- 口径写在一处 ⇒ 改口径必须改 L3，并同步更新守护测试 `backend/tests/data_pipeline/test_drift_classification_ssot.py`。

## 后续（不属于本 ADR）

- 「同一维度多种格式并存」（`format_signature`）：解掉历史文件因模板升级而补不回来的问题，属 V2 重建期范围；
- 入库批量刷新物化视图：解决「每入库一个文件刷 25 个视图」的吞吐问题，属 V2 重建期范围。
