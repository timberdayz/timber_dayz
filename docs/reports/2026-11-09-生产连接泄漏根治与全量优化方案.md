## 二、连接泄漏：为什么必须「彻底」而不是止血

### 2.1 比喻

数据库连接池像一栋 **80 个坑位的停车场**。Celery 每跑一个任务，就开一辆车进停车场，**但没把车开走**（连接没归还）。车越停越多，停车场最终满员，此时任何新请求（开门）都进不来 ⇒ 随机 500。

### 2.2 实测证据（生产，只读）

| 指标 | 实测值 |
|---|---|
| 连接总数 | **80 / 80 打满** |
| 最近 5 分钟 / 15 分钟 / 60 分钟新建 | 11 / 23 / 45 条（≈0.75 条/分钟，**只增不减**） |
| 来源分布 | `172.18.0.5`（backend_api）32 条；`172.18.0.6`（celery_worker）47 条 |
| 最早一条连接 | **8 小时 27 分前**创建，至今仍在 |
| 这些连接的最后 SQL | `COMMIT;` ⇒ 事务已提交，**连接本身没关** |
| Celery 配置 | `--concurrency=2`（2 个子进程 ⇒ 每进程独立连接池） |

### 2.3 根因（代码级）

`backend/models/database.py:430` 的 `reset_async_engine_pool_for_new_loop()` 实现为：

```python
async_engine.sync_engine.dispose(close=False)   # ← 只「标记作废」，不「关阀门」
```

- asyncpg 的连接**绑定在事件循环上**；`asyncio.run()` 一结束，循环就死了，连接**再也关不掉**，只能滞留在数据库服务端干占位。
- 这个 workaround 被 `backend/tests/test_celery_async_runtime_reset.py:24` 的 `assert called["close"] is False` **固化成「契约」**，所以没人敢改。
- 9 个调用点：`data_sync_tasks.py`(L149/L490)、`scheduled_tasks.py`(L508/L1633)、`refresh_queue_tasks.py`(L487/L711)、`price_adjust_notify_tasks.py`(L169)、`source_freshness_tasks.py`(L44)、`data_processing.py`(L128)、`services/event_listeners.py`(L247)。

### 2.4 根治设计（不是加池子，不是加 kill 脚本）

| 动作 | 说明 |
|---|---|
| 新增 `backend/utils/async_task_runner.py::run_async_task()` | 全仓库**唯一** `asyncio.run` 出口；在 **当前 loop 内** 于 `finally` 中真正关闭 engine |
| 新增 `backend/models/database.py::dispose_async_engine()` | `await async_engine.dispose()`（= close=True），在当前 loop 内真正关闭连接 |
| 9 个调用点改调统一出口 | 不再各自 `asyncio.run` + `dispose(close=False)` |
| `reset_async_engine_pool_for_new_loop()` 降级为兜底 | 保留函数但改写注释，明确写清「这是兜底，不是正解」 |
| 改 `test_celery_async_runtime_reset.py:24` 断言 | 从「必须 close=False」改成「最终必须真正 close」 |
| 新门禁 `scripts/verify_async_loop_cleanup.py` | R1 禁裸 `asyncio.run(`（只许在 runner 内）；R2 禁 `dispose(close=False)`（只许在兜底函数内且须写理由）；R3 `reset_...` 只许在 helper/门禁内出现；豁免必须写理由，否则门禁自身报错 |
| **泄漏回归测试（直接证伪）** | 循环跑 N 轮同步任务，断言 `pg_stat_activity` 中本进程连接数**不增长**；本地 15432 隔离库执行 |
| CI 接线 | 接入 `.github/workflows/ci.yml`（现有两个门禁之后） |

**验收标准**：本地连跑 50 轮同步/采集任务，`pg_stat_activity` 连接数稳定在基线不增长；门禁返回 0；后端全量 0 failed。

## 七、风险与回滚

| 风险 | 影响 | 缓解 / 回滚 |
|---|---|---|
| 生产连接已 80/80 打满 | 上线期间新连接被拒，冒烟可能**假失败** | 上线前先重启一次 celery worker（释放泄漏连接）只为**腾出空间**，这不是修复本身 |
| 10 个迁移不可逆 | 数据回退困难 | 强制顺序：先演练 → 再备份 → 再迁移；备份必须 `pg_restore --list` 校验 |
| `dispose()` 真关连接池若实现不当 | Celery 并发任务可能误伤 | `run_async_task` 内**每个任务独立收口**，不跨 loop 共享 engine；单测 + 50 轮泄漏回归验证 |
| `max_connections` 提到 200 只是**争取时间** | 不修代码仍会漏 | 明确：这不是修复，是防止修复上线前被打死 |
| 部分索引在线建索引失败 | 迁移中断 | 用 `CONCURRENTLY` + 幂等；失败可重跑 |
| 前端门禁升级后立刻红 | CI 阻塞 | 顺序强制：先清红项再升级门禁 |
