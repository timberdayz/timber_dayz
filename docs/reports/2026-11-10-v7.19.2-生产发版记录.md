## 一、背景与触发

- 发版对象：`tag v7.19.2` → commit `387d64075d5fed33aef038f0c6269379b65d8a7f`
  （= 批1~7 全部根治修复的验收版本；main 另有一次纯排版 commit `ad3d4b2d` 在其后）。
- 官方流水线 run `42671879430`（Deploy to Production）两次 attempt 均
  `completed/failure` 且**一个作业都没有被创建**；同一时刻 main 的 CI 作业全绿但 run 层判失败。
- 根因是 GitHub 官方平台事故（`Incident with Actions and Checks API`，
  Actions 组件由 partial_outage 升级为 **major_outage**），非本仓库工作流问题：
  `v7.19.1` 及以前 7 次发版全部成功，且 `deploy-production.yml` 在
  `v7.19.1..v7.19.2` 之间未改动。
- 事故期间无法用官方通道推进 ⇒ 启用**备用通道**：镜像由 CI 已产出的同一 commit 制品提供，
  部署动作由仓库自带脚本执行（与官方流水线调用的是**同一个脚本**）。

## 三、备用通道的准备（与官方清单逐条对齐）

1. **部署包**：按 `scripts/build_deploy_bundle.sh` 的同一份清单，从 git tag `v7.19.2`
   的对象直接构建（25 个文件），并在服务器端**逐条比对文件清单**后解包。
   - 踩坑记录：第一版打包把 `deploy_remote_production.sh` 放到了包内 `scripts/` 下，
     而官方脚本是放在**包根目录**；若不修正，服务器上会继续用**旧版**发版脚本
     （49484 字节，无备份守卫、无 fail-closed）。已修正并以 `wc -c` + 特征串双重校验。
   - 踩坑记录：`config/` 只取**顶层** `config/*.yaml|*.py`（官方脚本不递归）。
     首版误把 `config/collectors/**` 等子目录扁平化塞进包内，若 compose 挂载 `./config`
     就会污染容器的 `/app/config`。已用发版前备份把 config 目录**精确还原**（23 文件 / 7 目录，
     与备份基线一致），再解官方包。
2. **镜像**：CI 已产出 `ghcr.io/timberdayz/timber_dayz/{backend,frontend}:sha-387d640`
   （`org.opencontainers.image.revision` = `387d64075d5f…`，与 tag 指向的 commit **完全一致**）。
   服务器从 GHCR 拉取该制品后打上 `v7.19.2` 标签，并推送到 CNB 主分发通道：
   `docker.cnb.cool/timberdayz/xihong_erp/{backend,frontend}:v7.19.2`（**推送成功**）。
   - GHCR 上 `v7.19.2` 标签推送被拒（服务器凭据无 `write:packages`），不影响部署：
     发版脚本以 CNB 为主源、GHCR 为兜底，且本地已有同名标签。
3. **陈旧前端源码**：服务器上残留一份旧 `frontend/` 源码树，会让脚本尝试在服务器本地
   构建前端（缺 node_modules 将直接阻断发版）。已移至 `frontend_stale_20261110_025258/`，
   使脚本走"无前端源码 ⇒ 使用 CI 预构建镜像"这条与官方服务器侧一致的路径。

（该问题已由同伴在 `scripts/deploy_remote_production.sh` 中以 "Phase 0.9" 形式修复，本文件不重复其改动。）
