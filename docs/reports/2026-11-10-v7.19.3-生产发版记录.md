## 二、为什么这 4 个 commit 值得单独发一次

1. **Phase 0.9 是发版链自身的修复**。v7.19.2 的官方流水线挂在 Phase 1：
   `Conflict. The container name "/c4d00738453d_xihong_erp_postgres" is already in use`。
   根因：docker compose v2 在 recreate 时把旧容器改名成 `<12位哈希>_原名`，
   部署若在「改名 → 创建新容器」之间中断就留下残骸；而**哈希由容器配置决定**
   ⇒ 每次 rename 的目标名相同 ⇒ **不清理就会一直失败**（不是偶发）。
   Phase 0.9 只删**已停止**的残骸（Exited / Created / Dead），running 的只报告不删，
   并先打印现场；守护测试 `test_remote_deploy_script_removes_only_stopped_recreate_leftovers`
   断言三条边界不被改坏。
2. **迁移失败可诊断**。`scripts/run_current_schema_migrations.py` 以前不捕获 alembic
   子进程输出，失败只报 `current-schema alembic upgrade head failed (1)`，
   真实原因（PG 报错 / 迁移的前置检查失败）只留在子进程 stderr 里。现在失败原因
   会带进异常消息（部署日志不丢，成功时 stdout 照常转发）。
3. **迁移契约测试从「假红」变成真信号**。以前 6 个用例失败且报错被 GBK 吞成
   `AssertionError: None`；补上 `20261116` 要求的数据前置后 5 个转绿，
   剩下 1 个暴露的是**真实缺陷**（见第五节）。

### 8.2 SSOT 是否真的落到生产对象上（读生产 `pg_get_viewdef`，不是读仓库文件）

`semantic.fact_inventory_snapshot` 的线上视图定义里逐条命中：

- `WHEN semantic.is_collection_source_identifier(lower(COALESCE(NULLIF(TRIM(BOTH FROM COALESCE(raw_inventory.shop_id,'')),''), NULLIF(TRIM(BOTH FROM COALESCE(raw_inventory.raw_data->>'shop_id',''),''),''),''))) THEN 'unknown'`
  ⇒ 采集方代号走**唯一执行点**（语义层函数），命中即置 `unknown`；`ELSE` 分支才取真实标识。
- `COALESCE(mapped.warehouse_code, semantic.resolve_warehouse_code(mapped.warehouse_name)) AS warehouse_code`
  ⇒ 仓码归一走**唯一实现** `semantic.resolve_warehouse_code`。
- `FROM semantic.resolve_shop_identity(d.platform_code, d.identity_candidates, NULL) ... LATERAL ... ON true`
  ⇒ 身份解析入口统一走语义层函数。

三个 SSOT 函数在生产 `semantic` schema 均存在：`resolve_warehouse_code`、`is_collection_source_identifier`、`resolve_shop_identity`。
