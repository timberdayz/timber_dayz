# 一页简报：连接泄漏根治与 v7.19.4 上线

> 日期：2026-11-10｜读者：业务负责人 / 管理层
> 一句话：**系统原本每天都在悄悄"漏"数据库连接，迟早整个卡死；11 月 10 日我们把这个定时炸弹拆掉并发了上线，同时把"全新环境建不起来""老库升不上去""测试目录悄悄腐烂"这三个一直卡着的坑，一起填平了。**

---

## 一、原本的五个问题

**1）一根"越用越少"的管子（最要命）**
每来一个业务请求，数据库就少一个可用连接，而且**不归还**。实测每分钟漏 2~8 个，
总共只有 80 个槽位。当天实测已经用到 73/80，日志里出现过 **88 次"连接不够用"**。
后果：高峰期页面打不开、报表拉不出来、系统整体变慢甚至瘫掉。

**2）采集来的数据在"静静消失"**
采集平台同步进来的数据，入库时被当成"这不是一家店"而被丢掉。
库存表 4111 行全部挂在同一个假店铺名下 —— 数字对不上，而且**查不出是谁丢的**。

**3）发版流程本身有"必然失败"的坑**
部署时如果上次中途断过，服务器会留下一个"半成品容器"占着名字，
**下一次发版百分之百失败**。

**4）两条"必经之路"都走不通**
- **全新环境从零建库**：迁移链条走到一半会要求"6 个 TikTok 出口账号必须已经存在"，
  而全新环境里它们**恰恰不存在** ⇒ 新环境**根本建不起来**；
- **老库升级**：旧版运营目标下的历史行被系统锁成只读，新版本的升级脚本偏偏要改它们
  ⇒ 撞车抛错、**老库升级必然失败**。

**5）测试目录在"悄悄腐烂"**
有两批测试用例长期**没人跑**，所以它们跟代码口径不一致时不会变红，只会一直烂在那里。
2026-11-10 实测：根目录测试里有 **33 条过期红**潜伏着。

---

## 二、我们做了什么、结果如何

| 事项 | 做法（业务语言） | 结果 |
|---|---|---|
| 连接泄漏 | 不再"借了不还"，用完立即归还；不同运行场景各用各的连接池，不再互相踩 | **已上线**：连接数连续采样 **18 → 18 → 19 → 19 → 19 → 19 → 19**，稳定后不再涨；最老连接只随开机时长自然增长，没有堆积 |
| 先止血 | 修复上线前，先把"同时可用连接数"从 80 提到 200（并相应调低单连接内存，保证不撑爆服务器） | 争取到发布窗口，**未再出现连接耗尽** |
| 采集数据丢弃 | 把"哪些算店铺、哪些只是采集账号"收成**一份唯一名单**；库存与报表的仓库编号也统一到一个算法 | 4111 行如实标为"未归属店铺"（不再冒充一家店）；仓库编号覆盖 **100%**（1232/1232） |
| 发版流程 | 加了"自愈"步骤：部署前自动清理上次中断的残骸，**只清已停止的，正在跑的一律不动** | 官方发版流水线全绿，事后零残骸 |
| 全新环境能建 | 补齐"从零建库"的两段式操作手册与账号清单，并把**空库从零建库的全链演练**做成流水线里的常驻检查 | 已在**全新空库上实测跑通全链**，且每次发版都会自动再跑一遍 |
| 老库能升 | 按产品定的口径：**这批历史行本来就不该被改** ⇒ 升级脚本遇到它们时**跳过并把跳过条数写进日志**（不偷偷跳过、不改历史数据） | 老库升级从"必然失败"变成"走得通"，且**历史数据零改动** |
| 顺手拆雷 | 发现"新脚本不进镜像"会让**下一次发版在生产直接崩**，已补齐并加了防复发检查 | 镜像构建通过，问题消除 |
| 测试不再腐烂 | 把那 33 条过期红清到 **0**，并把两个"没人跑的目录"接进**每次发版都会跑的常规检查** | 口径漂移以后会在流水线里当场变红，不再潜伏 |
| 清掉误导人的清单 | 组件清单里残留 3 个"文件其实早就不存在"的条目（会让人以为某平台有订单导出入口） | 已清理，并加检查：清单里的文件必须真实存在于磁盘上 |

## 三、现在的状态（全部实测，不是推测）

- 线上版本 **v7.19.4**，7 个服务**全部健康**；健康接口显示 `ready` / 生产模式 / 数据库已连接
- **本次升级对生产数据零改动**：升级前后数据库版本号完全一样 ⇒ **没有跑任何数据迁移**
- 数据库连接 **19 个且稳定不涨**；最近 1 小时：连接耗尽 **0**、程序报错 **0**、页面 5xx **0**
- 数据核对：库存 4111 行、状态 1232 行的仓库编号 **100% 有值**；候选店铺名单与"采集账号名单"**零重叠**
- 部署现场干净：残留容器 **0**
- 代码库与两个镜像仓库**同一版本**，自动检查全部通过

**过程中的一个小插曲（已解决）**：推发布标签时 GitHub 主站的 git 端口不通，
我们改走该平台官方提供的备用加密通道把标签推上去，**发布动作仍然由官方流水线自动完成**
（不是在服务器上手工部署）。生产零事故、无数据丢失。
