# 老库升级路径：只读触发器与回填迁移冲突 —— 口径决策材料

> 面向对象：产品负责人（口径拍板）+ 研发（实现）
> 状态：**未决**。本文只给证据、选项与代价，不含实现，也不改任何仓库代码。
> 生产影响：**实测为 0**（见 §3），不阻塞线上，不阻塞发版。

## 0. 一句话问题

一个**从老库升级**、且库里**带 legacy operation 型父目标历史行**的库，
在迁移链走到 `current_schema_20261215_migrate_sales_targets_a` 时会被数据库拒绝：
只读触发器说"这些行不许改"，而这条迁移正要改它们。

**需要产品回答的业务问题只有一个**：

> 那些没有 `metric_catalog_version` 的 **operation 型父目标**下的历史档位行，
> **到底该不该被补上 `period_label` / `period_start` / `period_end`？**

答案不同，实现路径（A/B/C）就不同。见 §5。

## 1. 冲突的两方（代码事实）

### 1.1 只读触发器

- 建表迁移：`current_migrations/versions/20260808_operation_performance_workbench.py:216`（首次创建）
- 重建迁移：`current_migrations/versions/20260810_operation_contract_isolation.py:176`（当前形态）
- 触发器函数：`a_class.enforce_operation_breakdown_contract()`，作用于 `a_class.target_breakdown`
- 封锁条件（`20260810_operation_contract_isolation.py:186-189`）：

  ```sql
  IF FOUND AND parent_target.target_type = 'operation' THEN
      IF parent_target.metric_catalog_version IS NULL THEN
          RAISE EXCEPTION 'historical operation breakdowns are read-only';
  ```

  即：**只有**当父目标 `target_type = 'operation'` **且** `metric_catalog_version IS NULL` 时才封锁
  INSERT / UPDATE / DELETE；其余情况按契约版本一致性校验。

- 设计意图（见 `20260914_warehouse_platform_profit.py:3` 同族说明）：历史 operation 目标是
  **不可变快照**，只允许读，不允许改。

### 1.2 回填迁移

- `current_migrations/versions/20261215_migrate_sales_targets_a.py:365-374`
- 行为：把 `a_class.target_breakdown` 中
  **`breakdown_type = 'shop'` 且 `period_label IS NULL`** 的历史行补上
  `period_label` / `period_start` / `period_end`（规范化，2025-07~09 的历史行）
- 谓词里**没有 `target_type` 过滤** ⇒ 只要这些行的父目标是 operation 型且缺版本，
  这次 UPDATE 就会被 §1.1 的触发器拒绝。

## 2. 为什么不能用"加一个前向迁移"来解（顺序事实）

链上共 **86 个修订**（用 alembic 自己算，非手工解析 `down_revision`）：

| 修订 | 链位（0 = 最新/最后执行） | 由旧到新第几步执行 |
|---|---|---|
| `current_schema_20261223_collection_source_identifiers`（head） | 0 | 86 |
| **`current_schema_20261215_migrate_sales_targets_a`** | **8** | **78** |
| `current_schema_20261116_add_tiktok_export_store_name_aliases` | 37 | 49 |
| **`current_schema_20260810_operation_contract_isolation`（触发器）** | **83** | **3** |

⇒ 触发器比 `20261215` **早 75 个修订**就建好了。

在一条老库升级链上，alembic 的执行顺序是：
`20260808` 建函数 → `20260810` 建触发器 → … → `20261215` 执行那段 UPDATE（触发器已生效）→ **抛错、链断**。

**因此：任何加在 `20261215` 之后的前向迁移，在这个场景下永远执行不到。**
前向迁移只能修"已经过了 20261215 的库"（未来防护），修不了"正要过 20261215 的库"（老库解堵）。
这两件事必须当成两个范围来立项，不能混成一项。

| `a_class.target_breakdown` 总行数 | 241 |

| 隔离区 `core.data_quarantine` | 9 行（与"9 行进隔离区、金额合计 990429.2"口径一致，**不是丢失**） |

⇒ 触发器在生产**当前覆盖 0 行**；`20261215` 在生产**没有任何受阻对象**。
风险不落在生产。

### 3.1 全新库不受这条影响（与"空库建不起来"是两件事）

全新库上 `20261215` 的 UPDATE 目标集为空（没有历史行）⇒ 压根不触发写 ⇒ 不冲突。
**全新库的真实阻塞是另一个点**：`current_schema_20261116_add_tiktok_export_store_name_aliases`
的 fail-closed 数据前置检查（要求 6 个 TikTok 出口账号已登记）。
两者**互不相干**，请勿合并成一个立项。

## 4. 现状：这条缺陷被有意保留为"真红"

- 缺陷探测器：`test_legacy_adoption_preserves_duplicate_operation_shop_overrides_and_audits_them`
- 它的造数**已经与触发器条件一一对应**：
  父目标 `target_type='operation'` 且 `metric_catalog_version` 未指定（NULL）
  ⇒ 用例失败是**正确暴露**冲突，不是环境问题。
- 仓库用"失败集 diff"而不是"全绿"做门禁，所以这条用例继续当探测器；
  **没有**加 `xfail` 掩盖，也**没有**把造数改成 shop 型（那会让它变绿但丢掉探测点）。

## 5. 三个可选路径与各自代价

| 方案 | 做法 | 对"老库升级"是否有效 | 代价 / 约束 |
|---|---|---|---|
| **A** | 改 `20261215` 本身：在那段 UPDATE 前后 `ALTER TABLE a_class.target_breakdown DISABLE TRIGGER trg_enforce_operation_breakdown_contract;` … 完成后 `ENABLE` | **有效** | 触碰"已应用迁移不可变"条款（`20260914_warehouse_platform_profit.py:3`）⇒ 需走显式豁免 + 记录理由；只影响**尚未应用过 20261215 的库** |
| **B** | 改 `20260808` / `20260810` 的触发器函数：放行"仅补 `period_label`/`period_start`/`period_end` 的规范化写" | **无效** | 老库早已应用过这两个修订，alembic **不会重跑** ⇒ 只影响全新库；而全新库本就没有脏行可改。**此路对老库是空操作** |
| **C** | 不改任何已应用迁移：把"老库升级前的解锁步骤"写进 DR 手册 / 升级前置脚本 | **有效** | 增加一个运维前置步骤（人工或脚本化）；升级窗口内需要额外操作 |
| **D** | 前向 `ALTER FUNCTION` 迁移，调整触发器语义 | 对**已经 ≥20261215 的库**有效（未来防护） | **对老库解堵无效**（见 §2）⇒ 是另一个范围 |

> 注：A 与 B 都要触碰"已应用迁移不可变"的条款；C 是唯一不改历史迁移的解法，但把成本挪到了运维流程。

## 6. 建议（供拍板参考，不代替拍板）

- 研发倾向 **「把回填限制在有版本的父目标上」**（即只在父目标 `metric_catalog_version IS NOT NULL`
  的范围内做规范化），理由：对历史不可变数据**零副作用**，且不需要豁免不可变条款。
  代价是需要把"跳过"这件事显式记进迁移日志，否则会被误读成"数据漏改"。
- 但这条是否**符合业务期望**，只有产品能定：那些 operation 型历史行**本来就不该被改**吗？
  如果"本来就不该被改"，那更简单的解法是——**让迁移显式跳过并记日志**（而不是去解锁触发器），
  实现成本最低、语义最干净。
- 若产品的答案是"**应该被改**"，那才需要走 A（显式豁免不可变条款）或 C（运维前置步骤）。

## 7. 需要产品回复的三个问题

1. 无 `metric_catalog_version` 的 operation 型父目标下的历史档位行，
   **该不该**被补 `period_label` / `period_start` / `period_end`？（决定要不要动触发器）
2. 若**不该被改**：期望迁移的行为是"跳过并记日志"，还是"报错让人来看"？
   （决定 A/C 之外的第四条路是否成立）
3. 这些历史行当前在业务上还有没有读取方？
   若无人读取，也可以直接把这条规范化从迁移里去掉（同样是触碰已应用迁移，需豁免）。
