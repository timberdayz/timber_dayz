## 0. 一句话结论

**账没算错，"人"的状态口径散了。** 真正的风险不在"离职员工还显示在列表里"（那是观感），而在于：

1. **生产上的 HR 算账链路本身是断的** —— 人员店铺归属表、人力成本分摊表在生产都是 **0 行**，而工资单确认的前置校验强制要求人力成本分摊存在，所以生产上 31 张工资单里有 23 张卡在 `draft`（2026-06 / 07 各已发放 4 / 3 张，说明这条链路曾经通过，是后来数据被清空才断的）。
2. **"离职"被当成一个开关用，而不是一个结算边界** —— 既会漏发（离职后仍可能被生成工资单），也会误伤（离职当月的加班费/奖金录不进去）。
3. **访客身份是死胡同** —— 生产里已经存在 1 条访客档案（梁曦予），她永远无法进入薪资与收入链路。
4. **两名在职新员工入职至今零工资记录** —— 曾维剑（2026-08-26 入职）、文鹏（2026-11-08 入职）工资单/提成/绩效/手工录入四项全空；生产工资单只覆盖到 2026-07，**2026-08 之后的月份从未被结算过**。
5. **试用期在系统里根本不存在** —— 业务口径明确「试用不发薪」，代码行为也一致，但没人真用过 `probation` 这个值：曾维剑、文鹏在库里都是 `active`。于是系统分不清"试用"与"正式"，也无法在转正时补齐试用期工资。
6. **部门没有真源，只有两个各存一半的碎片** —— 员工档案侧 2/11 有值（结构化外键 → 树形部门表），账号侧 5/12 有值（自由文本，且后端**只写不读**）。两边拼不出完整的组织归属。

## 3. 目标业务规则（唯一口径）

### 3.1 员工状态词表（后端加约束，前端单一来源）

| 取值 | 中文 | 含义 | 可发工资 | 可进薪资页 | 可进"我的收入" |
|---|---|---|---|---|---|
| `active` | 在职 | 正常在职 | ✅ | ✅ | ✅ |
| `probation` | 试用期 | 在职但未转正，**不发薪**（2026-11-20 业务确认） | ❌ | ❌ | ✅（只读） |
| `leave` | 停薪留职 | 在职但不发薪 | ❌ | ❌ | ✅（只读） |
| `inactive` | 已离职 | 离职 | **仅限最后发薪月及之前** | 只读 | ✅（只读历史） |

> 词表只有这 4 个值，与数据库 CHECK 约束一致。**「删除」不是第五个状态** —— 它是「办理离职」的历史入口，同样落到 `inactive`。

- 数据库层：`a_class.employees.status` 加 `CHECK` 约束
- Pydantic 层：`EmployeeCreate` / `EmployeeUpdate` 的 `status` 加 `Literal` 或 `pattern`
- 前端层：新建 `frontend/src/constants/hr.js`，导出 `EMPLOYEE_STATUS` / `employeeStatusLabel()` / `employeeStatusTagType()`，所有页面统一引用

### 3.2 离职三要素（替代"删除"）

一个员工从"在职"变成"已离职"，必须同时确定三件事：

1. **离职日期**（`leave_date`）—— 他是哪天走的
2. **最后发薪月**（`last_payroll_month`，新增字段）—— 他最后拿工资的月份（YYYY-MM）
3. **离职原因**（新增字段 `leave_reason`，选填）—— 为什么走

### 3.3 最后发薪月语义（核心）

> **所有"能不能发钱"的判断，一律以 `last_payroll_month` 为准，不再以 `status` 为准。**

- `year_month <= last_payroll_month` → **允许**录入、确认、发放（离职结算必须能做）
- `year_month > last_payroll_month` → **禁止**新增任何归属/绩效/提成/工资单；历史记录只读
- 在职员工：`last_payroll_month` 为空 → 视为"无上限"（现状行为不变，零误伤）

这条规则一次性解决两个方向的问题：既不漏发（离职后不会被生成新工资单），也不误伤（离职当月该发的照发、照录、照确认）。

`status` 退回到它该管的事：**只表达"在不在职"这个展示事实**。

### 3.4 账号身份三态（与员工身份解耦）

| 概念 | 字段 | 含义 |
|---|---|---|
| 登录身份 | `core.dim_users.status` | `pending` 待审批 / `active` 启用 / `suspended` 停用 / `deleted` 已删除 / `rejected` 已驳回 |
| 用工身份 | `a_class.employees.employee_identity_type` | `visitor` 访客（只有账号，没有确认的用工身份）/ `employee` 正式员工 |
| 在职状态 | `a_class.employees.status` | 在职 / 试用期 / 停薪留职 / 已离职 |

**关键规则**：登录身份**只管"能不能进系统"**，用工身份**只管"能不能进人力链路"**，在职状态**只管"算不算在职人数"**。三者不再互相兼职。

### 3.5 试用期与转正（2026-11-20 业务确认后新增）

**业务口径**：试用期员工**不参与发薪**（沿用现状代码行为），但**可参与考核**；转正后从转正月份起进入工资单链路。

**现状缺口**：试用期这个状态在系统里形同虚设 —— 业务上是试用员工，库里却是 `active`；且**没有「转正」这个动作**，所以试用期段的工资永远补不回来。

**落地口径**：

| 动作 | 触发 | 效果 |
|---|---|---|
| **建立员工档案（审批即建档）** | 管理员审批新用户时勾选「同时建立员工档案」 | 新档案 `status='probation'`（试用），可传 `employee_status='active'` 直接转正 |
| **转正** `POST /api/hr/employees/{code}/regularize` | 试用期结束 | `probation → active`，写 `regularization_date`；**并一次性补齐试用期至转正月之间应发未发的工资单** |

> 「补齐试用期工资」的具体算法（按转正月补、还是按试用期各月补）属于月度刷新链路的既有能力，本方案**只负责把状态与转正动作打通**，不新增工资计算口径。

### 3.6 「已作废」是第四个工资单状态（2026-11-20 业务确认后新增）

**业务口径**：李四 EMP260004 的 4 张工资单（2026-03/04/06/07）是**测试数据**。但系统里没有「作废」这个动作 —— 要么留着等被误发，要么直接删行（丢审计）。

**落地口径**：工资单状态机从三态扩为四态 —— `draft` 草稿 / `confirmed` 已确认 / `paid` 已发放 / **`void` 已作废**。

- 作废**保留行、保留审计、记录原因与操作人**（`void_reason` / `voided_at` / `voided_by`）
- **不可确认、不可标记已发放、不可编辑**
- 不参与任何金额汇总（确认工资单的前置校验、人力成本分摊取数都要跳过 `void`）

### 3.7 部门与职位的唯一真源（2026-11-20 业务确认后新增）

**业务侧结论**：部门信息必须统一 SSOT 标准。

**现状**：两个来源各存一半，且形态不同 —— 员工档案侧 `department_id`（外键 → 树形部门表）仅 2/11 有值；账号侧 `dim_users.department`（**自由文本**）5/12 有值，**且后端只写不读**（注册时写入、待审批列表展示，此外无任何业务逻辑读它）。

**落地口径**：

| 结论 | 理由 |
|---|---|
| **组织归属唯一真源 = `a_class.employees.department_id` → `a_class.departments`** | 结构化、可树形、能算「某部下有多少人」，是考核与归属划分唯一能用的维度 |
| 账号侧 `dim_users.department` **降级为「注册时填写的部门」**，不参与任何业务判断 | 后端本就只写不读；人是自由文本字段的载体，人会调岗而账号不会 ⇒ 自由文本必成过期快照 |
| 注册表单该字段**保留但改名标注**「仅供 HR 识别，不影响组织归属」 | 不改 `dim_users` 表结构 ⇒ 零迁移风险；只改语义与文案 |
| 存量值**人工确认后回填**到员工档案 | 自由文本对不上部门表编码，不自动回填 |

**实施影响**：员工列表的「部门」列一律读档案侧真值（现有 `getDepartmentName(row.department_id)` 已如此，**保持**）；账号管理页只展示「注册时填写的部门」作为参考信息。

## 4. 访客升级为正式员工（专项设计）

### 4.1 先定义清楚：访客不是员工

**访客 = 有系统账号、但用工身份尚未被管理员确认的人。**

因此当前"访客档案"在员工管理列表里占一行，本身就是错的 —— 它不是员工，它是账号的副产品。所以：

> **员工管理列表默认只显示 `employee_identity_type = 'employee'` 的档案；访客档案单独归入一个"待转正访客"分组（或独立标签页），不混在员工里。**

这一步同时解决了你截图里"员工列表混着不该出现的人"的问题。

### 4.2 三层解法（主路径 + 存量修复 + 防漏）

#### 方案 A（主路径，推荐，覆盖未来所有新员工）：**审批即建档**

把"建立用工身份"这件事，从"员工自己打开档案页时被动发生"挪到"管理员审批通过时主动发生"。

- 审批弹窗（`UserApproval.vue`）在选角色之外，增加一个区块：**用工信息**，含 `是否建立员工档案`（默认勾选）、部门、职位、入职日期
- `POST /api/users/{user_id}/approve` 增加可选负载：`create_employee: bool` + `department_id` / `position_id` / `hire_date`
- 审批通过时**在同一个事务里**原子完成四件事：
  1. 账号 `status → active`
  2. 建立员工档案（`employee_identity_type='employee'`, `status='active'`, `user_id=当前账号`）
  3. 写入入职日期
  4. 记审批日志
- 事务失败则整体回滚，**绝不出现"账号批了但档案没建"或反过来**

**效果**：新员工入职第一天就是正式员工，"我的档案"直接可用，薪资与收入链路自动打通。访客路径从此只在"用户不等审批就自己打开了档案页"这个边缘场景保留。

> ⚠️ 注意：管理员目前是**先建员工再绑定**（先在人力管理建档案，再到用户管理关联）。方案 A 让这个顺序**反过来** —— 审批时一次建完并绑定。两种顺序并存不冲突，但**方案 A 落地后，旧的"先建后绑"路径应该只在补录存量时使用**，否则会造出重复档案。UI 上需要明示推荐路径。

#### 方案 B（存量修复，覆盖已存在的访客档案）：**显式转正入口 + 冲突合并**

给访客档案一个明确的转正动作，而不是让管理员去猜。

**B-1 独立转正按钮**
- 员工管理页的访客分组里，每条访客档案有「转为正式员工」按钮
- 点击后弹出表单：部门、职位、入职日期、身份类型（默认 `employee`）
- 提交后：把 `employee_identity_type` 从 `visitor` 改为 `employee`，写入 `hire_date`

**B-2 绑定冲突时的"合并"选项**
- 管理员在编辑某条员工档案、选择一个已被占用的账号时，当前后端直接 409「该登录账号已关联其他员工」
- 改为：返回明确信息 **"该账号已关联访客档案 EMP260009（梁曦予，访客，2026-08-04 创建）"**，并在前端给出两个明确选项：
  - **合并到当前员工**（推荐）：把访客档案上的联系方式（手机/邮箱/地址/紧急联系人）搬到当前员工档案，删除访客档案，账号绑定到当前员工
  - **仅改绑**：解除访客档案的账号关联，把账号绑到当前员工；访客档案保留为无账号孤儿，后续由"待转正访客"分组统一处理
- 后端新增一个专用端点 `POST /api/hr/employees/{code}/merge-visitor`，保证合并是**一个事务**，不走通用 update 的 `setattr` 循环

**B-3 生产存量**：梁曦予 EMP260009 走 B-1 转正（补齐部门/职位/入职日期），她已有的账号 `18976425991` 保持绑定关系不变。

#### 方案 C（防漏机制）：**档案填全自动升级**

- 当一条 `visitor` 档案被管理员补齐了**部门 + 职位 + 入职日期**三项，且身份仍为 `visitor` 时，系统在保存时**自动**把身份升为 `employee`，并写一条转换日志
- 这样即使管理员忘了点"转正"，只要档案填全了，身份自然跟上
- 降级保护：自动升级**只在三项齐全时触发**，不齐全则保持 `visitor` 并在列表里高亮提示"档案信息不全，无法转正"

#### 4.3 完整的新用户生命周期（方案 A + B + C 落地后）

```
用户注册
   ↓ 账号 status=pending
管理员审批（待审批列表）
   ↓ 通过时：原子完成「激活账号 + 建员工档案 + 绑定 + 写入职日期」
   ↓ 拒绝时：账号 status=rejected，可重新注册
正式员工（identity=employee, status=active）
   ├─ 可进薪资页、可看"我的收入"、可拿工资单
   ├─ 调岗/转正：改 status（active ↔ probation）
   └─ 离职：办理离职 → status=inactive + leave_date + last_payroll_month

【边缘路径】用户在审批前就打开"我的档案"
   ↓ 自动建访客档案（identity=visitor）
   ↓ 管理员在"待转正访客"分组里处理：
      ├─ 方案 B-1 转正 → 变正式员工
      ├─ 方案 B-2 合并到某条正式员工档案
      └─ 保持访客（外部/合作方账号，不进人力链路）
```

## 10. 集成期补齐的两处口径（2026-11-20）

前四批落地后，集成复跑发现两处**方案里没写、但必须定**的口径。它们都不是新需求，
而是「把作废这个状态真正做完整」时暴露出来的连带问题。

### 10.1 「已作废」必须**可撤销**

**问题**：`a_class.payroll_records` 上有 `(employee_code, year_month)` **唯一索引**
⇒ 一人一个月只有一张工资单 ⇒ **作废单占着坑位**。若作废不可逆，误作废一次，
那个人那个月就**永远发不出钱**（建不出第二张有效工资单），而界面只显示「已作废」，
用户完全不知道这里是个死胡同。

**定案**：

- 新增「撤销作废」端点（`POST /api/hr/payroll-records/{record_id}/unvoid`），
  把作废单恢复成**草稿**，清空作废留痕，审计日志保留「作废 + 撤销作废」两条痕迹；
- 薪资页配对提供「作废工资单」与「撤销作废」两个入口，作废必须填原因；
- 守卫：撤销作废后，这张单重新走「确认 / 发放」，与普通草稿无差别。

**配套**：月度人工录入遇到已作废单时直接 409 并提示「请先撤销作废」——
否则用户录了一堆数，最后发现根本落不到任何有效工资单上。

### 10.2 作废**不锁月**，且作废单**不被刷新改写**

**问题**：刷新工资单的逻辑原本只有两种分支 —— 「已锁定就跳过」或「直接改写」。
作废单两个都不属于：它不是锁定态，所以会被**原地改写金额**（一张本该冻结的历史留痕
被静默改了数）；而它又占着坑位，所以也建不出替代单 ⇒ 该员工该月就此空缺。

**定案**：

- 作废单在刷新时被**单独识别并跳过**，既不改写金额，也不新建替代单；
- 单独回报「作废冲突」清单（`void_conflicts` / `void_conflict_details`），
  前端明确提示「这些单已作废、本次未生成、如需补发请先撤销作废」；
- ⚠️ **作废绝不能进「锁定集合」** —— 一旦进去，一张作废单就会把**整个月**钉死
  （同月其他人的工资单再也重算不了）。锁定集合 = 已确认 / 已发放。

### 10.3 顺带澄清：「已锁定」集合里的历史遗留值

锁定集合保留了一个历史遗留值 `approved`（老版本工资单路由写过它）。现网代码已不再写入，
但**仍按锁定处理** —— 宁可多锁，不可漏锁：漏掉它会让某个环境残留的历史工资单被整月重算
**静默改掉**（2026-11-05 那次「界面显示已锁定、后台却允许整月重算」事故的同款后果）。
它同时留在工资单词表里（只读展示），前端 `constants/hr.js` 与后端词表**逐值一致**。
