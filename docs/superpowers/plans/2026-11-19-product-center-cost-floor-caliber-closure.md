### 0.2 要解决的事（按严重度）

1. **底线链漏算三块真实成本** —— 头程、仓储、贴单费。规则表里全有（SG-01 头程 380 元/CBM、仓储 5.27 元/CBM/月、贴单 1.00 元/件），但**底线公式一项都没算** ⇒ 底线系统性偏低 ⇒ 定价偏低。
2. **底线链与利润链两套口径** —— 同一 SKU、同一价位，利润链说利润率 45.06%，同口径真相 18.28%，**差 26.78 个百分点**（正好等于桶里"佣金以外"的部分）⇒ 护栏拿着偏松的底线放行本该拦住的品。
3. **平台佣金率填了不生效** —— `product_pricing_service.py:5` 明写"平台佣金率已包含在 other_cost_rate 内，不得单独进入分母"，所以运营在界面上填的佣金率**根本没进计算**。同时桶里的佣金还是 1 月实测旧值（Shopee 14.87% / TikTok 7.37%），而平台佣金率已按官方牌价校准（16% / 8.175%）⇒ 桶偏小 ⇒ 底线偏低约 1.1pt。
4. **尾程的"成对生效"机制让尾程根本进不了底线** —— 生产 `delivery_cost_rate` **全 NULL** ⇒ 尾程不进底线；而桶里又摊着运费 ⇒ 口径既保守又不可解释。
5. **界面术语混用** —— "物流"在商品中心界面里同时指**头程**、**货损**、**运输方式**三件事。

### 0.3 分阶段

| 阶段 | 内容 | 前置 | 可否立即做 |
|---|---|---|---|
| **P1** | 拆佣金 + 桶换口径 + 尾程进分子 + **SPU 两率折进成本** + 底线/利润同源 + **护栏收口（带仓底线）** + 前端术语 + 修空白显示 | 桶新值人工确认 | **可** |
| **P2** | 头程/仓储/贴单进底线分子 | **需 SKU 体积**（1122 个只有 18 个有） | **降级做**（2026-11-19 实施）：缺体积 ⇒ 该项**未计入**但仍出底线 + 显式标注 `missing_unit_volume` |
| **P3** | 两率的**实测标定**（按品类/平台区分）+ 尾程段单列 | **需退货/物流明细数据** | 否 |

**P2 为什么能降级做**（与拍板 #7「等数据」不冲突）：P2 的前置是「体积」，
但**缺体积不等于「这条成本不存在」**。若按「缺失即留白」处理，
1104 个 SKU 会直接失去底线 ⇒ 把「数据没录」变成「系统不管」，
比「底线偏松」严重得多。⇒ 取**逐步补齐型**缺料纪律：
该项**未计入**（不是 0 成本），但**仍然出底线**，并在界面**显式标注未计入**。
体积录齐后，不用改任何代码，自动就完整了。

**取消项**（原方案的 P0 影子计算、§6 桶重算 8 条口径、`scripts/recompute_platform_cost_rates.py`）——
按拍板 #1，**不搞自动重算**，桶由人工维护。数字由人拍，不靠脚本算。

## 1. 诊断（带实测证据）

### 1.1 底线链比利润链少算三块成本

利润链的成本项清单（`backend/services/product_profit_service.py:331-341`）：

```
purchase, logistics, storage, label_fee, delivery,      # 按件
platform_fee, creator_commission, return_loss, damage_loss
```

底线链的成本项清单（`backend/services/product_pricing_service.py:64-89`）：

```
分子 = purchase_cost + delivery_cost(且要"成对生效")
分母 = 1 − other_cost_rate + delivery_cost_rate − creator − 退货率 − 货损率 − 目标利润率
```

**头程 / 仓储 / 贴单费在底线链里根本不存在**。

生产实测（规则都在，只是底线不读）：

| 项 | 表 | 生产实况 |
|---|---|---|
| 头程 | `finance.logistics_provider_rules` | 6 行 active，SG-01 极迈物流 380 元/CBM（volume 计价，normal，默认行）；MY-01 620/660；PH-01-CHILD 850/950 |
| 仓储 | `finance.warehouse_storage_rules` | 3 仓：SG-01 5.27、MY-01 2.0、PH-01-CHILD 2.0 元/CBM/月 |
| 贴单费 | 同表 `label_fee` | 3 仓均为 1.00 元/件 |

⇒ 底线**每件少算**（SKU 920 验算）：头程 7.60 + 仓储 0.21 + 贴单 1.00 = **8.81 元**。

### 1.2 两条链差 26.78 个百分点

**利润链完全不扣残差桶**（`other_cost_rate` 在 `product_profit_service.py` 里一次都没出现；
全后端非测试用点只有 `product_pricing_service.py`、`product_pricing_query_service.py`、
`price_adjust_notify_service.py`、`product_center.py`）。

SKU 920（Shopee / SG-01 / 不包邮 / 日常档）验算：

| 价位 | 利润链说利润率 | 同口径真相 | 差 |
|---|---|---|---|
| 157.64（现状底线） | **45.06%** | **18.28%** | 26.78% |
| 139（参考售价） | **40.99%** | **14.21%** | 26.78% |
| 202.50（新底线） | **51.78%** | **25.00%** | 26.78% |

差值恒等于 26.78% = 桶 41.65% − 桶里摊的实测佣金 14.87% —— 因为利润链压根没扣它。

**业务后果**：按现价 139 卖，系统告诉运营"利润率 40.99%"，同口径真相 14.21%；扣掉广告就可能直接亏。

### 1.3 平台佣金率填了不生效

`backend/services/product_pricing_service.py:5`（模块 docstring）：

> 平台佣金率已包含在 other_cost_rate 内，不得单独进入分母

`compute_cost_floor` 的入参（`:39-49`）里**根本没有佣金率** —— 前端填的 `default_fee_rate` 到不了公式里。
`product_pricing_query_service.py:411` 传的也只有 `other_cost_rate`。

⇒ 界面上的「平台佣金率」是一个**看起来在生效、实际没生效**的字段。

而桶里的佣金是 1 月实测旧值（Shopee 14.87% / TikTok 7.37%），与官方牌价（16% / 8.175%）已经不一致
⇒ 桶偏小 ⇒ 底线偏低约 1.1pt。台账 `STATUS.md`「当前未结」#10⑦ 已记为欠账。

**桶当初为什么长这样**：2026-10-20 设计时，平台结算单的费用分项**符号约定混乱、加总对不上账**
（设计稿 `2026-10-20-sku-pricing-guardrails-design.md:201` 记录：TikTok 侧按成本加总得 98.75%、
按回冲算得 86.93%，而净利率隐含的总成本率是 82.19%，差 4.74~16.56pp），所以不敢逐项建模，收进一个桶。

**今天实测复现了这个问题**（`semantic.fact_orders_atomic`，2026-01~11）：

| 分项 | shopee | tiktok |
|---|---|---|
| 平台佣金为负的占比 | **0 / 32777（全是正）** | **4508 / 5135（88% 负）** |
| 运费为负的占比 | 28163 / 32777（85%） | 2186 / 4540（48%，**同平台内部也不统一**） |
| 推广费为正 | 7359 / 10699（69%） | 3654 / 3778（97%） |
| 仓库操作费为正 | 21823 / 21826（99.98%） | 3808 / 3841（99%） |

⇒ **同一字段在两个平台符号相反；运费在同一平台内部也不统一；分项互相重叠不可加总**
（shopee 分项加总 46.37% > 反推桶 32.45%）。
⇒ 这正是**不能靠脚本反推、只能人工拍**的技术原因（呼应拍板 #1）。

### 1.4 尾程：现在的机制让它进不了底线

现状（批次 4）：尾程进底线必须"分子加尾程 ⇔ 分母加回 `delivery_cost_rate`"同时有值，
否则同一笔尾程被扣两次（`product_pricing_service.py:73-84`）。

生产 `core.dim_platforms.delivery_cost_rate` **全 NULL**【实测】⇒ 尾程**根本没进底线**；
而桶里又摊着运费 ⇒ 口径既保守又不可解释。

**为什么"成对生效"这个补丁本身有问题**：桶是人工/反推的黑箱，里面那笔运费**拆不出来**，
所以对冲永远无解 —— 要么尾程进不去，要么就得填一个假的拆分比例。**B 路线直接删掉这个机制**。

尾程本身是算得出来的（`product_delivery_cost_service.py:143` `compute_delivery_cost`）：
按「平台×仓」重量段费率取该段单价；SKU 没选重量段 ⇒ 落最轻段、各仓取最大价做保守估值并标 `estimated`。

### 1.6 退货 + 货损：行业基准件损率 → 折进成本

**业务定位（2026-11-19 拍板）**：这两个率是**行业基准的件损率** —— "这个 SPU 在行业主流数据下，
发 100 件里退几件、坏几件"。它是**款式级属性**，SPU 级是正确粒度（不拆到 SKU）。
它要**折成钱计算到产品成本里面去**（进分子），而不是按收入比例扣（现状）。

**① 率存在 SPU 上，不是 SKU 上**

`core.dim_spu` 两个 nullable Float 列【实测 287 个 SPU，286 个两个都填了】：

| 列 | 位置 |
|---|---|
| `logistics_damage_rate`（货损率） | `modules/core/db/schema_parts/dimensions.py:407` |
| `return_loss_rate`（退货率） | `modules/core/db/schema_parts/dimensions.py:408` |

**② SKU 通过桥表找到自己的 SPU**

`core.bridge_spu_sku`（`dimensions.py:604-651`）是带生效区间的人工归属表。
"当前有效"的**唯一**判定条件在 `backend/services/product_spu_binding.py:117-131`
（`binding_status == CURRENT_BINDING_STATUS AND effective_to IS NULL`），
ORM 部分唯一索引 `uq_bridge_spu_sku_current`（`dimensions.py:632-640`）保证一个 SKU 只有一条当前归属。

**绑定是完整性的硬要求**（业务定义："不绑 SPU 就是一个不完整的 SKU"）。
生产实测【实测】：1122 个 SKU 里 1085 个在售、37 个 `inactive`；
**37 个未绑 SPU 的全部是 `inactive` ⇒ 在售 SKU 零缺口**；已绑但两率缺失的 SKU = **0**；
在售 SKU 指向已淘汰（`active=false`）SPU 的 = **0**。
⇒ `missing_spu_binding` / `missing_spu_rates` 是**兜底**，不是日常流程。

**③ 现状（今天线上）两率怎么用 —— 按收入比例**

| 链 | 取数位置 | 公式位置 | 现状用法 |
|---|---|---|---|
| **底线链** | `product_pricing_query_service.py:412-414`（`linked_spu.return_loss_rate` / `linked_spu.logistics_damage_rate`） | `product_pricing_service.py:85-87` | **分母里按收入比例扣**：`1 − … − 退货率 − 货损率 − 目标利润率` |
| **利润链** | `product_finance_service.py:1282-1283`（`return_rate=spu.return_loss_rate` / `damage_rate=spu.logistics_damage_rate`） | `product_profit_service.py:309-318` | **按收入比例扣金额**：`return_loss = revenue × return_rate`、`damage_loss = revenue × damage_rate` |

利润链的 `revenue` = 测算售价（商家实收 = 折后到手价），`product_profit_service.py:277-282`。

**⑦ 新口径（2026-11-19 拍板）：折进成本，不区分头程尾程**

```
分子 = 按件成本合计 × (1 + SPU退货率 + SPU货损率)
分母 = 1 − 平台佣金率 − 平台其他成本率(桶) − 达人佣金率 − 目标利润率
```

**业务话**：这个款行业平均发 100 件要退 6 件、坏 1.5 件 ⇒ 付了 100 件货的钱只卖出 92.5 件
⇒ **每卖 1 件要多摊 1.075 件货的钱**。

**为什么这么算**：
- 现状把 1.5% 当**收入比例**扣 ⇒ 说的是"每卖 100 块收入，有 1.5 块收不回来"；
  而行业基准率说的是"**发 100 件，坏 1.5 件**"—— 那是**成本侧多背**，不是收入侧少收。
- 两件事在**金额上不等价**：SKU 920 上现状口径在 157.64 的底线上扣 **2.36 元/件**，
  按件折只要 **0.899 元/件**（59.93 × 1.5%）。
- **不区分头程尾程**（拍板）："单件货值"直接取**分子里的按件成本合计**，
  问都不用问这批损耗发生在哪一段 ⇒ P2 把头程/仓储/贴单加进分子后，货损期望**自动跟着变大**，
  **口径一次到位、P2 不用返工**。
- 因为两个率都是"件数比例"，分母里就不该再扣它们 ⇒ 分母只剩平台侧三样 + 目标利润率。

**利润链必须同步改**：`return_loss` / `damage_loss` 从"收入 × 率"改成"**按件成本 × 率**"进成本项，
否则底线说利润率 25%、利润链说别的数（§3.5）。

**⑧ SKU 920 验算（生产实测输入 + 真实服务函数）**

输入：采购 39 / 体积 0.02 CBM / SPU 退货 6% 货损 1.5% / shopee 佣金 16% 达人 1.11% 桶 3.58%（新口径，结算单实测）

## 2. 业务概念（新的统一口径）

### 2.1 钱被扣掉的方式只有三类

| 性质 | 判据 | 算式 | 归属 | 本次涉及 |
|---|---|---|---|---|
| **按件扣** | 卖一单就付这么多 | 固定金额/件 | **分子** | 采购、头程、仓储、贴单、尾程 |
| **按比例扣** | 卖越多扣越多，占收入一份 | 售价 × 费率 | **分母** | 平台佣金、平台其它扣款(桶)、达人佣金 |
| **按风险扣** | 会亏，但不是每单都亏 | 件损率 × 按件成本 | **分子**（期望成本） | 退货、货损（**P1 起就折进成本**） |

**一句话口径**：按件的钱进分子，按比例的钱进分母；**风险（退货/货损）折成钱也进分子**
—— 每件按件成本要乘 `(1 + 退货率 + 货损率)`。

### 2.2 运输四段路径（前端放这张图，术语就不会再混）

```
国内工厂 ──【头程】──→ 目的国本地仓 ──【仓储】──→ 出仓 ──【尾程】──→ 买家
          按体积 CBM     按体积 CBM/月  每件贴单费   按重量段
                      ↑
              【头程末端派送】= 港→仓这一段，不是买家快递（批次 5 已改名）
```

不在路径上的（平台侧）：平台佣金、平台其它扣款(桶)、达人佣金（按收入 %）；
退货、货损（行业基准**件损率** ⇒ 折成钱**进成本**：每件按件成本 × `(1 + 退货率 + 货损率)`）。

### 2.3 底线的定义

**底线 = 扣完成本后利润率恰好等于目标利润率的那个售价。**

自洽性检验（最强的一条守护）：**在底线上算利润，利润率必须 = 目标利润率。**
SKU 920 验算：新口径底线 156.58，广告前利润 27.0302（19.45%）；目标 25% × 156.58 = 39.1450
（差异来自底线量化到分，属正常误差）。

### 2.4 「定价设置」是什么（拍板 #1）

**定价设置 = 人工录入的平台成本率表。**

- 每个平台一本账：平台佣金率、默认达人佣金率、平台其他成本率(桶)三个手填项 + 生效日期 + 来源 + 版本。
- 人填、人负责、平台费率政策变了就人改。
- **系统不做自动重算**（不滚动刷新、不影子计算、不从结算单反推）。
- 尾巴上留「底线成本率合计」和「默认底线基数」两行给人看（现在这两行是**空白**，见 §7.2）。

## 3. 目标计算口径（最终）

### 3.1 新分母

```
分母 = 1 − 平台佣金率 − 平台其他成本率(桶) − 达人佣金率 − 目标利润率
```

**各扣各的，填的都生效。**（这是与现状最大的差别：现状佣金被藏在桶里，填了不生效。）

对应现状 `product_pricing_service.py:77-89` 的改动：

| 现状 | 新 |
|---|---|
| `− other_cost_rate` | `− other_cost_rate`（**语义变了**：不再含佣金、不再含尾程） |
| （无） | `− platform_fee_rate`（**新增入参**） |
| `− creator_commission_rate` | 不变 |
| `− spu_return_loss_rate` | **移出分母** → 折进分子（§1.6 ⑦） |
| `− spu_damage_rate` | **移出分母** → 折进分子（§1.6 ⑦） |
| `− target_margin_rate` | 不变 |
| `+ delivery_cost_rate`（成对生效时） | **删除**（尾程直接进分子，不再从分母加回） |

### 3.2 新分子

```
分子 = (采购成本 + 尾程配送费) × (1 + SPU退货率 + SPU货损率)                          （P1）
分子 = (采购成本 + 头程 + 仓储 + 贴单 + 尾程配送费) × (1 + SPU退货率 + SPU货损率)      （P2 起）
```

**括号里的"按件成本合计"就是"单件货值"** ⇒ 行业基准件损率直接折成钱，**不问这批损耗发生在哪一段**
（尾程前还是尾程途中）⇒ P2 把头程/仓储/贴单加进分子后，货损期望**自动跟着变大**，口径一次到位。

尾程进分子是 **B 路线**（拍板 #2）。现状的"成对生效"补丁与 `delivery_cost_rate` 参数**一并退役**。

### 3.3 桶的新定义

> **平台其他成本率 = 平台侧每 100 块收入里，除平台佣金、尾程、达人佣金之外，还要扣的一切。**

人工填。参考起点见 §6（**需人工确认**）。

- 字段名保留 `other_cost_rate`（改名要动 Pydantic / 前端 / 守护 / 调价通知快照，风险大于收益），
  但**注释与界面标签同步改成"平台其他成本率（不含平台佣金与尾程）"**。
- `fee_rate_source` 改为记录人工录入来源（例如 `manual_2026_11_19`），
  `fee_rate_version` 递增 —— 保留可追溯性，但**不再宣称可脚本复算**。

### 3.4 尾程（B 路线）

| 项 | 现状 | P1 |
|---|---|---|
| 「尾程占收入比」字段 `delivery_cost_rate` | 平台级，费率表算出的平台尾程均值 ÷ 平台平均售价 | **删列**（迁移带 downgrade 还原） |
| `compute_cost_floor` 的 `delivery_cost_rate` 入参 | 有 | **删** |
| 「成对生效」判定 | 有（`product_pricing_service.py:73-84`、`:205-212`） | **删** |
| 缺料原因 `missing_delivery_cost_rate_split` | 有 | **删**（`missing_delivery_cost` 保留） |
| 尾程进底线 | 进不去（生产全 NULL） | **直接进分子** |

**包邮开关的交互不变**（批次 6 的纪律）：不包邮 ⇒ 买家付尾程 ⇒ 商家不承担 ⇒ 尾程按 0 进分子（不是 None）。
生产 `finance.sku_platform_pricing` **0 行**【实测】⇒ 当前全部不包邮 ⇒ **P1 上线后尾程对底线数字零影响**，
一旦某天开了包邮，尾程立即按重量段进分子（届时重量段需先录，§8 #10）。

### 3.5 利润链同步（拍板 #5）

利润链现在漏扣桶 ⇒ P1 必须**同时**把桶加回利润链；而且 SPU 两率要改成**按件成本 × 率**进成本项
（与底线链同源），否则两条链永远对不上。

```
广告前利润 = 收入 − 按件成本合计 × (1 + 退货率 + 货损率) − 收入 × (平台佣金 + 桶 + 达人佣金)
```

落地位置：
- `product_profit_service.py:299-318` —— `return_loss` / `damage_loss` 从 `revenue × rate`
  改成 `按件成本合计 × rate`（**改的是口径，不是删项**）
- `product_profit_service.py:331-341` `_pre_ad_components` —— 新增桶项进成本项
- `product_finance_service.py:1265-1297` 调用处传桶

**自洽检验（最强的一条守护）**：在底线上算利润，利润率必须 = 目标利润率。
SKU 920 验算：不包邮 81.57 → 25.002%；包邮 125.34 → 25.000%；P2 之后 143.77 → 25.002%。

### 3.6 缺料纪律（沿用现有 `missing_reasons`，不放宽）

新口径下缺任一项 ⇒ **不算底线**（不是按 0 代入算个乐观数）：

| 缺什么 | 报什么 |
|---|---|
| 平台佣金率 | `missing_platform_fee_rate`（**新增**） |
| 桶 | `missing_platform_cost_rate`（沿用） |
| 达人佣金 | `missing_creator_commission_rate`（沿用） |
| 没绑 SPU | `missing_spu_binding`（沿用） |
| SPU 两率 | `missing_spu_rates`（沿用） |
| 采购成本 | `missing_purchase_cost`（沿用） |
| 定价档位 | `missing_pricing_policy`（沿用） |

**「不可省略型」 vs 「逐步补齐型」**（批次 9 定的两类纪律）：

| 类型 | 成员 | 缺了怎么办 |
|---|---|---|
| **不可省略型** | 采购成本、SPU 两率、平台佣金率、桶、达人佣金、定价档位 | **不算底线**（缺了就是算不准，宁可留白） |
| **逐步补齐型** | 头程、仓储、贴单费（P2）、尾程 | 该项**未计入**，但**仍然出底线** + 界面**显式标注未计入** |

⚠️ 尾程为什么属「逐步补齐型」：它只影响**分子**（多摊一点成本），
不影响分母 —— 少算它 ⇒ 底线偏松一点，但**不会算出一个离谱的数**。
而 SPU 两率在旧口径里是**分母**项，少算它会把分母做大 ⇒ 底线**系统性偏低** ⇒ 必须算。

⚠️ **同一条纪律也适用于利润链**（实施时补上）：平台佣金率与桶既然是「不可省略型」，
利润链缺它们就**必须整条留白**（不是按 0 计）—— 这与底线链一致。
但批次 9 之前利润链**压根不扣桶** ⇒ 桶没配不会让利润链留白；
批次 9 把桶加进扣项后**新增**了「桶没配 ⇒ 利润空白」这条路，
而最初**没有任何原因码指向它** ⇒ 运营看到一片空白，系统给的是「完整预计利润口径」
这种没法定位的兜底话 ⇒ 根本不知道该去补**哪个**费率。

**补法**（`product_profit_service.build_platform_profit_preview`）：
- 新增返回键 `platform_rate_missing_reasons`（两段都有），
  缺平台佣金率 ⇒ `missing_platform_fee_rate`；缺桶 ⇒ `missing_platform_cost_rate`
  —— **与底线链同一套词**（同一种缺失，两条链不能一个叫这个、一个叫那个）。
- 路由层 `missing_input_reasons` 同步补这两个键 ⇒ 前端利润列直接点名缺哪个。
- 桶的入参**去掉默认值** ⇒ 哪个调用方漏传桶会当场 `TypeError`，
  而不是悄悄留白、让运营去补一个其实没问题的费率。
- 守护测试：`backend/tests/test_profit_chain_required_rates.py`（7 条，含「0 是有效值不是缺料」）。

### 3.7 护栏收口：底价护栏必须与页面显示**同一条底线**（批次 9 新增）

**问题（实施时发现的既有口径分叉）**：利润测算保存的底价护栏
（`product_center.py::_compute_sku_min_selling_price`）**不传仓** ⇒
它算出的底线**少了尾程与履约成本**；而商品中心页面显示的是**带仓**的底线
⇒ **同一个 SKU 在两个地方两个底线数**，且护栏那条**更松** ⇒
「页面说低于最低售价别卖，护栏却放行」⇒ 护栏形同虚设。

**修法**（`_compute_sku_min_selling_price` 加 `warehouse_code` 入参）：
- 尾程按「平台 × 仓 × 重量段」算（与页面同一份取数）
- 履约按件成本从 `context["fulfillment_costs"]` 取（与页面同一份取数）
- 没传仓 ⇒ 两项都不进（与页面在无仓时**逐字一致**）

**实测影响**（`backend/tests` 种子口径，TikTok）：
护栏底线 30.98 → **57.46**（分母不变，分子多了尾程 5 与履约 3.55）。

⚠️ **这会让「预计售价偏低」的利润版本保存被拦下更多** ——
这是**收紧**，不是放松；CHANGELOG 里要点名。

### P2 · 履约成本进底线分子（**降级实施**，2026-11-19）

前置：`core.dim_erp_sku.unit_volume_cbm` 要录（1122 个只有 18 个有【实测】）。与重量段是同一批业务录数。

- 仓储 = 单件体积 × 仓月费率 × 周转天数/30（`build_reference_storage_cost`，`product_profit_service.py:25`）
- 贴单费 = 仓的 `label_fee`
- **取数层**：新模块 `backend/services/product_fulfillment_cost_service.py`（**唯一**实现）
  - `load_fulfillment_costs(db, sku_rows, warehouse_code)` ⇒ `{sku_id: {logistics_cost, storage_cost, label_fee, missing_reasons}}`

- 缺体积 ⇒ `missing_unit_volume`，**该项未计入**（不按 0 代入），**但仍然出底线**
  （逐步补齐型缺料；见 §0.3 的降级说明）
- 缺仓 ⇒ 三项全部未计入 + `missing_warehouse_for_fulfillment`（与尾程不传仓同一套纪律）
- 运输方式**不进底线**（底线是「SKU × 平台 × 仓」的量，运输方式属于发运批次维度）：
  取该仓**不限运输方式**时唯一可确定的规则；挑不出来（多条 default 费率不同）⇒ **不计入**

## 6. 平台桶的起始值（**对着结算单实测**，人工确认后落库）

### 6.1 「桶」是什么

**桶 = 界面上那个「平台其他成本率」输入框**（数据库字段 `core.dim_platforms.other_cost_rate`，每个平台一个百分比，手工填）。

它在旧口径下装的是一坨说不清的东西 —— 由恒等式反推：
`other_cost_rate = 1 − 实测采购成本率 − 实测净利率 − SPU退货率 − SPU货损率 − 默认达人佣金率`
（种子 `current_migrations/versions/20261020_sku_pricing_guardrails.py:62,67`：Shopee 41.65%、TikTok 27.27%，
来源标 `b_class_measured_2026_01_07`）⇒ 里面混着**平台佣金 + 摊进去的运费 + 其它说不清的扣款**。

**新口径下桶只装一样东西**：

> **平台侧按收入比例扣、但既不是平台佣金、也不是尾程、也不是达人佣金的那些钱。**

| 该装 | 不该装 |
|---|---|
| 平台服务费 / 交易手续费 / 支付手续费 | 平台佣金（有独立字段 `default_fee_rate`） |
| 平台杂项扣款（券成本、服务计划费等） | 尾程（SKU 级按重量段精确算，**进分子**） |
| 退款管理费 / 平台惩罚 / 商家体验扣款 | 达人佣金（有独立字段） |
| | 采购 / 头程 / 仓储 / 贴单（按件成本，**进分子**） |
| | 退货 / 货损（已按件折**进成本**） |

⇒ 用它们做分母会把所有比例放大。**必须用 `订单原始金额`（13573/13573 完整）**。

### 6.3 起始值建议

| 平台 | **建议起始值** | 口径 | 来源标注 |
|---|---|---|---|
| **Shopee** | **3.58%** | 结算单「服务费」实测 | `manual_2026_11_19_settlement_ledger` |
| **TikTok** | **3.11%** | 结算单「交易手续费」实测 | `manual_2026_11_19_settlement_ledger` |

**⚠️ 这推翻了早先的推算值**（旧桶做减法：Shopee 6.49% / TikTok 13.89%）。
那两个数的问题是：**旧桶本身的口径已经对不上现在的结算单** ——
TikTok 旧桶 27.27% 甚至**小于**当前分项之和 32.09% ⇒ 旧桶不可信，不宜再拿它做减法。
对着结算单实测才是能对业务讲清楚的数。

**代价（必须知道）**：桶变小 ⇒ 分母变大 ⇒ **底线再降一点**。
Shopee / SKU 920（包邮）：分母 0.5140 → 0.5431，底线 **125.34 → 118.62**（再降 6.72 元）。
但**利润率自洽性不变**（118.62 上利润率仍精确 = 25.000%）—— 底线降是因为这次扣全了，
不是因为纪律松了。

**保守余量的处理**：结算单**列本身残缺**（很多扣款项采集不到）⇒ 实测值可能偏小。
建议：**先按实测值上线**，并在「定价设置」里由运营**持续人工维护**（平台政策变了就改）——
这正是拍板 #1「定价设置 = 人工录入」的意义。
上线首月盯实际利润率，若低于目标利润率再上调桶。
