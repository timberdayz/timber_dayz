# 运营绩效自动计分设计

## 背景

运营绩效是店铺绩效中的固定 20 分维度。现有工作台要求管理员每月填写统一目标值和指标满分，并要求启用指标满分之和等于 20。这让管理员同时承担规则制定、权重分配和数据录入，且会产生小数分数和不可比的月度配置。

本设计将运营绩效收敛为“填写可核查的业务结果，由系统自动换算整数分数”。

## 已确认的业务决策

1. 运营总分固定为 20 分。
2. 系统按当月启用指标均分 20 分，不在 V1 开放自定义权重。
3. 单项满分和最终运营得分均为整数，不展示或结算小数分。
4. 20 不能整除启用指标数时，系统按固定的指标目录 `sort_key` 升序分配余数。例如启用 3 项时，满分为 7、7、6。
5. 指标目标、单位、评分方向和填写说明由受控目录预设，绩效管理员不能在月度工作台修改。
6. 管理员填写店铺的实际业务数据，不能直接填写量化指标分数。
7. 培训完成改为“培训完成率”，目标固定为 100%。
8. “其他人工指标”改为“专项运营检查”，仅允许基于固定三级结论评分。
9. 考试成绩在业务明确使用及格率或平均分前不作为 V1 启用指标。
10. 至少启用一项指标；空规则不得保存、不得确认店铺范围，也不得进入店铺数据录入。
11. 使用本规则版本的月份，其生效绩效配置的 `operation_max_score` 必须为 20；不为 20 时保存规则和确认范围均返回明确业务错误。
12. 店铺范围确认至少保留一家参与店铺；全部排除时不得确认该月运营范围，也不得以“无运营数据”绕过绩效结算条件。

## 指标目录

V1 只提供下列可启用指标：

| 指标 | 类型 | 目标/标准 | 店铺录入 |
| --- | --- | --- | --- |
| `customer_satisfaction` 客户满意度 | 越高越好 | 100% | 当月满意度百分比 |
| `complaint_count` 投诉次数 | 越低越好 | 不高于 3 次 | 当月投诉次数 |
| `reply_timeliness` 回复及时率 | 越高越好 | 95% | 当月及时回复率 |
| `training_completion_rate` 培训完成率 | 越高越好 | 100% | 已完成人数与应完成人数 |
| `operation_special_check` 专项运营检查 | 定性检查 | 固定三级结论 | 已完成且合格 / 部分完成或需整改 / 未完成或不合格 |

目录必须为每项维护不可变的 `metric_code`、`sort_key`、单位、数据类型、目标和规则版本；显示名称可以修改但不能作为计算、余数分配或历史重放依据。

客户满意度、回复及时率均以 `0` 至 `100` 的百分数存储和录入，目标必须大于 `0` 且不超过 `100`。投诉次数为非负整数，目标为非负整数；目标为 `0` 时仅实际为 `0` 才达成 100%。培训完成率只允许录入非负整数的“已完成人数”和“应完成人数”，并由系统计算百分率；已完成人数不得大于应完成人数，应完成人数为 `0` 时按“无需培训、达成 100%”处理并展示该说明。专项运营检查只存储稳定结论代码 `passed`、`partial` 或 `failed`，后两种结论必须填写说明。

客户满意度 V1 以百分比录入和展示。现有 0 至 5 星原始数据若在后续自动接入，必须由数据适配层统一换算为百分比，不能与百分比口径混用。

## 整数计分模型

设运营总分为 `T = 20`，当月启用指标数为 `N`。规则保存要求 `N >= 1`：

```text
基础满分 = floor(T / N)
余数 = T mod N
```

目录顺序靠前的 `余数` 个指标各增加 1 分。每项满分均为整数且总和始终为 20。

量化指标先计算 0 至 1 的达成系数：

```text
越高越好: min(实际值 / 目标值, 1)
越低越好: 实际值 <= 目标值时为 1，否则为目标值 / 实际值
```

专项运营检查的达成系数固定为：

```text
已完成且合格 = 1
部分完成或需整改 = 0.5
未完成或不合格 = 0
```

单项得分为“自动分配满分乘以达成系数”，使用十进制计算并统一采用 `ROUND_HALF_UP` 取整。例如 `3.5` 固定取为 `4`。最终运营得分是各单项整数得分的总和，范围为 0 至 20。前端预览、后端计算和正式结算必须复用同一规则版本，不能依赖各语言的默认浮点取整行为。

示例：仅启用客户满意度，自动满分为 20；目标为 100%，实际为 90%，系统得分为 `round(20 * 90%) = 18`。

## 月度工作流

### 评分规则

规则页改名为“本月启用指标”。管理员只切换指标启用状态，页面只读展示每项的目标、单位、方向、自动分配满分和评分说明。不存在统一目标值或自由满分输入框。规则在店铺范围确认前为草稿，草稿保存覆盖同一草稿版本；确认店铺范围时冻结规则版本。范围已确认后禁止改规则，若需更正必须显式撤销范围确认并清除该月店铺录入草稿后生成新规则版本。

草稿保存和范围确认均必须携带当前规则版本与绩效配置版本，服务端使用乐观锁比较；任一版本陈旧时返回 `409 Conflict`，并要求客户端刷新后重新操作。范围确认时再次校验规则版本、启用指标数和 `operation_max_score = 20`，禁止确认一个被并发覆盖或不满足总分合同的规则。

页面实时展示启用数量、整数满分分配和合计 20 分。保存时生成当月规则快照。

### 店铺范围确认

维持当前设计：系统加载全部启用店铺，绩效管理员确认参与范围；排除店铺必须填写原因；参与店铺必须具有当月销售目标分解。

### 店铺数据录入

只显示参与店铺。量化指标录入实际值；培训完成率只能由已完成人数和应完成人数计算；专项运营检查使用三级选择并在非“已完成且合格”时要求说明。

每项展示目标、实际、计算过程和只读自动得分。缺少任一必填数据时，店铺保持待完成，不进入正式结算。

## 数据与历史快照

保存当月规则时，必须持久化当月启用指标、目录版本、目标值、单位、方向、目录顺序、自动分配满分和评分规则版本。后续目录默认值变化不得影响冻结月份；工资锁期后的月份不可修改，并始终按最后冻结版本重算。

使用 `scoring_model_version=auto_integer_v1` 的月份只能通过运营绩效工作台服务写入规则、范围和店铺实际数据。保留的通用运营目标 CRUD、导入、复制及旧维护入口必须在识别到该版本时返回明确业务错误，不得写入、覆盖或绕过目录受控、冻结规则、乐观锁和自动整数计分约束。

V1 不移除既有月度店铺范围快照和店铺数据录入约束；仅替换规则输入和计分语义。现有小数存储字段可继续存储原始结果，但正式评分、展示、排名和结算只使用整数结果。缺少任一必填运营数据的参与店铺保持 `pending/partial`：该店不得进入正式店铺绩效、排名、可归属个人绩效、收入或工资单；其他数据完整且满足独立前置条件的店铺可结算，整月列表明确标记为存在待完成店铺。

复制上月规则只复制启用的 `metric_code`，新月使用复制时当前目录的默认目标和规则生成新草稿，不继承店铺范围、店铺实绩、自动得分或冻结状态。已有月度的旧自由满分/人工分模式保持其原有规则版本，不得重写历史结算结果。

“显式迁移”仅允许绩效管理员对未锁期、未确认店铺范围且没有店铺运营录入数据的旧模式月份发起。迁移写入不可变 `scoring_model_version=auto_integer_v1`、操作者和时间，并保留原规则快照作为审计证据；迁移后不可回退。已确认范围、有店铺录入或已锁期的旧模式月份只能按旧版本继续处理，需新建月份才可使用新模式。

## 非目标

- V1 不开放月度自定义权重。
- V1 不自动接入客户满意度、投诉或回复时效的数据源。
- V1 不启用考试成绩，直至确认门店级别的统计口径。
- V1 不提供无标准的自由人工打分。

## 后续扩展

自定义权重仅作为后续高级能力提供给绩效管理员。届时每项权重仍必须为整数、合计必须为 20，并需生成不可变月度快照和变更审计记录。

## 验收标准

1. 启用 1 至 5 项时，系统自动分配的每项满分均为整数且合计为 20。
2. 启用 3 项时固定按目录顺序得到 7、7、6。
3. 不存在统一目标值或自由满分输入控件。
4. 客户满意度目标 100%、实际 90%、仅启用该项时，自动得 18 分。
5. 量化指标录入页不允许直接编辑得分。
6. 培训完成率按 100% 目标计算；专项运营检查按三级结论计算。
7. 页面展示每项的填写说明、目标、公式/示例和自动得分。
8. 缺少必填数据保持待完成，不进入正式结算。
9. 已冻结月份在目录默认值变化后仍按其快照规则重算；未冻结草稿、冻结规则和工资锁期后的修改边界均可验证。
10. 零个启用指标无法保存和确认范围；生效 `operation_max_score` 不等于 20 时返回明确业务错误。
11. 规则草稿或范围确认使用陈旧版本时返回 409，不能覆盖较新版本。
12. 仅未锁期、未确认范围且无店铺录入的旧模式月份可显式迁移；其余旧模式月份保持原计分版本。
13. 全部店铺排除时无法确认范围；旧运营目标写入口无法修改自动整数计分月份。
