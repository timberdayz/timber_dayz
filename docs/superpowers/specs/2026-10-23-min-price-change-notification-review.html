一、事实确认：最低售价确实没有存储

这是整个方案成立的前提，也是过去无法通知的根本原因。

换句话说：系统能回答"现在最低卖多少钱"，但从来没有回答过"比上次是高了还是低了"。所以"这次要调价"这件事必须靠新增一个比对基线来产生，不能靠"读现有数据"推导出来。

二、上一轮方案的三处修正

方向确认后，有三点必须改。其中第三点是我上一轮的事实性错误，主动纠正。

上一轮 · 已废弃

按幅度筛：只通知变动 ≥5% 或 ≥X 元的，其余合并成日报。

批量熔断：单次变更 SKU 数超阈值时只发汇总，不逐条推。

日常聚合推送：把同类变更打包成一条消息推。

这三项都是在替业务方做取舍，会直接造成漏通知——与需求正相反。

修订后 · 唯一标准

零遗漏：凡是最低售价这个数发生变化的 SKU，全部生成通知记录，一条不落。

不做前置筛选：系统不判断"这条重不重要"，只负责完整投递。

重要度交给视图：紧急程度作为字段写进表里（降 / 升 / 保护失效），由运营在飞书里排序、分流，而不是由系统在推送前丢掉。

这样既满足"全都要通知"，又让运营能自己按重要度安排处理顺序。

事实纠正：上一轮我说"库龄管道刚补上数据时会一次产生 495 条噪音通知"，这个判断是错的。核对过代码后：select_age_tier 在 age_days = None 和 age_days = 0 时选出的都是第 1 档，所以库龄管道修复前后，所有 SKU 的最低售价数值完全相同（只有 pricing_tier_source 从"回落档"变成"按库龄"，那不是价格变化）。冷启动噪音为零，不需要"首帧静默"这类特殊处理。

不需要独立的台账表，也不需要复杂的设计。

比对基准是"上次已处理的价格"，不是"上次的价格"。所以一个 SKU 从 ¥128.56 变到 ¥90.82 → 通知一次，基线更新为 90.82；之后每天都还是 90.82 → 不再重复通知；若某天补货导致库龄归零、底线回到 ¥128.56 → 再次通知（这是"可以提价了"的信号，见第六节）。
算价走共享实现：页面与通知都调 backend/services/product_pricing_query_service.py 的同一个函数——规则行、平台费率、库龄的取数口径也只有那一份。否则会出现「页面按日常档显示、通知却按滞销档发」的自相矛盾。
分两个事务：① 检测（算价 → 比对 → 产出变更集 → 静默推进基线 → 建 outbox 任务 → commit）；② 投递（批量写入飞书 → 成功后回写基线 → commit）。飞书写入是外部 IO，放在长事务里既慢又危险；投递失败时任务留在 outbox 里按指数退避重试，不与检测结果一起回滚。
唯一被排除的变更：下架造成的跳高。库存清零 → SKU 从库龄表消失 → 库龄回落第 1 档（目标利润率最高）→ 底线跳回全档最高位。但这个品已经不卖了，底线高低没有业务含义，不排除的话机器人会持续收到"某个已下架的品，底线从 ¥90 涨到 ¥128"。判定：库龄来源从"按库龄"变成"无库龄回落"，且其它定价输入一个都没变。

这不是"筛选"——排除的是语义上根本不成立的变更。但基线仍要静默推进，否则明天还会重复判定为同一次跳高，后续真实的变化反而被噪音挡住。

所以：ERP 侧只管新增，不管更新也不管归档

职责边界已明确——机器人负责归档，行归档到哪、是否删除，ERP 一概不管。因此 ERP 的写入语义收敛到最简单的一种：每次最低售价发生变化，就新增一行。不做 search、不做 update、不管理 record_id。

方案ERP 侧动作表内实际行数结论
A. 每次变更新增一行 只 create，一次调用 ≈ 未处理待办数（几百~几千） 采纳 行被机器人归档后表不累积
B. 每个 SKU 恒一行 先 search 再 create / update 恒定 ≈ 1,100 行 不需要 多一层 search 与 update 逻辑
纠正上一轮结论：上一轮写"每次变更新增一行，一年约 18 万条，必然撞 20,000 上限"——这个判断的前提是行不归档。实际分工是机器人负责归档，所以表里只留尚未处理的行，容量是"在办待办数"而非"历史累计数"，不构成风险。A 方案比 B 更简单，且额外收获：同一 SKU 在归档前的多条变更记录天然形成变更历史，运营和机器人侧都能看到完整轨迹。
随之而来的一个必须处理的一致性问题：既然 ERP 不做 update，就没有"重写旧行"这个动作，基线必须在推送成功之后才更新。否则飞书写失败（限流、网络抖动）时基线已被推进，那次变化就永久丢失——正是"该通知的没通知"。落地方式是复用现有 outbox：先落任务（带 payload 哈希做去重），投递成功后再回写基线。

六、全量通知之后，必须把两种方向标清楚

既然不筛选，就必须在表里让运营一眼分辨"这条是机会"还是"这条是亏本"。

方向触发原因含义紧急度
底线下降 库龄跨档 → 目标利润率放宽 → 成本线下沉 可以更便宜卖了，主动降价清货的机会 机会型 按库存金额排序处理
底线上升 补货 → 库龄归零 → 落回日常档 → 底线回升 若平台售价还停在旧低价，就是在亏本卖 必须型 需要立刻改价

第二条是全量通知真正立功的地方。补货会让库龄归零、档位回落、底线从 ¥90.82 抬回 ¥128.56。如果平台上还挂着 ¥95 在卖，那是在亏本——而这件事在今天没有任何人会知道。只推"降价"方向的话，这类损失会一直静默发生。
关于"需要调价"的口径：最低售价是底线，不是平台当前售价。底线降了，现价可能仍高于新底线（不必改）；底线升了，现价可能已低于新底线（必须改）。所以建议两个方向都进表，用上表的"紧急度"字段区分，而不是在推送前按"是否真的需要改价"过滤掉——这样既满足"全都要通知"，运营也能按紧急度安排顺序。

七、四个问题的最终结论

筛选和阈值的问题不需要问了，剩下这四个已全部拍板。

  1. 飞书表用"恒一行"还是"每次变更加一行"？每次变更加一行 —— 上一轮"一年 18 万条必然撞上限"的判断前提是行不归档；实际机器人负责归档，表里只留未处理的行。更重要的是：ERP 侧只新增就没有"重写旧行"这个补救动作，基线推进顺序就成了唯一的可靠性保障（见第八节）。归档前的多条记录还天然形成变更历史。
  2. 变更流水要不要在飞书里也能查？要 —— 同一张表靠视图分流即可（待处理 / 已处理 / 按方向），不额外建表。
  3. 人工在哪改价、回执怎么确认？飞书勾「完成」 —— ERP 不感知"这个 SKU 已接管"（人工接管体现在覆盖值上，覆盖值非空后库龄变化不再影响底线，天然不产生通知）。机器人监听「完成」列做归档，归档去向由机器人决定，ERP 一概不管。
  4. 通知的送达方式：只落表，还是也要机器人提醒？先只落表 —— 表格自带视图和筛选，运营打开就有清单；机器人提醒属于额外的打扰手段，等确认运营真的会看表之后再加。

八、风险与护栏

在全量通知的前提下，风险点从"漏推"转成了"推坏"和"推了没人管"。以下护栏均已落地。

高推送失败但基线已推进 → 永久丢通知

ERP 侧只做新增、不做更新，没有"重写旧行"这个补救动作。若先更新基线、再推飞书，一旦飞书写入失败（限流 1254291、网络抖动、token 过期），基线已被推进，那次变化就永远不会再来一遍——正是最该通知的时候静默丢失。

护栏：复用现有 outbox（ops.feishu_projection_tasks）：先落任务、用 payload 哈希做去重，投递成功后才回写基线；失败任务保留在 outbox 里按指数退避重试。

低飞书表撞 20,000 条上限

上一轮评为高风险的前提是"行不归档"。实际分工是机器人负责归档，表内只留未处理的行，容量是"在办待办数"（几百~几千），不构成风险。

护栏：仍保留一个监控——表记录数接近 20,000 时告警，防止机器人归档失效时无声堆积。

高同表并发写冲突

官方明确同一张表不支持并发调用写接口（1254291），全量推送若并发会大面积失败。

护栏：推送串行执行、批次间留 0.5~1 秒；沿用现有 outbox 重试机制；开启 ignore_consistency_check 提升吞吐。

中任务挂不上调度

现有飞书投影没有独立 Celery 任务，投递是在商品中心 API 写入时用 asyncio.create_task 顺带触发的。最低售价变更没有任何 API 写入事件，顺带触发永远不会发生。

护栏：新任务挂到 Celery beat（price-adjust-notify-daily，每天 10:00，给 09:00 库存采集留缓冲），路由 backend.tasks.price_adjust_notify_tasks.* → scheduled 队列。

高整批失败 → 已成功的块被重写，产出重复行

批量新增按 200 条一块分批。若"整批一次调用、失败就把所有任务标 failed"，第 3 块失败时第 1、2 块（400 行）其实已经写进飞书了，却被一起标成 failed → 重试再写一遍。调价记录表是只增不改的，重复行不会被覆盖，只会一直堆着。

护栏：每块独立成败——失败只标记该块的任务，已成功的块照常置 completed。已由 test_failed_chunk_does_not_rollback_already_created_chunks 守着。

高写入端点用错版本 → 100% 写不进表

旧端点 bitable/v1 会被飞书直接拒掉：99992402 field validation failed，连只带主字段的最小请求都过不去。代码能跑、单元测试能过，但一条也写不进去——纯单测发现不了这个。

护栏：改用 base/v3 + create_records；单元测试断言真实请求的 URL 与 body key；并保留「对真实表写一条再读回比对」的验收方式。

中单次批量上限按 500 估 → 超限丢整批

base/v3 的上限是 200（实测 201 条被拒：800010701 Array must contain at most 200 element(s)），比旧版 bitable/v1 的 500 小。超限时飞书拒掉整批，代价是丢整批而不是丢一半。

护栏：FEISHU_BATCH_CREATE_LIMIT = 200，分块推送、每块独立成败。

中调价记录表配到了错误的 base

调价记录表与三张状态镜像表不在同一个多维表格。若沿用镜像表的 base token 写表 id，URL 里的 base 与表对不上 → 必然失败。

护栏：新增 ops.feishu_projection_configs.price_adjust_base_token（留空回落 FEISHU_PRODUCT_BASE_TOKEN），由 test_price_adjust_uses_its_own_base_token_when_configured 守着。

中人工接管后仍被催办

覆盖值优先级最高，库龄变化不再影响底线，但系统仍按"库龄变了"反复推送。

护栏：覆盖值非空即视为人工接管，该 SKU 退出待办队列、不再产生变更记录。

低首次运行的批量误报

首次运行时基线表是空的，若不特殊处理会把 1,122 个 SKU 全部当成"变了"。

护栏：判据是"有没有基线行"而不是"价格列是不是 NULL"——算不出底线的 SKU 同样被处理过、同样有上下文，同样不算"首次"。首次运行只写基线不推送；此后仅对有基线且数值不同的 SKU 推送。注意这与库龄冷启动无关——冷启动本身不产生价格变化。

低纪律线将来接管

补齐参考售价后，库龄会多一条通过折扣率影响底线的路径，同一个"降价"背后原因不同。

护栏：原因字段强制区分成本线 / 纪律线 / 覆盖值三个来源。
