# DOS 指标口径与命名决策

> 状态：设计稿（待评审）
> 日期：2026-10-24
> 关联：库存增量采集设计（`2026-10-24-miaoshou-inventory-incremental-collection-design.md`）、SKU 级滞销排名设计（`2026-10-21-sku-level-clearance-ranking-design.md`）、指标语言规范（`docs/team-skills/sea-metrics-language/SKILL.md`）

---

## 1. 要解决的问题

系统里有两种「DOS」，来源不同、数值不同，但名字都长得像「周转天数」：

| | 正常 DOS | 现在这个 |
|---|---|---|
| 销量来源 | ERP 订单事实表算出来的销量 | 妙手库存清单自带的销量列 |
| 现状 | **算不出来** | 已可用 |
| 粒度 | 订单表**没有仓库维度** → 只能到 SKU 级 | SKU × 仓 |
| 字段 | `estimated_turnover_days`（9999 哨兵） | 尚未落地 |

本 spec 的目标：**把两个口径的命名一次性定死**，让后续任何 agent 看到字段名就知道它算的是什么、依据是什么、能不能进结论。

---

## 2. 决策：不要叫「快捷 DOS」，改叫「清单口径 / 订单口径」

### 2.1 为什么「快捷 DOS」是错的名字

「快捷」描述的是**我们做这件事时省了多少事**，不是**这个指标是什么**。三个具体问题：

1. **它暗示了一个错误的紧迫感。** 名字里带「快捷 / 临时 / 近似」，后续 agent 会本能地想「等订单口径修好就换成它」——于是两边各写一份口径，等于把「唯一实现」纪律又破坏一次，而唯一实现纪律正是商品中心最低售价与滞销模块能对齐的前提。
2. **它其实冤枉了自己的数据。** 实测证明库存清单的销量列不是估算值（见 §3.2），它有严格单调性、是整数、跨批次自洽。「近似」在事实层面不成立。
3. **它把「口径差异」说成了「质量差异」。** 两个 DOS 的差别不在精度高低，而在**依据的数据不同**——平台侧统计的销量 vs ERP 重算的销量（退款/取消/归属时间窗/时区都会造成差）。用「精确 vs 近似」描述，会让后续 agent 在做差异归因时找错方向。

### 2.2 关键事实：这个「临时方案」其实是唯一能做仓库级 DOS 的方案

实测（2026-10-24）：

- `b_class.fact_miaoshou_orders_daily / weekly / monthly / manual` **全部 0 行** → 订单口径 DOS 今天无原料。
- `semantic.fact_orders_atomic` 共 31012 行，**只有 shopee / tiktok，没有任何仓库维度列** → 即使 miaoshou 订单域修好，订单口径 DOS 也**做不出 SKU × 仓粒度**，只能到 SKU 级。
- 而滞销清理、补货决策恰恰需要仓库粒度：实测 37 个跨仓 SKU 里 **8 个各仓销量不同**（如 `HKR-GNH-Cream` 菲律宾 s90=7 / 新加坡 s90=0）。

结论：**仓库级 DOS 只能来自库存清单自带的销量列**。订单口径 DOS 修好后能提供的是 SKU 级的**交叉校验基准**，不是替代品。

因此这不该被命名为「临时/快捷」，它是一个**独立成立的口径**。

### 2.3 「DOS」这个词本身有歧义 —— 先定义，再命名

这是比「快捷DOS vs 正常DOS」更根本的一层混淆，必须先钉死。

#### 2.3.1 两个量互为倒数的两端

| 概念 | 公式 | 单位 | 回答什么 |
|---|---|---|---|
| **日均销量**（daily average sales） | `窗口销量 ÷ 窗口天数` | **件 / 天** | 卖得**快不快**（速度） |
| **DOS**（Days of Supply） | `库存 ÷ 日均销量` | **天** | 还能卖**多久**（时长） |

两者是**同一个公式的两端**，实测恒等式在 **368 个可算行上零违例**（`库存 ÷ 日均销量 = DOS`，误差 >0.05 的行数为 0）：

```
DOS90 = 可用库存 ÷ (近90天销量 ÷ 90)
日均90 = 近90天销量 ÷ 90
```

**Walter 的口头认知「30 天日均销售 / 90 天日均销售」= 上表第一行**，它是 DOS 公式的**分母**，不是 DOS 本身。

#### 2.3.2 两个量的量级完全不同

| | 最小 | 平均 | 最大 |
|---|---|---|---|
| 日均90（件/天） | 0.011 | 0.176 | 3.51 |
| DOS90（天） | 1.5 | 331.9 | 3510.0 |

两个真实样本：

| | SKU | 仓库 | 库存 | 日均90 | DOS90 |
|---|---|---|---|---|---|
| 最快周转 | `SBF004-PURPLE-035` | 菲律宾1店-儿童书包 | 1 | 0.68 件/天 | **1.5 天** |
| 最慢周转 | `SBF002-QLSQW-035` | 菲律宾1店-儿童书包 | 78 | 0.02 件/天 | **3510 天** |

#### 2.3.3 为什么滞销判定必须用 DOS，不能用日均销量

同一批 368 个可算行，两种切法的命中量差异极大：

| 判据 | 命中行数 | 占比 |
|---|---|---|
| 日均 ≥ 1 件/天 | **9** | 2.4% |
| 日均 ≥ 0.5 件/天 | 26 | 7.1% |
| 日均 ≥ 0.1 件/天 | 154 | 41.8% |
| **DOS ≥ 90 天** | **254** | **69.0%** |
| **DOS ≥ 180 天** | **161** | **43.8%** |
| DOS < 30 天 | 30 | 8.2% |

原因：**日均销量是绝对值，跟库存规模绑定**。
- 库存 78 件、日均 0.02 件/天的 SKU，`0.02` 这个数字看着微不足道，但它意味着 **3510 天**才卖完 —— 用日均判定会被完全漏掉。
- 库存 1 件、日均 0.68 件/天的 SKU，日均看着挺高，但它其实**明天就断货**。

滞销问的是「这批货多久能清掉」，是**跟自己的库存比**，不是看卖得快不快 → 必须用 DOS。

#### 2.3.4 命名方向（需拍板）

仓库现状里两个位置已经各有人占：

| 概念 | 现有字段 | 现值 |
|---|---|---|
| 日均销量 | `mart.inventory_backlog_base.daily_avg_sales` | 全 0（订单口径无 miaoshou 数据） |
| 天数 | `mart.inventory_backlog_base.estimated_turnover_days` | 0 / 9999 两值 |

**建议：DOS 固定表示「天」（Days of Supply，行业通行含义），日均销量沿用「日均销量」叫法。**

理由：
1. DOS 的国际通行含义就是 Days of Supply，供应链同事看到即知是「可支撑天数」
2. 两个语义位置在仓库里都已有字段占位，不需要为日均销量另造名字
3. 反过来把 DOS 让给「日均销量」，那么更重要的滞销判据「还能卖多少天」反而要用一个非标准名，对外沟通成本更高
4. 字段名 `checklist_dos_sales30` 本身已把两者分开：`dos`（天数）+ `sales30`（销量窗口）

**前端中文展示名建议直接写「可售天数（近90天销量）」而不是「DOS-90」**，业务同事不会把 DOS 读成日均销量。

### 2.4 命名方案

仓库里已有 `docs/team-skills/sea-metrics-language/SKILL.md`，它规定了三层口径语言（平台原生口径 / 系统统一口径 / 会议决策口径），并明确「不要把平台原生指标和系统统一指标混成一个结论」。本决策**直接沿用该词典的词汇**，不再另造「快捷」这类词。

**字段名（语义层 / mart / API）**

| 口径 | 字段名 | 中文名 | 状态 |
|---|---|---|---|
| 清单口径（妙手库存清单自带的销量列） | `checklist_dos_sales30` | DOS-30（库存清单口径） | `observe` |
| 清单口径 | `checklist_dos_sales90` | DOS-90（库存清单口径） | `observe` |
| 订单口径（ERP 订单事实表） | `order_dos_sales30` | DOS-30（订单口径） | `blocked`（无 miaoshou 订单数据） |
| 订单口径 | `order_dos_sales90` | DOS-90（订单口径） | `blocked` |

**禁用名（后续 agent 不得使用）**

| 禁用 | 原因 |
|---|---|
| `quick_dos` / `fast_dos` / `short_dos` / `approx_dos` | 描述省事程度而非口径；暗示精度差（事实不成立） |
| `platform_dos_*` | **与仓库既有 `platform_code` 语义冲突**——本仓库 `platform_code` = shopee/tiktok/miaoshou（电商平台），用 `platform_` 会被读成「跨平台口径」 |
| `dos_30d` / `dos_90d` | `30d` 会被读成「DOS=30 天档」，而实际含义是「用近 30 天销量窗口算」 |
| `dos_30` / `dos_90` | 同上，且更短更易混 |
| `estimated_turnover_days`（继续对外暴露） | 该列今天装的是订单口径 DOS 且常年 9999 哨兵，名字完全不体现来源 |

> `estimated_turnover_days` 的处置：`mart.inventory_backlog_base` 底层列名本次不动（避免大范围改动）；**对外 API 与前端字段名**在滞销模块改造时改名为 `order_dos_sales30`，使口径分类在接口层就成立。

## 3. 实测事实基线（file 3004，1113 行，metric_date 2026-09-01）

### 3.1 销量列的形态

| 项 | 实测 |
|---|---|
| raw_data 键名 | `近7天销量数据` / `近30天销量数据` / `近60天销量数据` / `近90天销量数据`（**无 `*` 前缀**，与 `*商品SKU` 不同命名空间） |
| 覆盖 | 1113/1113 全覆盖，另一批次 1226/1226 全覆盖 |
| 可解析性 | 1113 行全部可直接转数字，0 失败 |
| 整数值 | 全部为整数，0 行非整数 |
| 非负 | 0 行为负；最大值 s90=316、s30=113、s60=205、s7=22 |
| 粒度 | SKU × 仓。1113 行 = 1113 个唯一 SKU×仓，零重复 |
| 跨仓差异 | 37 个跨仓 SKU 中 8 个各仓销量不同 |

⚠️ SQL 取值注意：`单价` 键名含真换行（`*单价\n（元）`），必须写成
`raw_data ->> ('*单价' || chr(10) || '（元）')`。

### 3.2 销量窗口严格单调 → 不是估算值

全量 1113 行 + 另一批次 1226 行，`7 ≤ 30 ≤ 60 ≤ 90` **零违例**。

这是判定「这是平台规范统计的滚动窗口累计销量，而非估算/插值」的决定性证据。若是估算值，长窗口出现回落是必然的。

### 3.3 DOS 分档（可用库存口径）

| DOS-90 档 | 行数 | 货值 | 占比 |
|---|---|---|---|
| A < 30 天（快断货） | 30 | ¥9,886.54 | 4.4% |
| B 30–90 天 | 84 | ¥48,504.97 | 21.3% |
| C 90–180 天 | 93 | ¥36,779.27 | 16.2% |
| D ≥ 180 天（重度积压） | 161 | ¥95,123.31 | 41.9% |
| 不可算（零销量 / 无库存） | 745 | ¥36,906.48 | 16.2% |

总货值 ¥227,200.57（有库存行）。

库存总量口径与可用库存口径的差异极小（DOS<30：32 vs 30；DOS≥180：164 vs 161），**建议用可用库存**（真实可售、可调拨的部分更贴近补货决策）。

### 3.4 DOS-30 与 DOS-90 的交叉（可用库存口径，294 行两档都可算）

| DOS-30 ＼ DOS-90 | <30 | 30–90 | 90–180 | ≥180 |
|---|---|---|---|---|
| **<30** | 24 | 13 | 0 | **0** |
| **30–90** | 4 | 42 | 24 | 10 |
| **≥90** | 1 | 25 | 53 | 98 |

两条可直接用于产品设计的结论：

1. **不矛盾**：DOS-30 判「<30 天」的 37 行，在 DOS-90 口径下没有一行落到 ≥180 天。30 天口径不会把快断货误判成重度积压。
2. **1 行反直觉信号**：DOS-30 ≥90 但 DOS-90 <30 → 近 60–90 天有一波集中动销，30 天窗口已回落。这行是「近期动销过」，需要单独标记，不能当滞销。

### 3.5 零销量必须独立标记

| 项 | 实测 |
|---|---|
| 近 90 天销量 = 0 的行 | 673 行（含无库存行） |
| 其中有库存 | **141 行**（可用库存口径 138 行） |
| 零销量积压货值 | ¥36,477.36 |
| 仓库分布 | 新加坡 92 / 马来仓 31 / 菲律宾3店-时尚箱包 10 / 菲律宾仓库（维修工具）5 / 菲律宾1店-儿童书包 3 |
| s30=0 但 s90>0 | 74 行有库存 → **30 天口径会把它们误判为滞销** |

→ 零销量**不得**塞成 9999 哨兵，必须独立成状态标签（`zero_sales` / `no_stock` / `computable`）。

### 3.6 30 天窗口的误判风险

两档 DOS 相差 ≥30 天的行：**179 行**（库存总量口径）/ 177 行（可用库存口径）。30 天窗口对「三个月前卖过、近期没动」的商品会直接判成滞销，而 90 天窗口能识别出来。

→ **滞销判定用 DOS-90；DOS-30 只作补货信号与辅助列。**

## 4. 展示层：口径 ≠ 分档

两个容易在页面上被读错的地方，必须在设计时分开：

| | 是什么 | 呈现 |
|---|---|---|
| **口径（窗口）** | DOS-30 / DOS-90：销量取多长的窗口 | 表格**列** |
| **分档（严重度）** | <30 / 30–90 / 90–180 / ≥180：库存有多久没卖掉 | **状态标签 / 色阶**，不编码进数字 |

- 现有 `estimated_turnover_days >= 30/60/90` 的切法是严重度分档，**与 DOS-30 的「30」不是一回事**。顶部三卡当前 30/60/90 三个数字完全相同（217787.41），就是因为三个切点切的是同一个值且被 9999 哨兵污染 → 改造时去掉 60 天+ 这张假卡。
- 页面上不要出现「DOS-30 更严重 / DOS-90 更宽松」这类暗示。列头写 `DOS-30` / `DOS-90`，列头 tooltip 写「按近 30 天销量窗口计算的周转天数」，卡片副标题写「DOS 基于妙手库存清单的平台销量统计（30/90 天窗口）」。

## 5. 实现要求（供后续批次执行）

1. **语义层需暴露销量列**：`semantic.fact_inventory_snapshot` 目前**没有**任何 sales 列，`mart` 层只有 `daily_avg_sales`（来自订单口径）。落地 DOS 必须在语义层把 4 个销量窗口投影出来。
2. **唯一实现**：DOS 计算收敛到一处（纯函数 + 唯一取数路径），滞销模块与商品中心最低售价都调它。沿用 `product_pricing_query_service` 的既有纪律。
3. **禁止哨兵**：DOS 不可算时返回 NULL + 独立状态标签，不允许 9999。
4. **改名清单**（滞销模块改造时）：对外字段 `estimated_turnover_days` → `order_dos_sales30`；新增 `checklist_dos_sales30` / `checklist_dos_sales90`；新增 `checklist_sales_30d` / `checklist_sales_60d` / `checklist_sales_90d`（近 90 天销量，供展示）。
5. **指标词典登记**：按 `sea-metrics-language` 的强制流程，`checklist_dos_sales30/90` 需登记进 `references/metrics-dictionary.md`（口径、公式、来源、适用范围、能证明什么、不能证明什么）与 `references/metric-status.md`（状态 `observe`）。⚠️ 该 skill 在仓库里有两份内容完全相同的副本（`team-skills-bundle/` 与 `docs/team-skills/`），改动需同步两份。

## 6. 六项待拍板事项 · 建议稿（2026-10-24 补充实测）

以下建议已用真实数据核算，可直接作为实施规格。

### 6.1 DOS 分档阈值 → 建议 90 / 180 两档进榜，<30 判快断货不进榜，零销量单独一档

滞销榜（可用库存 + DOS90）的完整构成：

| 档 | 行数 | SKU | 货值 |
|---|---|---|---|
| 重度积压 DOS ≥ 180 | 161 | 161 | ¥95,123.31 |
| 中度滞销 DOS 90–180 | 93 | 93 | ¥36,779.27 |
| **零销量积压**（近 90 天销量 = 0 且有库存） | 138 | 138 | ¥36,411.48 |
| **合计进榜** | **395** | **395** | **¥168,379.94** |
| （不进货）30–90 天 | 84 | 84 | ¥48,504.97 |
| （不进货）< 30 天 快断货 | 30 | 30 | ¥9,886.54 |

**零销量必须进榜，且排在最前**：它是「90 天完全没卖」，比 DOS ≥ 180 更严重。

⚠️ **不能沿用现有的「不可算 → 回落最小档」逻辑**：`select_age_tier` 在 `age_days is None` 时回落到 `min_age_days` 最小的一行（日常档）。按此逻辑会有 **708 个 SKU 落进日常档，其中 138 个是零销量有库存**（1597 件、货值 ¥36,411）——最该清的货反而享受日常折扣 0.10。这是本次必须一并修掉的错配。

### 6.2 DOS 库存口径 → 建议可用库存

- 两种口径差异极小：DOS<30 为 32（总量）vs 30（可用）；DOS≥180 为 164 vs 161
- 理由：DOS 回答「还能卖多少天」，分母是真实卖出的量，分子应取可售的部分——预占与次品本就卖不掉，不该算进「还能卖多久」
- **货值仍用库存总量**（压着的钱包含预占与次品）
- 与现状一致：`mart.inventory_backlog_base` 的分子用 `available_stock`、金额用 `inventory_value`

### 6.3 商品中心最低售价 → 建议 DOS-90，但必须同时做三件事

**先说一个必须先修的问题**：`finance.sku_pricing_policies` 的列名与标签本身就错位——

| `min_age_days` | `tier_label` | `discount_rate` | `target_margin_rate` |
|---|---|---|---|
| 0 | 日常 | 0.10 | 0.25 |
| 60 | 滞销30天 | 0.15 | 0.22 |
| 90 | 滞销60天 | 0.20 | 0.18 |
| 120 | 滞销60天以上 | 0.30 | 0.10 |

档位按「库龄门槛」存，标签写的是「滞销天数」。换成 DOS 后错位更荒谬（`min_age_days` 变成 DOS 门槛、标签仍是滞销天数）。

**三件事**：

1. **列名改**：`min_age_days` → `min_dos_days`（否则「age」与 DOS 永远分不清）
2. **阈值重标定**：现 0/60/90/120 是库龄 → 建议改 **0/30/90/180**，与滞销模块对齐。实测命中数：沿用 60/90/120 → 285 / 254 / 214 个 SKU；改后 30/90/180 → 338 / 254 / 161
3. **零销量有库存 → 最深滞销档**（138 个 SKU）

落档结果（1076 个库存快照 SKU）：

| 档 | SKU | 说明 |
|---|---|---|
| 日常 | 600 | DOS<30 的 30 + 零销量无库存 495 + 无库存但有销量 75 |
| 滞销档1（DOS 30–90） | 84 | |
| 滞销档2（DOS 90–180） | 93 | |

### 4.8 滞销判据：库存停滞时长（取代 DOS 做判据）

**信号定义**：


**为什么它比 DOS 更适合当判据**（全部实测，file 3004 / 1113 行）：

| 维度 | DOS（库存 ÷ 近90天销量） | 库存停滞时长 |

- **单调性成立**：DOS 判「快断货 / 30-90」的行里，**没有一行**是停滞 ≥ 180 天的

### 2.5 DOS 的两个层级：SKU 级（定价用）与仓级（运营用）

DOS 是 SKU×仓 粒度的证据，但定价动作是 SKU 级的。因此 DOS 唯一实现必须同时输出两个层级：

| 层级 | 算法 | 用在哪 | 理由 |
|---|---|---|---|
| **SKU 级** | `Σ各仓可用库存 ÷ (Σ各仓近N天销量 ÷ N)` | 商品中心最低售价选档 | 定价是全国一价，一个 SKU 一个档 |
| **仓级** | 每仓独立 `该仓可用库存 ÷ (该仓近N天销量 ÷ N)` | 滞销模块展示、调拨建议、豁免判定 | 运营动作（清仓/调拨/补货）都是仓级的 |

## 3. SKU 级定价 vs 仓级库存：矛盾与解法

### 3.1 矛盾是什么

最低售价是 **SKU 级** 的（一个 SKU 一个价、一个底线），改价通知也是 SKU 级的（`ops.price_adjust_baselines` 按 `sku_id`）。但库存证据是**仓级**的。

于是出现：某 SKU 在 A 仓压着货卖不动（该降价清货），在 B 仓却缺货（不该降价、该补货甚至该提价）。**一个价，服务两种相反的诉求。**

### 3.2 实测：矛盾真实存在，但范围极小

库存状态三分（file 3004，1113 行）：

| 状态 | 行数 | SKU |
|---|---|---|
| 无货无销量（未铺货） | 541 | 518 |
| 可算（DOS 有值） | 368 | 368 |
| 有货零销量（最滞销） | 138 | 138 |
| **无货但有销量（真缺货）** | **66** | **66** |

37 个多仓 SKU（全部跨 2 个仓）的结构：

- **26 个**：两仓都无货 —— 记录占位，不是真多仓经营
- **11 个**：1 仓有货 + 1 仓无货
- **0 个**：两仓**同时有货**

**唯一命中「积压 + 真缺货」的 SKU**：

| SKU | 仓库 | 可用库存 | 近90天销量 | 状态 |
|---|---|---|---|---|
| `HKR-LRI9-Squeezer-035` | 新加坡 | **0** | 5 | **真缺货**（卖得动却没货） |
| | 菲律宾仓库（维修工具） | **215** | 6 | **DOS 3225 天**，重度积压 |

合并口径下：`215 ÷ (11 ÷ 90) = 1759 天` → 判重度积压 → **会触发降价通知**。这正是 Walter 描述的场景。

### 3.3 为什么正确解法是「调拨」，不是「降价」

- 降价解决不了缺货 —— B 仓没货可卖，降价只会拉低它**补货之后**的毛利
- 调拨能同时解决两件事：A 仓的货搬到 B 仓，A 仓积压解除、B 仓缺货解决
- 「最低售价」是**底线**不是实际售价，所以降价的代价是延迟发生的毛利损失

### 3.4 解法：SKU 级判档 + 仓级豁免

沿用仓库既有原则——`price_adjust_notify_service.is_delisting_jump` 已确立「**语义上不成立的变更不该通知**」，本次是同一条原则的第二个应用。

**规则**：SKU 级 DOS 判滞销时，若该 SKU **存在任何一个仓**处于「有销量但无库存（真缺货）」或「DOS < 30（快断货）」，则**档位封顶在次深档**，不进入最深折扣档。

理由：
1. 缺货说明这个 SKU 还有市场 —— 压着的货可以用调拨解决，不必用降价
2. 降价对缺货仓是纯损失（无货可卖），对补货后是毛利损失
3. 与「零销量 → 最深档」并不冲突：零销量仓的货是死的，缺货仓的货是活的

**配套三件事**：

1. 改价通知的「变动原因」新增一条 `仓级缺货豁免`（飞书「调价记录表」的单选选项需同步加一项）
2. 滞销模块对「同 SKU 一仓有货、一仓缺货」的行给出**调拨建议**，而不是只给降价
3. 豁免判定与 DOS 计算**同源**（同一个唯一实现输出仓级明细），不允许各写一套

### 3.5 被排除的方案

| 方案 | 为什么不做 |
|---|---|
| 仓级定价 | 跨平台电商定价是 SKU 级，妙手无此能力 |
| 完全按「最差仓」判档 | 数学上更保守，且**解决不了**矛盾；实测与合并口径判定一致，无收益 |
| 只提示不自动改价 | 放弃了本可以自动化的清货收益；但作为豁免后的兜底保留（人工覆盖 `min_selling_price_override` 已存在） |

## 4. DOS 唯一实现：分层、取值、计算、使用

### 4.1 数据链路

```
妙手「仓库清单」页导出
  └─ b_class.fact_miaoshou_inventory_snapshot     物理表，raw_data jsonb 内含「近7/30/60/90天销量数据」
       └─ semantic.fact_inventory_snapshot          视图  ★ 新增 4 个销量列 + observed_at / created_at
            └─ mart.inventory_snapshot_latest       视图  ★ 排序键改 observed_at（分区键已是 SKU×仓）
                 └─ inventory_dos_query_service    唯一取数  ★ 新建
                      └─ inventory_dos_service     唯一计算  ★ 新建（纯函数）
                           ├─ 滞销模块（仓级明细）
                           ├─ 商品中心（SKU 级）
                           └─ 最低售价变更通知（SKU 级 + 仓级）
```

**为什么落点是 `mart.inventory_snapshot_latest`**：它的分区键已经是
`(platform_code, platform_sku, product_sku, warehouse_name)`，即**每 SKU×仓 取最新一行**，
正是 DOS 需要的粒度；且它带 `product_sku`（可关联 `core.dim_erp_sku.sku_key`）、
`available_stock` / `on_hand_stock` / `inventory_value` / `unit_cost`。

### 4.2 SQL 层只放「原子事实」，不做除法

这是守住唯一性的第一道闸：**DOS 的除法不在 SQL 里做**。

现状隐患：`mart.inventory_backlog_base` 就是 SQL 里算 `estimated_turnover_days`（还带 9999 哨兵），
一旦滞销模块和商品中心各自再算一次，就是两份口径。本次要把这层拆掉。

语义层新增（照 `sql/semantic/inventory_snapshot.sql` 既有的数值清洗写法）：

```sql
-- 妙手库存清单自带的销量窗口。键名无 * 前缀。
-- ⚠️ 缺失必须落 NULL 而不是 0：shopee/tiktok 的 raw_data 没有这些列，
--    落 0 会被当成「零销量积压」误判成滞销。
CASE WHEN raw_data ? '近30天销量数据'
     THEN NULLIF(REGEXP_REPLACE(COALESCE(raw_data->>'近30天销量数据', ''), ',', ''), '')::numeric
     ELSE NULL END AS checklist_sales_30d,
-- 60/90 天同理
```

「销量列缺失」与「销量为 0」必须可区分：前者 = 不可算，后者 = 零销量。

#### 4.2.1 可用库存的来源与清洗链

| 环节 | 事实 |
|---|---|
| 页面 | 妙手「仓库清单」页的「可用库存」列 |
| 落盘 | `b_class.fact_miaoshou_inventory_snapshot` 平铺列 `可用库存`（text）+ `raw_data` 同名键 |
| 语义层取值 | `COALESCE(raw_data->>'可用库存', raw_data->>'available_stock', raw_data->>'Available Stock', raw_data->>'available') AS available_stock_raw` |
| 语义层清洗 | 去逗号 / 去空格 / 去全角字符 → `NULLIF(...,'')::numeric`；最外层 `COALESCE(available_stock, 0)` |
| 原始形态 | 1113 行：null=0、空=0、零=597、**负=10**（含非数字字符的也是这 10 行） |
| 自洽性 | **库存总量 = 可用库存 + 预占库存，1113 行全部成立（0 行不等）** |

⚠️ 语义层最外层的 `COALESCE(available_stock, 0)` 会把「字段缺失」和「真的是 0」**洗成同一个值**。
这不影响 DOS 判定——`stockout`（真缺货）只依赖 `sales_90d > 0`，销量列是独立的，缺失可辨。

#### 4.2.2 窗口销量的来源与「新鲜度」风险（重要）

| 环节 | 事实 |
|---|---|
| 页面 | 妙手「仓库清单」页的「近7/30/60/90天销量数据」四列 |
| 落盘 | 平铺列 + `raw_data` 同名键（**无 `*` 前缀**，与 `*商品SKU` 不同命名空间） |
| 字符形态 | 1113 行：含非数字=0、空=0、NULL=0 → 纯数字字符串，防御性清洗即可 |
| 语义 | 全整数、非负；`7 ≤ 30 ≤ 60 ≤ 90` **1113/1113 零违例** → 是规范的时间窗口累计销量 |

**★ 关键发现：妙手的销量是「行级存储快照」，只有行被写入才会刷新。**

实测（file 2764 vs 3004，两批共同 1109 个 SKU×仓）：

| 现象 | 行数 |
|---|---|
| 销量变了 | 420 |
| 「更新时间」变了 | **1109（全部）** |
| **只变销量、更新时间没变** | **0** |
| 只变更新时间、销量没变 | 689 |

即：**行被修改时，妙手会同时刷新销量窗口；行没被改时，销量值原封不动。**

**实时页面复验（2026-10-24 晚间，CDP 探针）**：同一筛选条件（更新时间维度 2026-09-01~10-08）
连查两次、中间静置 30 秒、不做任何业务操作 → **20 行的更新时间 / 创建时间 / 库存总量 / 可用库存 /
近90天销量逐字相同**。→ 「更新时间」是稳定的行级存储字段，**不是每次查询刷新的**。

⚠️ **但「行被修改」≠「库存数量变了」**：1109 共同行里 **93 行（8.4%，货值 ¥13,560.33）库存数量
完全没变、销量却变了**（销量差 −62 ~ +10，中位 −1）。说明妙手在**非库存变动**的操作
（批量编辑、改价、盘点等）时也会刷新行的销量列。

⚠️ **「更新时间变了」也不能直接当成业务变更**：file 2764 有 **535 行（43.7%）的更新时间被一次性
批量写成 `2026-05-08 10:36:36~39`**（4 秒窗口，一次 bulk UPDATE），而同样这些行在 file 3004 里
各自是真实更新时间（其中 136 行等于创建时间 = 从未修改）。→ **变更判定必须由我们自己比对行内容
（库存数量/销量），不能只信妙手的「更新时间」语义。**

按「更新时间」新鲜度分桶看销量（file 3004，**该批是全量采集**）：

| 更新时间 | 行数 | 有销量行 | 平均近90天销量 | 零销量有货 | 货值 |
|---|---|---|---|---|---|
| 当天（10-24） | 28 | 26 | 47.96 | 1 | ¥195.00 |
| 近 4 天 | 172 | 162 | 21.13 | 4 | ¥231.50 |
| 10 月 | 185 | 156 | 8.93 | 10 | ¥1,583.50 |
| 9 月 | 114 | 68 | 1.64 | 9 | ¥4,427.00 |
| 更早 | 614 | **28** | **0.12** | 114 | ¥29,974.48 |

**这正是增量采集要面对的风险**：增量只抓「更新时间」落在水位线之后的行，其余行的销量停留在旧值。

**⚠️ 2026-10-24 晚间修正：原来那句「实测偏差规模：可忽略」是错的，已作废。**
错在哪：上面这张分桶表是在**全量采集**的批次上量的——全量采集时**每一行的销量都是当次采到的
真值**，所以「更新时间久远但销量非 0」只有 28 行、货值 ¥4,823.52，DOS 全部落在 90~2160 天，
「会逃出滞销榜 0 行」。**这个结论只在全量采集下成立。**

**增量模式下这个前提不成立**（详见 §4.2.4）。

#### 4.2.4 增量模式下 DOS 的实测偏差（2026-10-24 晚间新增）

**基线事实**：当前筛选（更新时间维度 2026-09-01~10-08）实际返回 **SKU 总数 151**，
全量是 **1113 行 / 56 页** → **增量批次只覆盖约 13.6% 的 SKU**，
其余 **86.4% 的行，库存和销量都停留在上一次全量采集的那一刻**。

**模拟**：拿已入库的两个批次（A=file 2764 早，B=file 3004 晚）模拟增量模式——
「库存数量变过的行」用 B 的销量（会被重新采集刷新），其余行沿用 A 的销量（陈旧），
与「全量模式全部用 B 的销量」对比 DOS90 判档：

| 指标 | 结果 |
|---|---|
| 判档不一致 | **56 / 1109 行（5.0%）**，货值 ¥8,390.18（占总货值 3.7%） |
| 滞销漏判（全量算滞销、增量不算） | **37 行，货值 ¥2,164.18** |
| 滞销误判（全量不算滞销、增量算） | 3 行，货值 ¥0.00 |
| 「库存没变但销量变了」（增量必然漏掉的刷新） | **93 行（8.4%），货值 ¥13,560.33** |

档位迁移（全量 → 增量）Top：`不可算 → 快断货(<30)` 28 行、`不可算 → ≥180` 12 行、`≥180 → 90-180` 6 行。

**这还只是两次采集相隔 2.5 天的误差**，而且方向不确定（漏判 37 行 / 误判 3 行）。

**按陈旧程度分桶（模拟 2.5 天后的判档差异率）**：

| 更新时间距采集日 | 行数 | 货值 | 漏刷新行 | 判档差异行 | 差异率 |
|---|---|---|---|---|---|
| ≤ 7 天 | 251 | ¥137,278.23 | 13 | 7 | 2.8% |
| 8–30 天 | 194 | ¥39,751.63 | 14 | 7 | 3.6% |
| 31–90 天 | 88 | ¥22,064.23 | 37 | 13 | 14.8% |
| 91–180 天 | 90 | ¥8,566.40 | 29 | 29 | **32.2%** |
| > 180 天 | 486 | ¥16,242.08 | 0 | 0 | 0%（全是零销量死行，分母恒为 0） |

→ **行越陈旧，判档越容易翻**。增量模式长期运行时，陈旧行持续累积，
误差随「距上次全量刷新的时长」放大，不会收敛。

**结论（取代原结论）**：

1. DOS 的**分母（近 N 天销量）不是自己会更新的数据**，它是「上次这行被写时」的窗口值。
2. **增量批次产出的 DOS 不能直接当滞销判据**——它只对本次采集到的 13.6% 行是新鲜的。
3. ⚠️ **2026-10-24 晚间修正**：本条原写「DOS 必须以全量刷新为前提」——
   **采集策略已定为不再全量**，该前提不成立。DOS **降级为参考值，不做全域使用**（§6.6）。
   滞销判据改用**库存停滞时长**（§4.8）。
4. 「增量查不出删除/下架」这条风险**因为不再全量而变得更要紧**：
   增量永远看不到被删除/下架的 SKU → 状态层会残留幽灵行、库存价值可能虚高。
   必须用别的手段兜（见增量设计稿 §6.3 的替代方案）。

#### 4.2.3 顺带发现：当前库存域采集**没有切「更新时间」维度**

| config | domains | date_range_type | 区间 |

```python
def compute_dos(
```

### 4.4 取数层（唯一取数）

新建 `backend/services/inventory/inventory_dos_query_service.py`，**结构照抄
`inventory_age_query_service.py`**（同仓库既有样板）：

```python
async def load_current_checklist_dos(db: AsyncSession, sku_ids: list[int]) -> dict[int, dict]:
    """按 product_sku -> core.dim_erp_sku.sku_key 关联，取仓级明细。

    返回 {sku_id: {"warehouses": [...], "sku_dos_30": ..., "sku_dos_90": ...,
```

容错纪律**照抄既有样板，一条都不能省**：
1. 先 `SELECT to_regclass('mart.inventory_snapshot_latest')` 探测——不存在就**根本不发出**那条会失败的查询
2. 万一查询仍失败，用 `db.begin_nested()` 开 SAVEPOINT 包住，异常只回滚到保存点
3. **必须留日志**：表不存在 / 列改名 / 权限不足 / 类型推断失败全部退化成同一种「无 DOS 数据」，

⚠️ 绝不能用 `try/except` 包裸查：PostgreSQL 里一条语句失败会让**整个事务 aborted**，

### 4.6 五道闸，保证「唯一」

| # | 闸 | 说明 |
|---|---|---|
| 1 | **结构保证** | DOS 计算函数只有一个定义，三处 import 它——不是靠测试保证，是靠 import 保证 |
| 2 | **SQL 层禁止算 DOS** | 语义层只暴露原子事实，除法只在 Python，杜绝「视图里一份、代码里一份」 |
| 3 | **口径只写一处** | `inventory_dos_service.py` 的 docstring 是唯一定义处，其他地方引用不复述 |
| 4 | **测试门禁** | 单测断言 `compute_dos` 输出 == 用真实数据算出的值；改了公式测试就红 |
| 5 | **指标词典** | 口径登记进词典（两份副本同步），其他 agent 读到就知道去哪调 |

### 4.7 降级链（照既有纪律）

| 情况 | 处理 |
|---|---|
| DOS 读不到（表不存在 / 查询失败） | 回落第 1 档（日常）+ **记日志** |
| 销量列不存在（shopee / tiktok） | DOS = None，状态 = 不可算 → 回落日常档 + 标记来源缺失 |
| 销量列存在但为 0 | **不是回落**——进 `zero_sales`，按规则进最深档 |
| 库存缺失 | DOS = None，状态 = `no_stock` |

⚠️ 最后两行是本次的关键修正：**零销量不能再走「算不出 → 回落日常档」**。
按旧逻辑会有 708 个 SKU 落进日常档，其中 138 个是零销量有库存（1597 件、货值 ¥36,411）——
最该清的货反而享受日常折扣。
