## 1. 要解决的业务问题

### 1.1 现状

商品中心目前给了运营两样东西：

- **最低售价** —— 这个 SKU 最低能卖多少钱（成本线 / 纪律线 / 人工覆盖三者取大）
- **让利档位** —— 当前库龄档允许让多少、清货最多让多少（`current_discount_rate` / `clearance_max_discount_rate`）

但**没有给广告投放的任何指引**。运营在平台上看到的是 GMV MAX 的「目标ROI」和后台的「实际ROI」（平台报告值，含自然与达人归因），商品中心里既没有 ROI 的下限（低于多少就是亏），也没有建议值（该设多少）。这导致：

- 投放决策靠拍脑袋，或者干脆不投
- 最低售价只解决了「价格不能低于多少」，没解决「广告能花多少」

### 1.2 阻塞点：广告费率的语义是反的

商品中心现有的「广告费率」字段（`expected_ad_rate`）语义是：

```
广告费用 = 广告前利润 × 广告费率      ← 分母是「广告前利润」
```

而业界（Shopee / TikTok GMV MAX / Amazon）说的「广告费率」「ACoS」是：

```
广告费用 = 销售额 × 广告费率          ← 分母是「销售额」（平台 GMV = 商家实收）
```

同一个「20%」，两边实际投放强度差 `1/p` 倍（`p` = 广告前贡献毛利率）。**这个字段运营观测不到**——平台后台给的是 ROI，不是「广告前利润的分配比例」。

### 1.3 本 spec 的目标

**先把业务概念定死，再谈优化。** 分两半：

1. **§2–§5：概念基线** —— 术语定义、口径矩阵、命名决策、现存概念断裂清单。这部分是**结论**，后续任何 agent 看到字段名就知道它算的是什么、依据是什么、能不能进结论。
2. **§6–§13：优化方案** —— 在概念基线之上的分阶段实施路径。这部分可以按阶段独立排期。

### 1.4 非范围

- **不做价格弹性 / 销量预测**（§5.3 有详细说明，这是结构性缺口，单独立项）
- **不改 `other_cost_rate` 的黑桶结构**（拆明细是 V2，本 spec 只要求它不再被误读）
- **不改历史利润版本数据**；新旧口径并存，需在报表标注
- **不碰库存域（滞销榜 / 补货 / 库龄）的口径**，只在它消费商品中心数据的地方加标记
- **不做飞书投影字段变更**（除非 §6 阶段 1 明确列出）
- **不迁移已有 `sku_pricing_policies` 数据**

## 2. 术语基线

> 本节是**规范**。后续文档、代码注释、UI 文案、指标字典一律以此为准。

### 2.1 商品身份

| 概念 | 实体 | 标识 | 维度 | 谁维护 |
|---|---|---|---|---|
| **SPU** | `core.dim_spu` | `spu`（公司款号） | 公司 | 业务人员 |
| **ERP SKU** | `core.dim_erp_sku` | `sku_key`（唯一） | 公司 | 业务人员 |
| **平台 SKU** | `core.dim_products` / `core.dim_shops` | `platform_sku` | 平台 × 店铺 | 采集 |
| **SPU-SKU 归属** | `core.bridge_spu_sku` | 有效期历史表 | SKU | 业务人员 |
| **SKU 别名映射** | `core.bridge_erp_sku_keys` | 有效期历史表 | SKU | 采集 |
| **经营档案** | `finance.sku_operating_profiles` | SKU × 平台 × 仓 | 场景 | 运营 |

**规范条款**

- **SPU-SKU 归属是历史表不是外键。** 改绑 = 关旧行（`effective_to` + `binding_status='historical'`）+ 开新行。`effective_from` 必须晚于当前绑定，否则 422。部分唯一索引 `uq_bridge_spu_sku_current` 保证一个 SKU 同时只有一个 active 绑定。
- **SPU 承载公司侧的品类与两个风险率**：`logistics_damage_rate`（物流货损率）、`return_loss_rate`（退货损失率）。这两个率是成本线的输入，**属于 SPU 级，不属于 SKU 级**。
- **经营档案是场景值**：`sku_operating_profiles` 按 (sku_id, platform_code, warehouse_code) 唯一（`uq_sku_operating_profile_current`），存的是"这个品在这个平台这个仓怎么卖"。

### 2.2 价格概念

这是本次最需要钉死的一组。

| 概念 | 字段 | 维度 | 回答什么 | 谁定 |
|---|---|---|---|---|
| **基准售价** | `dim_erp_sku.reference_selling_price` | SKU | **不打折时的日常售价**（吊牌价） | 一次性维护，带来源与确认日期 |
| **测算售价** | `sku_operating_profiles.expected_selling_price` | SKU × 平台 × 仓 | **本次测算假设的成交价** | 运营每次填 |
| **成本线** | 派生 | SKU（公司口径） | 低于它就在亏本 | 系统算 |
| **纪律线** | 派生 | SKU（公司口径） | 低于它就超出折扣权限 | 系统算 |
| **最低售价** | 派生（不落库） | SKU（公司口径） | 三者取大 | 系统算 |
| **人工覆盖** | `dim_erp_sku.min_selling_price_override` | SKU | 人工拍板，允许低于成本线 | 运营，有审计 |

**规范条款**

**① 基准售价是「日常售价」，不是「参考值」。**

它承担四个角色：

- 纪律线的唯一基数：`纪律线 = 基准售价 × (1 − 当前档让利率)`
- 测算售价的兜底来源（运营未填时）
- 清货回收金额的基数：`清货回收金额 = 基准售价 × (1 − 清货让利率)`（库存域 `backend/services/inventory/sku_clearance_service.py:525-526`）
- 最低售价变更通知的归因项之一（`price_adjust_notify_service.py:187-189`）

它**不是**可有可无的参考值。当前填充率 **0.36%**（**生产库 1122 个 SKU 仅 4 个有值，2026-11-07 实测**；此前 2026-10-20 的 0.2% / 2 个为开发库口径），导致纪律线对 **99.6%** 的 SKU 不可算 → 最低售价实际全部由成本线单独决定。

> 阶段 2 因此必须为「基准售价缺失」设计降级路径，不能假设它普遍存在。

**② 基准售价必须是常态价。**

不得填促销价、清仓价、大促到手价。基准售价偏高 → 纪律线偏高 → 最低售价被顶高 → 护栏把品拦死；基准售价偏低 → 纪律线偏低 → 成本线兜底（安全）。**填错的最大风险是「货卖不动」，不是亏本。**

**③ 测算售价的来源必须可区分。**

回落发生在**两层**，且两层的落库都把兜底值和运营填的值混成同一个字段：

| 层 | 位置 | 行为 |
|---|---|---|
| 前端 | `ProductCenter.vue:1462` | `row.expected_selling_price ?? row.reference_selling_price` —— **在发请求前就已回落**，后端收到的永远是具体数字，无法分辨来源 |
| 后端 | `product_center.py:2715-2716` | 草稿保存把 `expected_selling_price` **写回经营档案**，兜底值就此变成"档案里的值" |
| 后端 | `product_center.py:2802-2803` | 利润版本落库时再次回落，`expected_selling_price` 与 `selling_price` 存的都是同一个兜底数 |

规范要求：来源标记必须**同时落两张表**——
- `finance.sku_operating_profiles.expected_selling_price_source`（档案自身可解释）
- `finance.sku_profit_estimates.expected_selling_price_source`（历史利润版本可解释）

取值 `operator` / `fallback_from_baseline`。**前端不得在发请求前回落**，应把 `null` 传上去由后端统一回落并打标，否则前端与后端各算一次、标记还会打架。

**④ 最低售价不落库。**

库里只有人工覆盖值。自动值实时计算（`product_pricing_service.py:87-117`）。因此"比上次高了还是低了"这件事需要单独的记忆机制 → `ops.price_adjust_baselines`（§2.5）。

**⑤ 「利润率」统一指净利口径**（利润 ÷ 净收入），**不与「毛利率」混用**。商品中心所有涉及利润率的文案一律用「利润率」。

### 2.3 库龄与折扣权限

| 概念 | 定义 | 来源 |
|---|---|---|
| **库龄** | **距上次进货天数** | `mart.inventory_state.stock_added_at` |
| **档位** | 库龄落在哪个折扣档 | `finance.sku_pricing_policies` |
| **当前让利上限** | 当前库龄档的让利比例 | 档位表 `discount_rate` |
| **清货让利上限** | 最深档的让利比例（公司红线，全 SKU 相同） | 档位表最深行 `discount_rate` |

**规范条款**

**① 库龄 = 距上次进货天数，不是入库至今。**

西虹的经营模式是「卖完不补货、偶尔补货」，货进进来才重新开始计时。数据源 `mart.inventory_state`（`inventory_restock_query_service.py:35-43`），SKU 级**各仓取最长**（只算 `available_stock > 0` 的仓），join 键 `product_sku → dim_erp_sku.sku_key`。

**② 档位由库龄触发，不由 `turnover_class` 触发。**

`turnover_class`（快销 30 / 普通 60 / 慢销 90 天）**只用于参考仓储天数**，与定价无关。它在 1121 个 SKU 里仅 3 个有值，且从未建立过经营分类。

**③ 当前让利上限与清货让利上限不重复。**

一个随库龄变，一个是不变的红线。库龄 ≥120 天时两者重合，**这是预期行为不是 bug**。

**④ 库龄缺失回落到最浅档，且必须标记。**

回落档目标利润率最高 → 底线最保守 → 不会亏本。`pricing_tier_source ∈ {restock_days, fallback_no_restock_days}`。回落只有 warning 日志、无指标，需要补（§6 阶段 1）。

**⑤ 档位边界是可配数据，不是硬编码常量。**

档位键是 `min_restock_days`（库龄起点）而非 `sku_id`，因为底线是公司统一口径，且滞销阈值需要运营可改。规则**只进不退**：每次变更 = 关旧行 + 开新行，历史可追溯。

### 2.4 成本与利润

| 概念 | 定义 |
|---|---|
| **商品金额** | `P` —— 平台上的商品单价（吊牌价） |
| **买家实付** | `B = P − 平台补贴 d − 卖家优惠券 c` —— 买家银行流水里的数 |
| **商家实收** | `G = P − 卖家优惠券 c`（= `B + 平台补贴 d`）—— 商家真正收到的钱 |
| **净收入** | `revenue = 商家实收 G` |
| **广告前利润** | `pre_ad_profit = 净收入 − (采购 + 物流 + 仓储 + 贴单 + 平台佣金 + 达人佣金 + 货损 + 退货)` |
| **广告前贡献毛利率** | `p = 广告前利润 ÷ 商家实收` |
| **广告费用** | `广告前利润 × 广告分成率` |
| **利润** | `广告前利润 − 广告费用` |
| **成本完整度** | `incomplete` / `estimated` / `mixed` / `actual` |

> ⚠️ **`actual` 当前永不可达。** `product_profit_service.py:290-298` 的判定是「实际物流与实际仓储都有才算 actual」，而 `actual_storage_cost` 恒为 `None`（`product_finance_service.py:1116`）——**根本原因是系统里没有仓储费账单**：`LogisticsBill` 的费用构成全是运费（`headhaul/handling/last_mile/freight/customs/delivery/sensitive`），`transport_type ∈ (sea/air/rail)`；`WarehouseStorageRule` 是「CNY/CBM/月」的规则预估，不是账单。所以完整度的实际上限就是 `mixed`。

**三个销售额口径的关系**（必须区分，否则 §2.5 的 ROI 分子分母对不上）：

```
商品金额 P ──减卖家券 c──▶ 商家实收 G = B + d  ← 商家真正收到的钱
                         └─ 平台 GMV 也是这个数
买家实付 B ──减平台补贴 d──▶ ...
```

| 口径 | 谁在用 | 说明 |
|---|---|---|
| **商品金额 P** | 平台佣金基数 | TikTok 按 GMV 收佣金，不看买家实付 |
| **买家实付 B** | 业务概览的「销售额」 | 买家出掉的钱，不含平台补贴回补 |
| **商家实收 G** | **商品中心的「销售额」** | 商家实际收到的钱；**恰等于 TikTok GMV** |

> TikTok 官方口径：**GMV = 买家实付 + 平台补贴**（平台出资的折扣加回，卖家自己的券不加回）。代入上式即 `GMV = B + d = P − c = G`。**所以商品中心与平台后台的 ROI 是同一把标尺。**
>
> 与业务概览的差异只有平台补贴 `d` 一笔（业务概览记买家出的钱，商品中心记商家收到的含补贴回补）。无平台补贴时两者相等。

**规范条款**

**① 成本项清单是穷举的，且各缺项的处理规则不同。**

| 输入 | 缺失时 | 后果 |
|---|---|---|
| 达人佣金率 | **按 0 计** | 利润照算，少扣一笔佣金 |
| 贴单费 | **按 0 计**，标 `label_fee_source='assumed_zero'` | 利润照算 |
| 广告分成率 | **整条链返回 None** | **利润空白**，`completeness='incomplete'` |

> ⚠️ 这三条不一致是有意的，但**必须在 UI 上说得清**。「利润空白」和「利润算少了」的排查方向完全不同。

**② 费率不量化，金额才量化。**

费率只做 `Decimal(str(x))` 转换保留全精度；只有最终金额过 `_money`（`MONEY_QUANTUM=0.01`，`ROUND_HALF_UP`）。费率若也量化，底线基数 0.3333 → 0.3306，底线 28.23 → 28.02。

**③ 存在两个成本宇宙，不可混算。**

| | 最低售价（成本线） | 利润试算 |
|---|---|---|
| 物流 / 仓储 / 平台费 | 全部揉进 `other_cost_rate`（tiktok 0.2727） | **逐项显式计算** |
| 广告 | 含在 `other_cost_rate` 内 | **单列** |
| 成本来源 | 平台平均黑桶（恒等式反推） | 逐 SKU 规则（服务商规则 / 仓储规则 / SKU 尺寸） |
| 维度 | 公司统一（`platform_basis` = tiktok） | SKU × 平台 × 仓 |

实测差异（同一天、同 SKU）：某 SKU 在最低售价处，利润试算算出的净利率比成本线承诺的高出约 24 个百分点——因为成本线用平台平均成本率，而该品逐 SKU 的运费+仓储+贴单只有 2.1%。

> **两个数都不是错的，但不是同一个宇宙。UI 必须分别标注口径，禁止互相代入。**

**④ `confidence_level` 的真实语义是「采购成本人工置信度」**（取自 `dim_erp_sku.purchase_cost_confidence`），与利润本身的置信度无关。命名需在文档中说明。

**⑤ `cost_completeness` 当前有两套取值域混用**（`complete/partial/incomplete` 与 `incomplete/estimated/mixed/actual`），必须统一。

### 2.5 广告与 ROI

这是本次新增的术语组。

| 概念 | 定义 | 维度 | 谁给 |
|---|---|---|---|
| **广告前贡献毛利率** | `p = 广告前利润 ÷ 商家实收` | SKU × 平台 × 仓 | 系统算 |
| **保本ROI** | `商家实收 ÷ 广告前利润 = 1 ÷ p` | SKU × 平台 × 仓 | 系统算（财务硬底线） |
| **建议ROI** | `min(保本ROI × (1 + 安全边际), 50)`，安全边际默认 20% | SKU × 平台 × 仓 | 系统算（财务目标） |
| **目标ROI** | 打算填进 GMV MAX 的数 | 计划 | 运营填 |
| **平台报告ROI** | 后台跑出来的数 —— **含自然流量与达人归因** | 事实 | 运营抄 |
| **真实广告ROI** | 平台报告ROI 剔除自然流量基线与达人GMV后的数 | 事实 | 目前无人算 → 商品中心的增量价值 |
| **等效目标ROI** | `保本ROI ÷ 广告分成率` —— 把「广告费率」翻译成平台语言 | SKU × 平台 × 仓 | 系统算（只读，§2.5⑩） |
| **广告分成率** | `广告费用 ÷ 广告前利润` | — | **阶段 3 后由目标ROI派生，只读** |

**规范条款**

**① 保本ROI 就是业界标准公式 `保本ROI = 1 ÷ 毛利率`，其中「毛利率」必须严格限定为「广告前贡献毛利率」。**

AdRate 的内部口径与本仓库**数值等价**（已逐项核对）：

```
AdRate：综合贡献毛利率 = 1 − 货品成本率 − 平台费率 − 达人佣金率
                            − 优惠券承担率 − 退款损耗率 − 履约成本率
本仓库：p = (revenue − 采购 − 物流 − 仓储 − 贴单 − 平台佣金
                     − 达人佣金 − 货损 − 退货) ÷ 销售额
```

数学上等价（`revenue − X = 售价 − (X + 券)`），因为优惠券在两边都是"商家承担"。

**② 三个 ROI 必须分清，不得混用。**

| | 公式 | 回答什么 |
|---|---|---|
| 平台 ROI / ROAS | 归因销售额 ÷ 广告花费 | 平台后台给你的数，**与财务无关** |
| **保本ROI** | 1 ÷ 广告前贡献毛利率 | 低于它，这笔广告在亏钱 |
| 净 ROI | 净利润 ÷ 广告花费 | 真实投资回报 |

行业纪律：**ROAS 高 ≠ 利润好**。保本ROI 的价值恰恰在于把利润结构接回 ROAS 之后。

**③ 保本ROI 与广告分成率互为倒数关系。**

```
平台报告ROI = 商家实收 ÷ 广告费用 = 保本ROI ÷ 广告分成率
```

这条关系是「广告分成率」这一内部量能被外部验证的唯一途径。**注意平台报告ROI 需按 §2.5⑧ 剔除自然/达人归因后才可比。**

**④ GMV MAX 的「目标ROI」不是保本ROI。**

TikTok GMV MAX 自 2026-07-15 起成为 TikTok Shop 广告的强制默认模式，卖家只控制**预算 + 目标ROI + 商品集 + 排期**。平台的目标ROI 档位（保守 300–500% / 稳健 150–300% / 激进 50–150%）是**流量效率目标**，不是盈亏线；平台的 ROI 保护（实际 ROI 低于目标 90% 补发 credits）**也不是净利润保障**——它算的目标 ROI 不包含卖家的账上所有成本。

因此商品中心必须给出**两条线**：财务保本ROI（硬底线）+ 财务建议ROI（目标），并额外提示「平台建议目标ROI 低于你的保本线 → 照着填就是亏的」。这是平台不会告诉商家的信息，是商品中心的增量价值。

**⑤ 基准线存 `ops.price_adjust_baselines`，不放 `dim_erp_sku`。**

自动算出的最低售价不落库，所以需要基线记忆"比上次高了还是低了"。基线不能放 `dim_erp_sku`——该表参与采集机→云端的 `TRUNCATE + 全量重灌`（`scripts/sync_product_center_to_cloud.py:46,241`），放这里会被每次同步抹掉，同步窗口内的真实变化会被静默吞掉。

**⑥ 基线推进必须在投递成功之后。**

ERP 侧只新增不更新，没有"重写旧行"的补救动作。先推基线一旦飞书写失败（限流 / token 过期 / 抖动），那次变化永远检不出。

**⑦ 保本ROI 的分母是「商家实收」，不是商品金额，也不是买家实付。**

这条是 Q1 的结论，理由三条：

1. **与平台同一把标尺。** TikTok GMV = 买家实付 + 平台补贴 = `P − 卖家券` = 商家实收 `G`。所以 `保本ROI = G ÷ pre_ad_profit` 与后台的 ROI 可以直接对照。
2. **稳健性。** 若某平台（如 Shopee）用买家实付 `B` 作 ROI 分子，则 `B < G`，我们给出的保本ROI **偏高** → 要求更严 → **保守、安全**。用商品金额 `P` 则在有卖家券时偏高、在有平台补贴时偏低，两个方向都可能出错。
3. **财务正确性。** 分母是商家真正收到的钱，所有成本项（采购、佣金、货损、退货）都是相对它而言的。

实测：截图那行 `P=70 / c=2 / pre_ad_profit=34.49` → 商家实收 `G=68` → `p = 50.72%` → **保本ROI = 1.97**（商品金额口径会是 2.03）。

> ⚠️ **不要把商品金额口径的数放进 GMV MAX。** 那样会让运营以为自己在按商品金额的标尺设目标，实际平台按 GMV 算，差 3%。

**⑧ 平台报告ROI 达标 ≠ 这笔广告赚钱。**

GMV MAX 用 **7 天点击 + 1 天浏览** 的归因窗口，**把自然流量和达人带货的销售一并计入归因 GMV**。平台自己给的修正公式：

```
真实ROAS = (GMV Max 报告值 − 自然流量基线 − 达人GMV) ÷ 广告花费
```

并且判断"该不该加预算"要看**边际 ROAS**（增量GMV ÷ 增量广告花费），不是平均 ROAS——平均 ROAS 会被存量高 ROAS 订单拉高。

**规范要求**：商品中心的三色判定（§6 阶段 2）若直接用运营抄来的「平台报告ROI」，必须**同时显示归因虚高提示**。否则就是给运营一把更锋利的错刀。

**⑨ 建议ROI 要做上限封顶，封顶值取各平台可填上限的最大值。**

必须区分两个不同的数：

| | 含义 | TikTok | Shopee | 作用 |
|---|---|---|---|---|
| **可填上限**（硬约束） | 平台允许你填的最大目标ROI | **20** | **50** | **封顶用这个** |
| 建议档位（软参考） | 平台/业界推荐的投放档位区间 | 1.5 – 5.0（保守 300–500% / 稳健 150–300% / 激进 50–150%） | 未知 | 只做 UI 提示，**不做硬约束** |

> ⚠️ 初稿把「建议档位」当成了「可填上限」，是错的。可填上限远高于建议档位——**平台允许你填 20，但填 20 基本等于不投**。

```
建议ROI = min(保本ROI × (1 + 安全边际),  全局可填上限)     全局可填上限 = max(各平台可填上限) = 50
```

**只封顶，不封底。** 封底是**掩盖异常**——保本ROI < 1 意味着毛利率 > 100%，要么成本算错、要么有收入补贴，这是该报错的信号，不该被 clamp 藏起来。正常情况下保本ROI ≥ 1（毛利率 ≤ 100% 是物理事实），建议ROI ≥ 1.2，本来就在可填范围内。

**超上限时的处理**：保本ROI × (1+安全边际) > 50 时，给出 50 + 提示「该 SKU 保本ROI 超过平台可填上限，广告空间不足，优先走自然流量/达人」。**仍然要显示未封顶的原值**，让运营看到真实差距。

**安全边际取 20%**（不是 25%）：实测业界 buffer 是**相对百分比 12%–25%**（40% 毛利 → 保本 2.5 → 建议 2.8–3.0；25% 毛利 → 保本 4.0 → +20~25%），行业惯例 20–30%。取 20% 落在下沿，保守。

**⑩ 「广告费率」和「目标ROI」是同一个变量的两种表达，保留两个手填入口是错的。**

这是「广告费率」的来历问题（利润分配法）与 ROI 制的定量关系，**精确恒等，不是近似**：

```
广告费用 = 广告前利润 × s              （s = 广告费率/广告分成率）
目标ROI R = 商家实收 ÷ 广告费用 = 保本ROI ÷ s
⟹ s = 保本ROI ÷ R        ⟹        R = 保本ROI ÷ s
```

所以「我拿多少利润做广告」和「我设多少目标ROI」是**同一个投放决策的两种说法**：

| 运营想表达的（利润分配口径） | 广告费率 s | 等价目标ROI R |
|---|---|---|
| 利润全投广告，净利 0 | 100% | `保本ROI` |
| 拿 80% 的利润做广告 | 80% | `保本ROI × 1.25` |
| 拿 60% 的利润做广告 | 60% | `保本ROI × 1.67` |
| 拿 50% 的利润做广告 | 50% | `保本ROI × 2.0` |

**结论：运营手填的输入只保留「目标ROI」一个。** 理由三条：

1. 平台上填的就是目标ROI，运营手上本来就有这个数 → **手填成本为零**
2. 「广告费占广告前利润的几成」运营在平台后台**永远看不到** → 是个黑箱比例
3. 业界标准（TikTok GMV MAX / Shopee Ads / Amazon ACoS）全是 ROI 制

**代码切换无差异**：现实现 `ad_cost = pre_ad_profit × expected_ad_rate`（`product_profit_service.py:267`），改为 `ad_cost = 商家实收 ÷ target_roi` 后，在 `s = 保本ROI ÷ R` 时**两者恒等**。且代码里的 `revenue` 已是「售价 − 券」= 商家实收（与 §2.4 口径天然一致），**不需要改 revenue 口径**。

**存量数据可无损迁移**：`等效目标ROI = 保本ROI ÷ s`，反解出初值写进 `target_roi`，源标记 `migrated_from_legacy_rate`。开发库现状：`sku_operating_profiles` 3 行全部 `expected_ad_rate = 0.15`，`dim_platforms` **没有广告费率默认列** → 这个 15% 是人工填的，不是系统给的。

**⑪ 「新品拿多少利润做广告预算」这个诉求怎么承接：不新增字段，靠翻译。**

「预算」有两种意思，必须分开：

| 诉求 | 能不能做 | 原因 |
|---|---|---|
| **单均**广告投入多少（这一单我愿意掏多少广告费） | ✅ **自动得到** | `单均广告费 = 商家实收 ÷ 目标ROI`，不需要销量预测 |
| **月度总预算**（这个月我给这个 SKU 多少广告钱） | ❌ **第一版不做** | 摊到单均需要销量预测，而模型结构上不预测销量（§5.3） |

所以**不新增「预算」字段**，而是把「利润分配」的旧直觉翻译给运营看。界面上同时给出：

```
建议ROI 2.36   ← 填进 GMV MAX 的数（已封顶 50）
等效单均广告费  28.81 元
等效单均净利     5.68 元（净利率 8.4%）
```

**「等效单均净利」才是运营真正想看的那个数**（比"广告吃掉 83.5% 的利润"直观得多，而且「参考成本利润 / 利润率」两列已经是它了，不用新增列）。它同时回答了「我准备拿多少利润做广告」和「投完我还剩多少」。

> ⚠️ 注意「安全边际 20%」在业务上的真实含义：目标ROI = 保本ROI × 1.2 ⟹ **广告费吃掉广告前利润的 83.5%，净利只剩 16.5%**。这是数学必然（`1 − 1/1.2 = 1/6`），不是参数设错了。给运营解释「建议ROI」时必须同时给「等效净利」，否则 2.36 这个数会让人误以为留了很多。

## 3. 数据流与计算链路

### 3.1 五层链路

```
① 输入层   公司主数据 + 规则表 + 库存状态 + 运营输入 + 已确认账单
              ↓ 一次批量取齐（循环内不 await）
② 取数层   load_pricing_context + prefetch_platform_sku_profit_inputs
              ↓  纯标量
③ 计算层   定价引擎（成本线/纪律线/最低售价）+ 利润引擎（pre_ad_profit）
              ↓  纯标量
④ 决策层   ★新增★ p → 保本ROI → 建议ROI → 广告费率反解 → 三色判定
              ↓
⑤ 呈现层   最低售价 / 让利上限 / ROI 三线 + 护栏 + 审计 + 飞书投影
```

**现有分层纪律**（必须保持）：

- `product_pricing_service.py` 是**纯函数**（无 ORM、无 DB、无 I/O），所有降级分支、7+1 种 `missing_reasons`、分母 ≤ 0、折扣纪律兜底都在这里
- `product_pricing_query_service.py` 是 **ORM 适配 + 批量取数**
- `product_pricing_query_service.py` 与 `price_adjust_notify_service.py` **必须共用同一条取数路径和同一个计算函数**（口径分叉会导致"页面按日常档显示、通知按滞销档发"）
- `sku_pricing_policy_service.py` 是档位表「当前生效行」的**唯一**读取入口

**本次优化只动 ③（加一个纯函数模块算 ROI）与 ⑤（加列 + 改文案）。②、护栏、审计、投影链路不动。**

### 3.2 口径矩阵

利润测算 tab 的 28 列，按"这个数现实世界里存在吗"分类：

| 类型 | 数量 | 列 | 备注 |
|---|---|---|---|
| **业务事实输入** | 3 | 测算售价、优惠券、竞品价格 | 运营观测得到 |
| **伪输入** | 1 | **广告分成率** | ❌ 运营观测不到 → §6 阶段 3 降级 |
| 规则派生成本 | 9 | 采购成本、预估物流/仓储/贴单费、平台佣金率与金额、达人佣金、货损率、退货损失率 | 逐 SKU × 平台 × 仓 |
| 业务参照 | 7 | SPU / ERP SKU / 商品名称 / 基准售价 / 当前让利上限 / 清货让利上限 / 最低售价 | 公司口径 |
| 结论 | 5 | 预计广告费用、参考成本利润、利润率、混合成本利润、混合成本完整度 | |
| **冗余噪声** | 3 | 物流方式（与顶部筛选器重复）、实际物流、实际仓储（**恒 null**，且系统无仓储费账单） | |

### 3.3 一条线读懂整个链路

```
测算售价（运营填） − 优惠券（运营填） = 商家实收 = 净收入 = 平台 GMV
                                                ↓ 减 采购 − 物流 − 仓储 − 贴单
                                                ↓     − 平台佣金 − 达人佣金 − 货损 − 退货
                                                ↓ 广告前利润（系统算）
                                                ↓
                      广告前利润 − 广告费用(= 商家实收 ÷ 目标ROI) = 利润（系统算）
```

**运营只需要回答三个问题，系统回答其余：**

| 运营的三个问题 | 答案列 | 谁算 |
|---|---|---|
| 最低能卖多少？ | 最低售价 | 系统（成本线/纪律线取大） |
| 我能让多少？ | 当前让利上限 / 清货让利上限 | 系统（档位表） |
| ROI 设多少？ | 保本ROI（底线）/ 建议ROI（**已按平台可填上限封顶**） | 系统 |

**折扣与 ROI 是同一笔钱的两个切法**：折扣切售价，广告切利润；底线是切完之后利润还得够。

**两条必须跟着答案一起出现的提示**（否则答案会被误用）：

1. 「本表不预测销量」——提价掉量模型看不见（§5.3）
2. 「平台报告ROI 含自然/达人归因，达标 ≠ 赚钱」——后台的数不是利润数（§2.5⑧）

### 4.2 三条命名原则

**① 名字要描述"这个量是什么"，不是"我们怎么用它"。**

反例：「参考售价」描述的是"我们拿它当参考"；正例：「基准售价」描述的是"它是计算基准"。

**② 同一个量在全系统只能有一个名字。**

当前 `clearance_max_discount_rate` 在 SKU 资料 tab 叫「滞销可优惠」、在利润测算 tab 叫「清货极限」；`current_discount_rate` 在两个 tab 叫法也不一致。

**③ 层级必须写在名字里。**

同一张逐 SKU 表里混着 SKU 级（达人佣金率）、SPU 级（货损率、退货损失率）、平台级（平台佣金率）、公司级（最低售价）四种层级，不标注层级必然被误读。

| 禁用词 | 为什么禁 | 改用 |
|---|---|---|

### 5.3 结构性缺口：模型不预测销量

**这是本次最重要的认知边界，必须写进 UI。**

设售价 P、优惠券 c、商家实收 G = P−c、固定成本 F、比例成本率 s、目标 ROI = R：

```
利润(P) = G(1−s) − F − G/R
d(利润)/dP = (1−s) − 1/R
```

**结论：只要目标ROI ≥ 保本ROI，模型永远会说「提价增利」。**

证明：`保本ROI = G ÷ pre_ad_profit = G ÷ (G(1−s) − F)`，而

```
保本ROI > 1/(1−s)
⟺ G(1−s) > G(1−s) − F
⟺ F > 0   ✓ 恒成立
```

故 `R ≥ 保本ROI > 1/(1−s)` ⟹ `d利润/dP > 0` 恒成立。

**这意味着模型在结构上无法表达「提价掉量」。** 提价 → 自然流量下降、转化率下降、CPC 上升 → 净效果可能为负，模型完全看不见。

**但系统已建了半个反馈回路**（后果侧）：

```
价格定高 → 周转变慢 → 库龄涨 → 档位下沉 → 让利上限变大 → 纪律线下降 → 最低售价下降
```

系统建模了**后果**（库龄 → 让利权限），没建模**原因**（价格 → 销量）。

**规范条款**

- 商品中心的定位是**「价格下限与投放边界工具」**，**不是「最优定价工具」**
- 测算 tab 必须显示免责提示：「本表不预测销量；售价上调对自然流量与转化率的影响需另行判断」
- 若将来要做价格优化，需引入 SKU × 平台的历史成交价分布与价格带表现（原料在 `b_class.fact_*_orders_monthly`），**单独立项，不在本 spec 范围**

### 6.0.1 业务侧视角：这次到底变了什么

**一句话**：商品中心从「只管价格下限」变成「也管广告投放的边界」。**所有新增都是只读展示或改名，没有一项要求运营多填新东西。**

| 东西 | 业务上的说法 | 运营要做什么 | 我们要改什么 |
|---|---|---|---|
| 保本ROI / 建议ROI | 「这个品投广告，ROI 低于 X 就亏，建议设 Y」 | **什么都不用填**，看一眼 | 加两列（只读） |
| 等效单均净利 | 「按建议ROI 投，每单我净赚 5.68 元（净利率 8.4%）」 | **什么都不用填**，看一眼 | 不用加列，**改文案**（说明「参考成本利润」已扣广告费） |
| 目标ROI | 「这单我打算设多少」 | 手填一个数 | 加一列（手填） |
| 平台报告ROI | 「后台跑出来是多少」 | 手填一个数 | 加一列（手填） |
| 广告费率 → 广告分成率 | 「广告费占广告前利润的几成」 | **原来怎么填，现在还怎么填**（阶段 3 后折叠进「高级」，主流程不用碰） | 加一个并排显示的「等效目标ROI」 |
| 重估利润 → 混合成本利润 | 「物流用真实账单，仓储还是按规则估的」 | **什么都不用填** | **只改名 + 加提示，不动计算** |

**「双源并存」是什么意思（一句话）**：同一个格子有两种填法——

- 运营填了「目标ROI」→ 系统自己倒推广告费，**这个格子变成只读**
- 没填「目标ROI」的老 SKU → 跟现在一模一样，**手填广告费率**

界面上标一句「本行广告费由目标ROI自动倒推」还是「本行广告费为人工填写」，避免看混。**手填那条路径完全保留、零改动。**

**「混合成本利润」是什么意思（一句话）**：现在那列叫「重估利润」，听起来像"全部用真实数据重算了一遍"。但实际上——

- **物流费 = 真实账单**（运费账单是真的）
- **仓储费 = 规则估算**（系统里根本没有仓储费账单，只有"每立方米每月多少钱"的规则）

所以它其实是"一半真、一半估"。改名「混合成本利润」，鼠标悬停提示「仓储成本为规则预估」。**计算逻辑一个字不改。**

**「广告费率的来历」怎么处理（一句话）**：它原本是「我准备拿多少利润出来做广告预算」——**这是同一个投放决策的另一种说法，不是两套逻辑**（`等效目标ROI = 保本ROI ÷ 广告费率`，精确恒等）。所以做法是：**运营手填的输入收敛成「目标ROI」一个**（平台上填的就是它，运营手上本来就有），同时把旧直觉翻译给他看——「建议ROI 2.36 = 每单净赚 5.68 元」。**不新增预算字段**（月度预算需要销量预测，做不了，见 §5.3）。

**明确不做的事**（防止做重）：

- 不做销量预测、不做价格优化建议
- **不新增运营必填项**——新增列全部可空，不填不影响现有流程
- **不改任何现有计算公式**——成本线、纪律线、最低售价、利润，一个公式都不动
- 不做历史数据重算
- 不改飞书投影逻辑（只改投影层的列名）

### 阶段 1 · ROI 只读层（零风险，单独上线即有价值）

**后端**：新增纯函数模块 `backend/services/product_roi_service.py`（无 ORM、无 DB）：

```python
def compute_roi_metrics(
    *, net_revenue, pre_ad_profit,
    safety_margin: Decimal = Decimal("0.20"),
    target_roi_ceiling: Decimal = Decimal("50"),
) -> dict:
    """
    net_revenue    商家实收 = 测算售价 − 卖家优惠券（= TikTok GMV，见 §2.4）
    pre_ad_profit  广告前利润
    target_roi_ceiling  平台可填上限的全局最大值（各平台取 max，见 §2.5⑨）
    返回：advertising_contribution_margin_rate / break_even_roi / suggested_roi
          / suggested_roi_clamped / suggestion_note
    """
```

| 输出 | 公式 | 口径 |
|---|---|---|
| `advertising_contribution_margin_rate` | `pre_ad_profit ÷ net_revenue` | 广告前贡献毛利率 p |
| `break_even_roi` | `net_revenue ÷ pre_ad_profit` | 保本ROI（**分母口径见 §2.5⑦**） |
| `suggested_roi` | `break_even_roi × (1 + safety_margin)` | 建议ROI（未封顶） |
| `suggested_roi_clamped` | `min(suggested_roi, target_roi_ceiling)` | **真正填进 GMV MAX 的值** |
| `suggestion_note` | — | `above_platform_ceiling` / `null` |

> `target_roi_ceiling` 挂在平台维度（`dim_platforms`，TikTok 20 / Shopee 50），计算时取各平台的最大值。封顶逻辑属于**必须实现项**——保本ROI 超出可填范围时，给一个填不进去的数比不给更糟。
> **不封底**（理由见 §2.5⑨）：保本ROI < 1 是异常信号，该报错不该被 clamp 掩盖。

在 `build_platform_profit_preview` 的 `expected` / `actual_recost` 两段各输出这三个字段。

**同批修 C4（测算售价来源标记）**：新增 `expected_selling_price_source`（两张表，§4.4）。前端**停止预回落**——把 `null` 传上去，由后端统一回落并打标；否则前端回落一次、后端回落一次，两处的 `fallback_from_baseline` 判定会打架。

**前端**（利润测算 tab，最低售价右侧）新增 3 个只读列：

| 列 | 内容 | tooltip |
|---|---|---|
| 广告前贡献毛利率 | `p` | 「扣掉采购、物流、仓储、贴单、平台佣金、达人佣金、货损、退货后的占比。分母是商家实收（售价−优惠券），与平台 GMV 同一口径」 |
| 保本ROI | `1/p` | 「低于这个 ROI，广告就是亏的（财务口径）。分母为商家实收，与平台 GMV 同一把标尺」 |
| 建议ROI | `min(保本ROI × 1.2, 50)` | 「保本线上浮 20%（业界惯例 20–30%）。超过平台可填上限时截断，并提示广告空间不足」 |

**必须同时显示的两个「翻译」数**（§2.5⑪，否则运营看不懂 ROI）：

| 翻译 | 公式 | 回答 |
|---|---|---|
| **等效目标ROI** | `保本ROI ÷ 广告分成率` | 阶段 1/2 手填广告费率时，把「广告费率」翻译成平台能填的数 |
| **等效单均净利** | `广告前利润 − 广告费用`（= 现有「参考成本利润」列） | 「投完广告我还剩多少」——**不需要新增列，但文案要说清它已经是扣完广告费的数** |

> 「等效单均净利」是「利润分配」诉求的真正答案。运营原来的问法是「我准备拿多少利润做广告」，新问法是「建议ROI 2.36，我每单净赚 5.68 元、净利率 8.4%」。**同样一件事，换成平台语言，而平台语言能直接填进后台。**

**成本完整度守卫（必须同批实现）**：

- `reference_cost_status != 'ready'` 时，三个 ROI 数字**置灰**
- 显示「成本不全，保本ROI 偏乐观」
- 缺失原因按 `reference_cost_missing_reasons` 的三个清单分列显示（缺物流规则 / 缺周转类型 / 缺SKU体积）

> ⚠️ 这是本阶段**最容易出事**的点。成本不全 → `pre_ad_profit` 高估 → p 偏大 → 保本ROI 偏小 → 看起来宽松 → 运营真投广告 → 亏损。**没有这个守卫，本阶段不能上线。**

**同时补两条免责提示**：

1. 「本表不预测销量」（§5.3）
2. 「平台报告ROI 含自然流量与达人归因，达标不等于赚钱」（§2.5⑧）

第 2 条必须和 ROI 列同批上，否则运营会把后台抄来的数字直接当利润判据。

**安全边际做成配置项**，不写死在代码里。建议挂到 `dim_platforms`（按平台）或新建一张规则表；第一版可先用常量 + 注释，等有实际投放数据再拆。

### 阶段 2 · ROI 输入与判定

新增 2 个手填列：

| 列 | 内容 | 校验 |
|---|---|---|
| **目标ROI** | 运营从 GMV MAX 抄来的计划值 | `> 0` |
| **平台报告ROI** | 运营从后台抄来的实测值（**含自然/达人归因**） | `> 0` |

**来源标记**：两列都配 `*_roi_source`（`operator` / `platform_feed`）。理由与 §4.4 的测算售价来源同源——**接了平台广告消耗采集后，平台报告ROI 应能被自动值覆盖**，字段设计时就要留出这个位置（§2.5⑧）。

三色判定（行内）：

```
平台报告ROI < 保本ROI            → 🔴 亏损投放
保本ROI ≤ 平台报告ROI < 建议ROI    → 🟡 有利润但未达财务目标
平台报告ROI ≥ 建议ROI             → 🟢 达标
目标ROI < 保本ROI                 → 🔴 目标ROI低于保本线，这单投了就是亏
```

最后一条是商品中心相对平台后台的**增量价值**——平台建议值不知道商家的财务底线。

> ⚠️ **三色判定必须带归因警示。** GMV Max 的归因窗口（7天点击+1天浏览）把自然流量和达人带货也计入归因 GMV，所以「🟢 达标」很可能只是归因虚高。判定行必须同时显示：「平台报告ROI 含自然/达人归因，真实广告ROI 约为 报告值 ÷ 归因放大系数」。**商品中心目前拿不到归因放大系数**（需要平台广告数据源），所以第一版只能给警示文案，不能给数字——**给不出数字时宁可不给，不能编**。

**「广告分成率」列同时展示等价 ROI**：`等价ROI = 1 ÷ (p × 广告分成率)`，让两个口径同时可见（此时该列仍手填）。

### 阶段 3 · 广告分成率降级 + 字段瘦身

1. **广告分成率的手填入口取消，降级为「由目标ROI派生的只读值」**：
   ```
   广告费用 = 商家实收 ÷ 目标ROI          （与平台标尺一致）
   广告分成率 = 广告费用 ÷ 广告前利润
   等效目标ROI = 保本ROI ÷ 广告分成率      （手填阶段一直并排显示）
   ```
   - **主手填输入只剩「目标ROI」一个**（§2.5⑩）
   - 手填广告费率**降级为高级逃生口**：默认折叠，需显式展开才能改，旁边永远并排显示「等效目标ROI」
   - 存量 SKU 用 `等效目标ROI = 保本ROI ÷ s` 反解出 `target_roi` 初值，源标记 `migrated_from_legacy_rate`
   - **不一步到位**：阶段 1/2 期间手填与派生并存（此时目标ROI 刚引入，运营还在适应），阶段 3 才收口
2. **移除「物流方式」列**（与顶部筛选器完全重复）。
3. **「实际物流 / 实际仓储」折叠进「混合成本利润」的 tooltip**（改名理由见 Q4，§13）。
4. **表头分组**：`标识 | 定价 | 参照 | 成本 | 广告 | 结论`（`el-table` 不支持多级表头，用列名前缀图标或分组行实现）。
5. **竞品价格加提示**：「只影响竞品价差展示，不影响利润」。

### 阶段 4 · 基准售价治理（规则与工具落地）

**归属决策（Q6 已定）**：基准售价由**对应的运营自己填**，系统侧只负责把规则和工具落地，**不推动批量补齐、不替业务判断价格**。

这个决策把阶段 4 的风险等级从「中」降到「低」——**没有人会被系统批量改动底线**，每次改动都是单个 SKU、单个人、看得见后果的决定。

我们交付的是**四样工具**：

| # | 工具 | 具体做法 | 验收 |
|---|---|---|---|
| 1 | **来源可追溯** | `selling_price_source` 从自由文本改为枚举：`platform_listing` / `erp` / `manual`。⚠️ `platform_listing` 当前**无可靠数据源**（`feishu_projection_service.py:406-408` 明示"平台 SKU 档案靠人工维护，覆盖率未知"），保留枚举位但不承诺可采集 | 枚举 CHECK 约束生效；历史自由文本已清洗 |
| 2 | **确认日期** | `selling_price_confirmed_at` 字段已存在（`dimensions.py:215`）但 **SKU 资料 tab 无输入框**。补上，填基准售价时自动写当天 | 填值自动写当天 |
| 3 | **即时影响预览**（最重要） | 运营填基准售价的**当场**显示：「该 SKU 最低售价将从 **28.23** 变为 **63.00**（**+123%**）」，并标明原因是纪律线生效 | 填值即时反馈，不用保存后才知道 |
| 4 | **偏差校验 + 过期巡检** | 与历史成交价中位数偏差 > 30% → 提示；`confirmed_at` 超 90 天 → 标黄「基准售价已 N 天未确认，纪律线可能失真」 | 提示可复现，不误报 |

**工具 3 为什么是最重要的**：基准售价填错的**最大风险不是亏本，是货卖不动**（基准售价偏高 → 纪律线偏高 → 最低售价被顶高 → 护栏把品拦死）。这个风险**必须在填的瞬间被看见**，而不是等护栏生效后再回头查。

**工具 4 的前置依赖**：SKU 级历史成交价目前**取不到**——`sql/semantic/orders_atomic.sql` 已有 `platform_sku` / `product_sku` / `sku_id`（从 `raw_data` 提取），但**没有 join `bridge_erp_sku_keys` 映射到 ERP SKU**。补这个 join 即可得到 SKU 级成交价分布。

> 这也修正了 §12 原第 3 条的旧结论：「订单表商品键全空」不准确——键是有的（平台侧），**缺的是到 ERP SKU 的映射**。

**纪律线抬价的量级预警**：基准售价填 70、成本线 28.23 的 SKU，最低售价会从 28.23 跳到 63.00（**+123%**）。工具 3 必须把这个量级直接显示出来。

### 阶段 5 · 指标口径治理

`roas` 与 `mer` 在 `docs/team-skills/sea-metrics-language/references/metric-status.md:28-29` 状态是 **blocked**（"尚未形成统一系统口径"，owner=marketing，不允许作为会议最终结论）。

3. `platform-mapping.md` 的 blocked 列表同步

## 10. 测试清单

### 10.1 后端单元（无 DB，纯函数）

| 用例 | 断言 |
|---|---|
| 保本ROI 公式 | 给定固定输入返回精确值 |
| 保本ROI = 1/p | `break_even_roi × p == 1` |
| 建议ROI | `= break_even_roi × 1.20`（默认安全边际） |
| **建议ROI 封顶** | 保本ROI × 1.2 超过上限时 `suggested_roi_clamped == 50` 且 `suggestion_note == 'above_platform_ceiling'`，且 `suggested_roi` 保留未封顶原值 |
| **不封底** | 保本ROI < 1 时**不** clamp，返回异常标记（成本算错的信号不该被掩盖） |
| **平台报告ROI ↔ 广告分成率互逆** | `平台报告ROI = 保本ROI ÷ 广告分成率` |
| **提价单调性** | 目标ROI ≥ 保本ROI 时，提高售价利润单调增（§5.3 结论） |
| 成本不全 | `pre_ad_profit` 缺项时 ROI 返回 None 而非乐观值 |
| 分母 ≤ 0 | 不抛异常，降级并记 `non_positive_cost_denominator` |
| **分母口径** | `break_even_roi == net_revenue ÷ pre_ad_profit`（**分母是商家实收，不是商品金额**） |
| **与平台标尺一致** | 商家实收 == `P − c`；断言其等于 `B + d`（买家实付 + 平台补贴），即与平台 GMV 恒等（§2.5⑦） |
| **广告费率 ↔ 目标ROI 恒等** | 给定 `s`，反解 `R = 保本ROI ÷ s`，代回 `pre_ad_profit × s` 与 `商家实收 ÷ R` **结果完全相等**（§2.5⑩） |
| **代码切换无差异** | 同一输入下 `ad_cost = revenue ÷ target_roi` 与旧式 `pre_ad_profit × ad_rate` 得到的 `profit` 一致 |
| **等效单均净利** | `广告前利润 − 广告费用` 与现有「参考成本利润」列一致（不新增列，只改文案） |

## 12. 已知限制与明确不做的事

1. **模型不预测销量。** 提价掉量无法在商品中心评估（§5.3）。要做需引入价格带，独立立项。
2. **成本线用平台平均黑桶 `other_cost_rate`**，对大件/重货 SKU 偏低。拆明细是 V2。
3. **达人佣金率未单独设置时用平台默认值**（tiktok 6.06%），实测波动 3.7%–33.8%，对高佣金商品偏低。当前不做自动回填——**订单语义层有 `platform_sku` / `product_sku` / `sku_id`（`sql/semantic/orders_atomic.sql:259-275`），但没有 join `bridge_erp_sku_keys` 映射到 ERP SKU**（原结论「订单表商品键全空」不准确：键是有的，缺的是映射）。补 join 后达人佣金与历史成交价带都可自动回填，独立立项。
4. **最低售价是公司统一口径**，不随平台/仓变化。要逐平台算底线需把 `platform_basis` 从规则表列改为 SKU×平台维度，数据模型要重做，属 V2。
5. **`turnover_class` 不参与定价**，且从未建立过经营分类（1121 SKU 仅 3 个有值）。
6. **保本ROI 的绝对值依赖成本完整度。** 成本不全时数字偏乐观，必须靠守卫拦截而非靠运营自觉。
7. **库龄管道在生产上长期未刷新**（`refresh_queue_tasks.py:96-122` 注释记录：旧判据下 `mart.inventory_state` 从未被刷新过）。若该链修通前定价档位仍全部走 `fallback_no_restock_days`，则"越滞销越该让利"这一层尚未通电——**底线本身是真的能用，只是档位没分层**。
8. **历史利润版本不重算**，新旧口径并存，报表需标注 `fee_rate_version` 与本次新增的口径标记。
9. **商品中心拿不到「归因放大系数」。** GMV Max 的归因窗口（7天点击+1天浏览）把自然流量与达人带货计入归因 GMV，所以平台报告ROI 天然虚高。商品中心目前没有平台广告数据源，**算不出真实广告ROI**，只能给警示文案。接入平台广告消耗与归因数据后，这条才能升级为数字判定（§2.5⑧）。
10. **实际仓储成本没有数据源。** 系统里不存在仓储费账单（`LogisticsBill` 全是运费构成，`transport_type ∈ (sea/air/rail)`），只有 `WarehouseStorageRule` 的规则预估。所以「混合成本完整度」的上限就是 `mixed`，`actual` 永不可达。要接真实仓储成本需引入海外仓月度仓储账单采集，格式各异，独立立项（Q4）。
11. **目标ROI / 平台报告ROI 都依赖人工抄。** 商品中心没有平台广告数据源，`actual_roi` 只能手填；来源标记（`*_roi_source`）为将来接采集留位（§7）。
12. **月度广告预算做不了。** 「这个月给这个 SKU 多少广告钱」摊到单均需要销量预测，而模型结构上不预测销量（§5.3）。单均广告投入可从目标ROI 精确导出（`商家实收 ÷ 目标ROI`），**但月度总额需另接销量数据源**，第一版不做（§2.5⑪）。

## 13. 待确认项

### 13.1 已决（2026-11-06）

| # | 问题 | 结论 | 依据 |
|---|---|---|---|
| Q1 | 保本ROI 的分母用哪个销售额口径？ | **用「商家实收」= 测算售价 − 卖家优惠券** | TikTok GMV = 买家实付 + 平台补贴 = `P − 卖家券` = 商家实收 → 与平台同一把标尺；换其他口径两个方向都可能出错（§2.5⑦） |
| Q2 | 安全边际取多少？ | **20%**，按平台可配 | 实测业界 buffer 是相对百分比 12%–25%，行业惯例 20–30%；取下沿保守。另**必须做平台档位封顶**（§2.5⑨） |
| Q3 | 广告分成率是否降级？ | **做。阶段 1–2 手填与派生并存（过渡期），阶段 3 手填入口取消、降级为高级逃生口** | 直接一步到位会让存量 SKU（无 ROI 数据）广告成本变 None → 利润空白，比现在更糟（§6 阶段 3） |
| Q4 | 「实际仓储」接真实来源还是删列？ | **删列；「重估利润」改名「混合成本利润」；接真实来源独立立项** | 系统里**不存在仓储费账单**——`LogisticsBill` 全是运费构成，`WarehouseStorageRule` 是规则预估。`actual` 完整度永不可达（§2.4） |
| Q5 | 目标ROI / 平台报告ROI 存哪？ | **目标ROI → `sku_operating_profiles`（计划值）；平台报告ROI → `sku_profit_estimates`（时点事实）**；各带 `*_roi_source` | 与测算售价来源标记同一条规范；来源标记为将来接平台采集留位（§7） |
| Q6 | 基准售价补齐由谁执行？ | **对应运营自己填；系统侧只落规则与工具**（来源枚举 + 确认日期 + **即时影响预览** + 偏差校验） | 决策已定。阶段 4 风险等级因此从「中」降为「低」——无人会被系统批量改动底线（§6 阶段 4） |
| Q7 | 目标ROI 封顶值取多少？ | **50**（各平台可填上限取最大：TikTok 20 / Shopee 50） | Walter 2026-11-06 提供。**只封顶不封底**——保本ROI < 1 是异常信号，该报错不该被 clamp 掩盖（§2.5⑨） |
| Q8 | 「广告费率」的来历是利润分配法，还需要吗？ | **不需要。运营手填的输入只保留「目标ROI」一个** | 「广告费率」与「目标ROI」是同一个变量的两种表达（`s = 保本ROI ÷ R`，精确恒等）。平台填的是目标ROI，运营手上本来就有；广告费率在后台永远看不到。**代码切换无差异**（`ad_cost` 两式恒等），存量可反解迁移（§2.5⑩） |
| Q9 | 「新品拿多少利润做广告预算」这个诉求怎么保留？ | **不新增字段，靠翻译**：界面给「建议ROI = 2.36 ≈ 每单净赚 5.68 元（净利率 8.4%）」 | 单均广告投入可从目标ROI 精确导出；**月度总预算做不了**（需销量预测，§5.3），第一版不做（§2.5⑪） |
