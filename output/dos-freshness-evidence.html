实测定案 · 2026-10-24 晚间

DOS 的分母到底新不新鲜

针对「库存清单只在库存数量更新时才更新，所以近 XX 天销量只是跟着刷新的附带值，DOS 不会实时刷新」 这一质疑，做了三条实测：真实页面连查复验、两批 1109 个 SKU×仓 的交叉比对、以及增量模式误差模拟。 结论：质疑的方向成立，但有一环不成立；而且真实的后果比原判断更严重——原先那句「偏差可忽略」是错的，已作废。

定案 · 2026-10-24 晚间DOS 降级为参考值，不做全域使用

妙手「近 XX 天销量数据」是行级存储快照：那一行被写入时才刷新，没被写入就原封不动。 实测当前增量筛选（更新时间维度 2026-09-01~10-08）只返回 151 个 SKU，而全量是 1113 行 / 56 页 —— 86.4% 的行，销量停在上一轮全量采集的那一刻。

模拟增量模式跑 2.5 天：5.0% 的行 DOS90 判档不同、滞销漏判 37 行（货值 ¥2,164）； 而且行越陈旧翻得越狠（更新时间距今 91–180 天的行，判档差异率 32.2%）。

Walter 拍板：采集策略已定 —— 不再全量，只有「配置采集 + 增量更新」。 所以「DOS 只认全量批次」的前提不成立，那个方案撤回。 滞销模块里的 DOS 简化使用库存数据域采集到的数据，明确标注「参考」，不做全域使用 ——不用它做入选、不用它做排序、不用它做汇总卡口径。

连带决定：滞销判据改用库存停滞时长（今天 − 库存最后一次真实变动的时间）， 由落盘层行内容 diff 维护、不信妙手的时间戳。DOS 保留在表里作参考值。详见第七、八节。

六、被推翻的旧结论

✕ 旧结论（已作废）

「实测偏差规模：可忽略。」
「『更新时间久远但销量非 0』只有 28 行、货值 ¥4,823.52，DOS 全落在 90~2160 天，会逃出滞销榜 0 行。」
「DOS 不需要为了『销量新鲜度』额外做全量兜底。」

错在哪：那 28 行是在全量采集的批次上量的——全量采集时每一行的销量都是当次采到的真值。 增量模式下这个前提不成立。

✓ 新结论

① 妙手销量是行级存储快照，只在行被写入时刷新；不是查询时重算，也不是独立更新的数据。
② 行被写入不只由库存数量驱动（93 行反例），所以「只因库存数量更新而更新」不成立。
③ 增量批次只覆盖 13.6% 的 SKU → 增量批次产出的 DOS 不能当滞销判据。
④ Walter 拍板：DOS 降级为参考值，不做全域使用——不用它做入选、排序、汇总卡口径。
⑤ 滞销判据改用库存停滞时长（事件时刻，增量下始终准确）；dos_as_of / dos_stale 一律取消。

八、滞销判据换成「库存停滞时长」

DOS 降级为参考后，模块仍然要有入选标准。实测表明库存停滞时长比 DOS 更适合当判据—— 它是事件时刻，不会因为时间流逝而漂移。

维度DOS（库存 ÷ 近90天销量）库存停滞时长
数据性质流量近似 → 分母会漂移（窗口前移就变）事件时刻 → 不会漂移
增量模式下的准确性只对本次采到的 13.6% 行新鲜，其余停在旧值始终准确（增量只更新变动行，未变动的行本来就对）
长期运行陈旧行累积，误差不收敛（91–180 天桶差异率 32.2%）单调增长，不会漏判
刚补货的新货会误判成老积压（近90天没卖）不会（刚变动过，停滞天数小）
依赖谁维护依赖妙手维护的销量列只依赖库存数量，由落盘层自己 diff 出来

实现要害stock_changed_at 必须由落盘层自己 diff 出来

不能用妙手的「更新时间」——实测 file 2764 有 535 行（43.7%）的更新时间被一次 bulk UPDATE 批量覆盖，而那批行的库存和销量完全没变。落盘层只认「库存数量真的变了」。 现有两批对比中 388 行可算出真实变动时间，其余行从第二轮起完全自维护。

九、落到设计上的三条硬要求

  1. 变更判定双闸：妙手「更新时间」筛选只用来缩小候选集；是否记为真变更由我方比对行内容 （可用库存 / 库存总量 / 预占库存 / 近N天销量）决定。批量戳时间戳的行不进观测层，水位线也不被假变更推着走。
  2. 变更判定双闸：妙手「更新时间」筛选只用来缩小候选集；是否记为真变更由我方比对行内容 （可用库存 / 库存总量 / 预占库存）决定。批量戳时间戳的行不进观测层，水位线也不被假变更推着走。
  3. 滞销判据换成库存停滞时长：stock_changed_at 由落盘层的行内容 diff 维护； 滞销入选、汇总卡口径、排序主键全部改用它，不再用 DOS。
  4. DOS 保留为参考列并标注「参考」：简化计算，不做口径时点管控（dos_as_of / dos_stale 一律取消）； 指标词典里 DOS 条目必须写明「不作判定依据」与「能证明什么 / 不能证明什么」。
连带修正商品中心最低售价：本来就该用库龄，不该用 DOS

商品中心的 min_age_days 存的本来就是库龄门槛——它要的就是库龄。 早先「改用 DOS 选档」的建议是方向性错误，已撤回：名实不符要修的是 tier_label 文案，不是把数据源换掉。

实测还查出两个更硬的问题：① 四档折扣从未生效过——逐 SKU 复算 1122 个 active SKU，全部命中日常档 0.10 （495 个 age_days 全在 0~13 天 + 627 个走 None 兜底，两条路都掉进最小门槛行）； ② 锚点修好后库龄仍不够用——妙手「创建时间」是首次铺货时间，98.5% 的行 ≥180 天， 直接选档会 1060/1076 个 SKU（99%）落最深档，而「还在卖的老品」430 行 / ¥187,980 是真滞销的 5.8 倍。

→ 定案：商品中心也用「库存停滞时长」选档（SKU 级取各仓最长）， min_age_days → min_stall_days，标签改名，阈值 0/30/90/180，折扣率不动； 与滞销模块共用同一份实现。
