口径命名决策 · 2026-10-24

这个 DOS 不该叫「快捷 DOS」

系统里会有两种 DOS：一种用 ERP 订单数据算（正常 DOS），一种用妙手库存清单自带的销量列算（现在这个）。 它们数值不同、依据不同，但名字都长得像「周转天数」。这次要把两个口径的命名一次定死， 让后续任何 agent 看到字段名就知道它算的是什么、依据什么、能不能进结论。

采集策略已定：不再全量，只有配置采集 + 增量更新。妙手「近 XX 天销量」是行级存储快照，只在那一行被写入时才刷新，增量批次实测只覆盖 13.6% 的 SKU（151 / 1113）→ DOS 不作判定依据。

→ 滞销判据改用库存停滞时长（今天 − 库存最后一次真实变动的时间，由落盘层行内容 diff 维护，不信妙手的时间戳）；DOS 保留在表里作为参考值，并明确标注「参考」。完整取证见 output/dos-freshness-evidence.html。

为什么「快捷」是错的名字

「快捷」描述的是我们做这件事时省了多少事，不是一个指标是什么。三个具体后果。

误因它暗示了一个错误的紧迫感

名字带「快捷 / 临时 / 近似」，后续 agent 会本能想「等订单口径修好就换成它」——于是两边各写一份口径。 而「唯一实现」纪律正是商品中心最低售价与滞销模块能对齐的前提，一旦分叉就会出现 「页面按日常档显示、通知却按滞销档发」这类自相矛盾。

误因它其实冤枉了自己的数据

实测证明库存清单的销量列不是估算值：全量 1113 行 + 另一批次 1226 行， 7 ≤ 30 ≤ 60 ≤ 90 零违例，全整数、非负、跨批次自洽。 若是估算，长窗口出现回落是必然的。「近似」在事实层面就不成立。

误因它把「口径差异」说成了「质量差异」

两个 DOS 的差别不在精度高低，而在依据的数据不同：平台侧统计的销量 vs ERP 重算的销量 （退款、取消、归属时间窗、时区都会造成差）。用「精确 vs 近似」描述，会让后续 agent 在做差异归因时找错方向。

更要紧的是：这个方案其实是唯一能做仓库级 DOS 的方案

结论

仓库级 DOS 只能来自库存清单自带的销量列。订单口径 DOS 修好后能提供的是 SKU 级的交叉校验基准， 不是替代品。所以它不该被命名为「临时/快捷」，它是一个独立成立的口径。

命名方案：沿用仓库已有的口径语言

仓库里已有 docs/team-skills/sea-metrics-language/SKILL.md，规定了三层口径 （平台原生 / 系统统一 / 会议决策），并明确「不要把平台原生指标和系统统一指标混成一个结论」。 这个决策直接沿用该词典词汇，不再另造「快捷」这类词。

可用结论

不矛盾：DOS-30 判「<30 天」的 37 行，在 DOS-90 口径下没有一行落到 ≥180 天， 30 天口径不会把快断货误判成重度积压。
30 天会误判滞销：有 74 行近 90 天卖过但近 30 天没动，30 天窗口会直接判成滞销，90 天窗口能识别出来。 → 滞销判定用 DOS-90，DOS-30 只作补货信号与辅助列。

两个容易读错的地方
  • 口径（窗口） DOS-30 / DOS-90 = 销量取多长的窗口 → 表格列
  • 分档（严重度） <30 / 30–90 / 90–180 / ≥180 → 状态标签 / 色阶

落地时必须一起做的几件事

  • 语义层需暴露销量列：semantic.fact_inventory_snapshot 目前没有任何 sales 列，mart 层只有 daily_avg_sales（来自订单口径）→ 落地 DOS 必须先在语义层投影 4 个销量窗口
  • 唯一实现：DOS 计算收敛到一处（纯函数 + 唯一取数路径），滞销模块与商品中心最低售价都调它
  • 禁止哨兵：DOS 不可算时返回 NULL + 独立状态标签，不允许 9999
  • 改名清单：对外字段 estimated_turnover_days → order_dos_sales30；新增 checklist_dos_sales30 / checklist_dos_sales90
