由此确定的三个粒度事实

已取证
「更新时间」是行级，不是商品级
1113 行里 37 个 SKU 跨两个仓出现，且它们的创建时间与更新时间两两不同 （例：HKR-GNH-Cream 在 A 仓是 2026-01-20，在 C 仓是 2026-07-05）。同一 SKU 在不同仓是两个独立行，各有自己的时间戳。
主键是 SKU × 仓库（仓位几乎不参与）
1113 行 = 1113 个唯一 SKU×仓库组合，零重复；去重 SKU 为 1076 个。仓位 1080 行「无仓位」、32 行空值、仅 1 行有具体仓位号 —— 仓位可先不进主键。
筛选命中的是「该行最后一次被改动的时刻」
不是"这期间变动过"，而是"这行在妙手里的最后修改时间落在区间内"。同 SKU×同仓不存在多时间戳，说明每行只保留最新状态。
所以「增量」= 该行的状态被刷新过，不含期间变动量
筛选返回的是这些行的当前值（库存总量、可用库存等），不是区间内的进销流水。要拿"变动量"仍需订单域。

第三步 · 重新设计落盘与使用

增量采集不能沿用现在的落盘结构

现在的链路是 全量快照 → fact 表 → latest 视图取最新。 增量一旦接入，这个结构会立刻崩：批次只覆盖部分行，而 metric_date 是批次级的， 新批次日期一旧就被旧批次压回去 —— 这正是今天「1113 行只进了 4 行 latest」的根因。

① 采集层

按增量重录
仓库清单页新增「更新时间」区间筛选 → 只导出区间内被更新过的行。 组件已有可复用的日期范围能力（date_picker.py 的 apply_custom_range）， 订单域的 _ensure_date_range_from_config 就是现成范式。
读配置
沿用 time_selection / custom_date_range，从 ctx.config 取 start/end
写回行级时间
导出文件自带「更新时间」列，落地时存为该行的 observed_at，这是整套设计的锚

② 落盘层

必须改
把现在的「批次快照堆叠」拆成两层。
观测层 · 增量事实表
每行 = 一次观测（SKU×仓 @ observed_at）。只写本批新增的行，体积随增量线性缩小。

行级 observed_at取代批次级 metric_date —— 这是根治"旧批次压过新批次"的关键。
状态层 · 当前库存
每个 SKU×仓永续一行，按 observed_at upsert。增量批次只覆盖被刷新的那部分，未命中的 SKU 保留旧值 —— 状态天然完整，无需全量重建。

③ 使用层

跟着改
所有下游视图的"取最新"排序键，从 snapshot_date DESC, ingest_timestamp DESC 改成 observed_at DESC, ingest_timestamp DESC。改完的实测效果（用现有两批数据回放）：

最新批次只贡献 4 行，旧批次占 1226 行。
新采集的数据基本进不了下游。

第四步 · 顺带必须处理的两件事

增量改造会连带暴露两个既有缺陷

这两件不是增量引入的，但增量一旦上线，它们会从"暂时没修"变成"天天出错"。而且都有低成本解法。

库龄算不出来

现状 495 行全在 0-30

库龄锚点用的是 snapshot_date（快照日），算的是"距上次快照多少天"，不是货放了多久。 结果 age_days 最大只有 13 天，>30 天的 SKU 数为 0， 商品中心 56% 的 SKU 因此走 fallback_no_age_data 兜底档。

现状库龄分桶
0-30: 495
按「创建时间」重算
180+: 1096

真实分桶：0-30 → 4 行，61-90 → 8 行，91-180 → 5 行，180+ → 1096 行。 库龄能力立刻从"几乎无区分度"变成"可用"。

预计周转天数全是 9999

499 行哨兵值

inventory_backlog_base 的 30 天销量取自 semantic.fact_orders_atomic， 而该表 31012 行里没有任何 miaoshou 数据（只有 shopee 26341 / tiktok 4671）， 于是"有库存但零销量"被判成 9999，进而把 risk_level 全推成 high。

第五步 · 增量不能自举

必须配「全量水位线」，否则会静默漏数据

这是增量模式最容易出事的地方：增量只能告诉你"变了什么"，不能告诉你"漏了什么"。 若某次采集失败、某段时间断档、或某个 SKU 被从妙手删除，增量永远查不出来 —— 数据静默陈旧。

  1. 水位线记录在状态层，不在配置里

    每批成功落库后，记录该批的 max(observed_at) 与 ingest_timestamp。 下次采集的默认区间 = [上次水位线, 本次采集时刻]，而不是人工填的日期。

    当前可用的水位线：file 2764 → 2026-09-15 00:02:32　｜　file 3004 → 2026-10-24 12:13:32

  2. 断档超阈值 → 自动回退全量

    若本次请求区间与上次水位线之间存在缺口（比如中间失败了 3 天），增量结果不可信。规则：缺口 > 阈值（建议 3~5 天）时自动降级为全量采集，并在结果里标记原因。

  3. 首次接入 → 强制全量一次

    状态层为空时，增量只会写入少量 SKU，其余全部缺失。首次必须跑一次全量建立基线，之后才允许增量。

  4. 周期性全量兜底

    建议每周或每月一次全量快照，用于捕捉删除/下架/人为改动，并校验增量结果与全量的差异。

  5. DOS 降级为参考值，滞销判据改用「库存停滞时长」（2026-10-24 晚间定案）

    妙手「近 XX 天销量」是行级存储快照，只在那一行被写入时才刷新。实测增量筛选只覆盖 13.6% 的 SKU（151 / 1113），其余 86.4% 的行，销量停在上一轮全量采集的那一刻。

    模拟增量跑 2.5 天：5.0% 的行 DOS90 判档不同、滞销漏判 37 行（货值 ¥2,164）； 行越陈旧翻得越狠（更新时间距今 91–180 天的行，差异率 32.2%）。

    → DOS 降级为参考值：不用它做入选、不做排序、不做汇总卡口径， 不用再做口径时点管控。滞销判据改用库存停滞时长（今天 − 库存最后一次真实变动的时间）—— 事件时刻，不随窗口漂移，增量下始终准确。详见 output/dos-freshness-evidence.html。

变更判定也要双闸：别只信妙手的「更新时间」

实测发现：file 2764 有 535 行（43.7%）的更新时间被一次批量操作整体覆盖成 2026-05-08 10:36:36~39；另外有 93 行（8.4%）库存数量完全没变、 销量却变了 —— 说明妙手在非库存变动时也会写行。

所以：妙手的「更新时间」筛选只用来缩小候选集；是否记为真变更，必须由我们比对行内容 （可用库存 / 库存总量 / 预占库存 / 近N天销量）自己决定。

时间筛选解决的是"降压"，解决不了"数据完整性"

两件事是独立的：时间筛选让采集变快、让入库和 SQL 刷新变轻；数据完整性与 9999 靠的是落盘模型和销量口径。 两者要一起做，不能只做前者就以为问题解决了。
