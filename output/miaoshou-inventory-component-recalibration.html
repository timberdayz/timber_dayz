旧假设 vs 真实结构

旧 · 假设存在
.jx-picker-panel
.jx-picker-panel .jx-select

全部押在 class 上。class 是 UI 库的实现细节、随版本变； 页面一改版，8 个选择器同时失效 → 必然报「面板打不开」。

真 · 页面实际长这样
仓库: 全选 ✕ +4商品SKU ▾
是否有预占库存可用库存 ▾
创建时间 ▴ 开始时间 ____-结束时间 ____ 🔍 搜索重置
创建时间更新时间 ← 下拉浮层里就这两项

维度是内联下拉（触发器直接显示当前维度名），日期区间是内联两个输入框， 填完直接点「搜索」 —— 没有「确定 / 清空」按钮。

新策略：认文案，不认 class

环节旧（猜 class）新（认文案）为什么
维度下拉.jx-picker-panel .jx-select找可见的「创建时间 / 更新时间」文字文案是业务语义，稳定
维度落地证据modelvaluegroup 以 gmtModified 开头触发器文案变成「更新时间」人能读、能看懂
浮层可见等 .jx-picker-panel 出现等「更新时间」变得可见浮层展开 = 它出现
区间输入框.jx-picker-panel input.jx-range-inputinput[placeholder*='开始时间'] / '结束时间'placeholder 就是语义
「确定」必经步骤，找不到就失败可选：有就点，没有不算失败页面本来就没有
区间证据读筛选器根的 modelvaluegroup输入框回填值（真实页面）/ 属性（老路径）两条路径，取到哪条算哪条
幂等

已经是「更新时间」就不碰下拉 —— 你可能已经手动选过，重复点反而把状态点乱。

顺序无关

读当前维度前先 Escape 收起浮层，避免把浮层里的选项误当成触发器上的当前值。

格式自愈

填 2026-10-01 00:00:00 没落进去，自动降级成 2026-10-01 再试。

流程改动：增量模式搜索两次

旧 · 基线是假的
  1. 全选仓库仓库范围就位
  2. 设筛选读「SKU总数」当基线 ← 其实已经是筛选后的了
  3. 搜索再读一次总数 → 两者永远相等
  4. 断言「相等 → 只警告」分支 → 永远不报错
新 · 基线是真的
  1. 全选仓库仓库范围就位
  2. 搜索 #1读「SKU总数」当基线（筛选前的真实口径）
  3. 设「更新时间 + 区间」维度落地证据 + 区间落地证据
  4. 搜索 #2让筛选生效，再读一次总数
  5. 断言筛选后总数不得超过基线
为什么要多搜一次？ 仓库范围和日期区间是两套独立筛选条件： 仓库选完不点搜索，页面上显示的还是上一次的搜索结果 —— 拿它当基线， 断言就是自欺欺人。**全量模式仍然只搜索一次，行为完全不变。**

顺带修掉的两个「假东西」

假断言

_sku_total_before 原本在筛选之后才读 —— 基线和结果永远相等， 于是「筛选是否生效」这条断言永远走「只警告」分支，形同虚设。

现在基线改到搜索 #1 之后读，断言才真正有牙齿。

隐性 bug

读输入框值时把 input_value()（无参）和 get_attribute("value")（有参）混用 —— 两者双双失败， 永远读到空值。

这个 bug 在真实页面上也会让「区间没落进去」被误判。

取证探针也重写了

旧探针也假设了 .jx-picker-panel —— 所以它跟组件一起错，一直没能给出真证据。新探针：

  • 不假设任何结构，直接抓真实 DOM：维度元素（含 class 与 outerHTML）、所有 input 的 placeholder/class/type、「确定/清空/搜索/重置」按钮、下拉浮层结构
  • 用组件自己的定位逻辑跑一遍 probe_state() → 探针的结论就是组件的结论，不会再出现「探针能找到、组件找不到」
  • 输出 output/probe_inventory_date_filter.json + 截图
  • 只读保证不变：不 save 登录态、不填区间、不点搜索、不点导出
